## 3. 改动面

### 3.1 `彼方条目.ts`：2 → 0

新增并导出 `世界书条目形状`（接口），`isBifangEntry` / `sanitizeBifangEntryName` 收它的类型。

**为什么这个形状放在这个文件**：本文件就是"怎么认出彼方条目"那份知识的所在地，而认条目靠的正是
"两种来源、两种字段名"这件事。形状放这里，改条目判定的人一定看得见形状。

**为什么不用 `Record<string, unknown>`**（#59 要求写清）：

| 方案 | 后果 |
| --- | --- |
| `Record<string, unknown>` | 每个字段读出来都是 `unknown`，下游每处都要断言或 `String(...)` 包一层；信息量为零 |
| `Record<string, any>` | 能过类型门，但等于换个写法写 `any`，#52 明确不许 |
| **可选字段接口**（采用） | 字段**名字**是确定的（只有两种来源），不确定的只是"这一条带了哪几个" —— 写成可选字段后 `entry.name` 直接得到 `string \| undefined`，调用方一眼看出"可能没这个字段" |

条目里其余字段（`uid` / `position` / `probability` / `recursion` / `effect`…）彼方从不读取，所以**不列**：
列了等于假装我们在维护它们，插件改一个字段就假报错。

**点名项 ①：`getWorldInfoActivatedData` 为什么不存在于 `{}`**

`取EJS模板环境` 的返回类型是 `Promise<unknown>`（`共用/条目求值.ts:566`，那是烟火的同名函数搬过来的），
旧代码写 `env && typeof env.getWorldInfoActivatedData === 'function' ? (n,t) => env.getWorldInfoActivatedData(n,t) : null`。
`unknown` 上取属性直接报错。

**我没有改 `共用/条目求值.ts`**（那是跨文件、且烟火也在用），而是在 `worldbook.ts` 本地把"取方法"与"调用方法"分开：

```ts
type 主AI激活函数 = (name: string, text: string) => Promise<世界书条目形状[] | null | undefined>;

function 取主AI激活(env: unknown): 主AI激活函数 | null {
    const 候选 = env ? (env as Record<string, unknown>).getWorldInfoActivatedData : undefined;
    return typeof 候选 === 'function' ? 候选 as 主AI激活函数 : null;
}
```

判定条件（`env` 真值 + `typeof … === 'function'`）**与原代码逐字相同**；改的只是"判完之后把函数存下来"，
于是调用处不必写 `!`、也不必再判一次。这比"给 `取EJS模板环境` 的返回值加个字段"更保守：
后者会让**三个调用方**（彼方、烟火 reader、烟火读书）都受影响。

**为什么只声明这一个方法、不描述整份环境**：EJS 环境是「提示词模板语法」插件的私有对象，
字段随插件版本变。把整份形状钉死，插件一升级就假报错；而彼方只用这一个方法。

**点名项 ②：`有正文条目` + `有正文()` 谓词**

原代码里"这条有正文、能注入"这个判断散在三处，写法一致：

```ts
if (!entry || entry.enabled === false || !entry.content) continue;   // 人设收集
Boolean(entry && entry.disable !== true && entry.enabled !== false && entry.content && …)  // 激活收集
```

收成谓词后，`matched` / `alwaysEntries` / `activatedAll` 的 `content` 在类型上就是 `string`，
下游（`收集表格名([entry.content])`、`entry.content.includes('<%')`、`求值条目文本(entry.content, …)`）
不必再写 `String(entry.content)` 或判空。**类型跟着过滤条件走，而不是靠人记**。

注意：谓词里**没有**改条件。`有正文()` 只判 `enabled !== false && content`；
`acceptsEntry` 里那三个额外条件（`disable`、`isBifangEntry`、`isExcluded`）原样留在原处。

**一处刻意的"不复制对象"**：中途我写成了 `matched.push({ ...entry, content: entry.content })` 来满足类型，
后来退回成 `matched.push(entry)` + 谓词。理由：展开会新建对象，`isBifangEntry` 之类按引用比较的路径
（现在没有，但将来可能有）会行为不同。**类型收窄不该改变对象身份。**

`validateParsedFormat` 里，开头已判过"非空、非数组对象"并抛错，之后取动态键：

```ts
const 顶层 = parsed as Record<string, any>;
```

**这句断言为什么可以接受**：顶层是模型给的动态字段（键 = NPC 名），形状只能到"任意键"这一层，
不是"没想清形状"。原来的 `parsed['剧情时间']` 在 `parsed` 是 `unknown` 时连索引都做不到；
断言之后读的是 `顶层['剧情时间']`，**取值路径与原代码完全一致**。

**点名项：`:319` `Property 'has' does not exist on type 'never'` 与 `:376` `Set<string> | null` 不能赋值**

这两条看起来像真缺陷（"这个分支永远走不到"），**核实后不是**：

```ts
let skipCheckNames: Set<string> | null = null;      // 原代码：无标注，TS 推断成 null
if (自动建档 === false) {
    skipCheckNames = new Set();                     // 只在这个分支里赋值
    …
}
validateParsedFormat(parsed, 现有卡 ?? {}, skipCheckNames);
```

形参 `skipCheckNames` 也没标注，于是 TS 用**实参**（此时是 `null` 字面量类型）反推形参类型 = `null`；
再往里，`if (自动建档 === false)` 分支里赋的是 `Set`，但形参已被定为 `null` —— 两个方向的推断撞在一起，
TS 把变量收成 `never`，于是 `.has` 不存在。

这是**推断退化**，不是运行时缺陷：赋值就在同一个函数体内，运行时 `Set` 是真的。
标注形参 `Set<string> | null` 后，两处一起消失。**没有改任何运行时逻辑。**
