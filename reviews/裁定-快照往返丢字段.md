# 裁定 · 快照往返丢字段（P0，2026-11-13 真机+可执行用例双重证实）

> 裁定人：opencode（需求/仲裁）
> 方法：**不是读代码推断**。先用真机读到 `收束起始场` 缺失，再用 `tests/build.mjs` 同一条打包链写可执行用例，证明「写盘有、读回没有」。
> 复现脚本：`tmp/prove-shousu-loss.mjs`、`tmp/prove-chongtu-loss.mjs`（都能直接 `node` 跑，输出带判定行）。

## 一、根因（一句话）

`账本迁移.ts` 的 `账本字段表` 是快照读写的**唯一白名单**：

- 写盘 `快照载荷()` → `for (const 行 of 账本字段表) 载荷[行.键] = 行.存(账本)`（`账本迁移.ts:302-305`）
- 读回 `sanitizeSnapshot()` → `for (const 行 of 账本字段表) data[行.键] = 行.读回(源, data)`（`账本迁移.ts:524-529`）
- 章回读回 `规范化章回()` → `规范化条目<章回>(取层('章回'), raw)`（`账本迁移.ts:397`）
- `规范化条目()` → **只遍历 `定义.字段`，逐字段复制**（`字段表.ts:435+`）

而 `字段表.ts` 的 `章回层.字段` / `冲突层.字段` 里**没有** schema 声明的那几个字段。

**后果**：这些字段能写进内存、能写进快照，但**下一轮读回就没了**。

## 二、实证（可执行，不是推断）

### 2.1 `章回.收束起始场` —— 确认丢失

```
原始 收束起始场 = 5
原始 收束已用场数 = 6
写盘 章回键 = [章号,主题,计划高潮,进度,起始场,收束起始场,幕纲,当前幕号]
写盘 收束起始场 = 5
读回 章回键 = [章号,主题,计划高潮,进度,幕纲,当前幕号,起始场]
读回 收束起始场 = undefined
读回 收束已用场数 = 0
判定: 写盘有=true 读回有=false
❌ 数据丢失：写盘存了，读回没了
```

**真机印证**（`tmp/cdp/probe-snap1539.js`，读 1539 楼快照原文）：

```
章回键 = [章号,主题,计划高潮,进度,幕纲,当前幕号,中点,起始场]
收束起始场_存在 = false
章回进度 = 收束
```

**这就是「收束出口没生效」的根因**：

- `引擎规则.ts:749` `const 收束起始 = Number(账本.章回?.收束起始场) || 0;`
- `:750` `if (收束起始 > 0)` —— 起点丢了 → 恒为 0 → **收束预算整段从不执行**
- `提醒.ts:118` 同一个 0 → `收束已用场数` 恒返回 0 → `章长度提醒` 在收束态直接 `return []`

真机状态与之完全吻合：第 1 章、进度「收束」、当前幕 5/5、已分析 78 轮，`收束起始场` 不存在。

### 2.2 `冲突.最后行动幕` / `冲突.最后行动天` —— 确认丢失

```
原始 最后行动幕 = 2  最后行动天 = 5
写盘 冲突键 = [名,对立面,赌注,强度,阶段,下一步,顶回次数,最后行动幕,最后行动天]
读回 冲突键 = [名,对立面,赌注,强度,阶段,下一步,顶回次数]
读回 最后行动幕 = undefined
读回 最后行动天 = undefined
判定: 写盘有=true 读回有=false
❌ 数据丢失：最后行动幕/最后行动天 读回后消失
```

**后果**（反舔机制失效）：

- `字段表.ts:366/378` `取该出手的对手()` 用 `当前幕 - (条.最后行动幕 || 0)` 算「对手多久没动手」
- 字段每轮读回变 `undefined` → `|| 0` → 逾期 = 当前幕 = 78 → **恒判"该出手"**
- `提醒.ts:240` `隔天 = 天数 - (该出手.最后行动天 || 0)` → 恒等于总天数

不是"没催"，是**恒催**：每轮都喊「对手该动手了」，而 `update.ts:476` 回写后下一轮又归零 —— 一条永远在响、永远无效的提醒。

### 2.3 完整性扫描（我核过的全部差异）

用 schema 接口与字段表逐层比对（`tmp/scan16.py`）：

| 层 | schema 字段数 | 字段表字段数 | 缺失 |
|---|---|---|---|
| 章回 | 9 | 8 | **`收束起始场`** |
| 伏笔 | 30 | 30 | 无 |
| 冲突 | 9 | 7 | **`最后行动幕`、`最后行动天`** |
| 弧线 | 4 | 4 | 无 |
| 角色命运 | 15 | 15 | 无 |

**只有这三处**。但每一处都在真机上有可见后果。

## 三、为什么现有用例全绿还是漏了

`tests/daoyan-收束出口.test.ts` 第 [6] 段全 PASS：

```
PASS  进收束: 记本场(=已分析轮数+1=10), 忽略模型给的 999
PASS  同章继续收束: 沿用起点
PASS  退出收束: 清空起点
PASS  换章后进收束: 重记本场
```

它测的是 `应用引擎输出()` **内存里**的值，从没跑过 `快照载荷 → sanitizeSnapshot` 这一趟往返。

**这就是假绿**：机制在内存里成立，一落盘就没了。而真机每轮都要落盘。

## 四、修法（最小改动，两处）

### 4.1 `字段表.ts` 章回层补一行

```ts
{ 键: '收束起始场', 属性: '结构', 数值: true, 形状: '数字' },
```

放在 `起始场` 之后（顺序有语义：读回时后面的行可以读前面填好的字段）。

### 4.2 `字段表.ts` 冲突层补两行

```ts
{ 键: '最后行动幕', 属性: '结构', 数值: true, 形状: '数字' },
{ 键: '最后行动天', 属性: '结构', 数值: true, 形状: '数字' },
```

放在 `顶回次数` 之后。

### 4.3 加一条**结构性**用例（防止再漏）

不写"逐个字段断言"，写**差集断言**：`schema` 接口的每个字段都必须在对应层的 `字段` 里出现，否则红。这样以后任何人往 schema 加字段忘了加进字段表，当场就红。

> 这条用例本身有代价：schema 接口要在运行时可见。如果拿不到类型信息，退一步用**文本解析**（读 `schema.ts` 源码，正则抽接口字段名，与 `取层(名).字段` 比对）。项目已有同类先例（`tests/run.mjs` 用正则扫源码做导入检查）。

## 五、与 P2 的关系（重要）

**这三处必须先修**，否则 P2 的任何改前/改后对比都不可信：

- P2 的 2.4（删反向豁免）改的是「代码要不要让位」
- 而 `收束起始场` 丢失让「收束预算」整段哑掉 —— 就算让位删了，收束出口还是不生效

**顺序**：先修字段表（本批），再跑 P2 的 2.4。

## 六、我这轮撤回的一个判断

我在 `reviews/取证-代码规则让位-真机.md` 里写过「P2 核心论断被运行时证实」。**结论本身成立**（`硬约束: null` + 「保留其节拍」是真机原文），**但归因要补一句**：

那份取证的 `硬性要求` 里带着 `（代码规则）` 前缀，而**当前源码已经不再生成这个前缀**（P0.5 拆通道后只写 `硬约束`，`引擎规则.ts:591/923` 两处赋值分别是 `''` 和 `ai硬性`，全文再无拼接）。

也就是说：**1539 楼那道指令是旧产物时代生成的**（楼层时间早于当前构建载入时间 08:53:01），它证明的是「旧代码会这样」，不是「当前代码此刻正在这样」。

这不影响 P2 的结论（`让位` 逻辑当前源码仍在，`引擎规则.ts:619`），但**改前/改后对比必须用新生成的指令**，不能用这条历史快照。
