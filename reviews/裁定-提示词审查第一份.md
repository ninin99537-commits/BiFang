## 零、我自己新查出的一条（不在后台报告里）

### 新-1 · D-2 只改了一半：同一次 `结构提醒` 里两个场号口径

`取料.ts:245` 已经改成传 `已分析轮数 + 1`（D-2 改的），`章长度提醒` 也接受了这个场号。
但 `提醒.ts` 里有 **4 个调用点没跟着改**：

```
提醒.ts:309   生活幕              const 判 = 判收章(账本);            ← 没传场号
提醒.ts:355   幕纲落后或该收章     const 判 = 判收章(账本);            ← 没传场号
提醒.ts:360   幕纲落后或该收章     if (选收章发言者(账本) !== '幕纲落后')
提醒.ts:788   节奏提醒            if (拖 && ... && !判收章(账本).该收)
```

**后果（可执行用例证实，`tmp/prove-d2b.mjs`）**：

```
已分析轮数 | 取料传场 | 谁在说"该收章" | 收章语义条数
        39 |     40 | (无人说收章)   | 0   ← ❌
        40 |     41 | (无人说收章)   | 0   ← ❌ 就是这一轮
        41 |     42 | 幕纲落后       | 1   ← ok
```

为什么是 0 而不是 1：

- `章长度提醒` 拿的是**新场号 41**，算 `长 = 41 - 1 + 1 = 41 >= 40`，本来该说"已经演了 41 场"；
- 但它先跑 `选收章发言者(账本, 41)`，那个函数内部 `判收章(账本, 41)` 是**新场号**，返回 `幕纲落后`；
- 于是 `章长度提醒` 按规则让位（`提醒.ts:705` `if (选收章发言者(...) === '幕纲落后') return []`）；
- 而 `幕纲落后` 那条规则自己调的是 `判收章(账本)`（**旧场号 40**），`演了几场 = 40`，**不超期**，于是它也 `return []`。

**两边互相让位，中间漏出一个空档。** 这就是 D-2 那句"同一轮两个「收束已用」差 1"的同一个病，只是这次漏在"谁该说话"上。

**修法**：把 `提醒规则表` 的 `生成` 签名里那个 `{ 当前幕 }` 用起来 —— 四个调用点全部改成传 `当前幕`。一行一个。

**这条比 D 批任何一条都该先修**，因为它让"该收章"这个最重要的声音在阈值那一轮彻底消失，而且**现有用例全绿**（`daoyan-D批-判据.test.ts` 没测"两规则同时让位"）。

## 一、成立的（9 条）

### #1 原著"严格贴合"档自相矛盾 —— **P0，成立**

`prompts.ts:241`：`严格贴合: '节点按序发生，主角只能改变过程与代价，不能改变节点结果。'`
`prompts.ts:256`：`主角的行动改变了某个节点的走向时, 该节点之后按已发生的结果重算...被撞毁的原著线把对应伏笔改为「已消亡」`

第 256 行不随档位关闭，`严格贴合` 下两行同时下发：一句禁止改结果，一句教它改了之后怎么办。
**后果最重的是后半句**：它要求"把对应伏笔改为已消亡"，模型照做会批量作废伏笔。

**修法**：第 256 行只在 `档 !== '严格贴合'` 时拼；严格贴合下改成"节点结果不可改写；若正文已写出相反结果，保留正文事实、把该节点标记为已偏离，不要求回拽"。

### #2 "每个未收档冲突都会主动出手" —— **P0，成立**

`prompts.ts:146` 说"**每个**未收档的冲突, 对手都会主动出手"。
代码（`字段表.ts:363-382`）只催**一条**，且只催 `升级/僵持/决战` 三阶段，且排除"强度 ≤3 且无伏笔挂靠"的杂兵。
同一轮 `提醒.ts:243` 还会明确告诉它"只这一条 —— 其它未收档的对抗本轮不必强行出手"。

**这是同轮自打脸**：导演读到"每个都要动"和"只这一条"。

**修法**：第 146 行改成与代码同口径。

### #4 "同一章只催一次"被兑现条件自检绕过 —— **P1，成立**

`prompts.ts:115`：`同一条线**同一章只会被催一次**`
`提醒.ts:597` 作者自己写明：`判"临期"时**不看催办节流**(最近催办章)`
`提醒.ts:601-617` 筛选条件里确实没有 `最近催办章`，且挂在每轮都跑的 `提醒规则表`。

**修法**：二选一 —— 改提示词（"窗口催办一章一次；兑现条件自检每轮都提醒"）或给自检加节流。**我倾向改提示词**：自检的价值就在于"每轮都问一遍你核对了没有"，加节流会把它变成另一个哑掉的机制。

### #5 "回收窗口只是最迟提示" —— **P1，成立**

`prompts.ts:110`：`目标窗口.最早章/最迟章 是权威窗口; 旧的 回收窗口 只是"最迟回收提示"`
`证据链.ts:165-166`：`const 最迟 = 显式最迟 ?? 旧窗口; const 最早最终 = 最早 ?? 旧窗口;`

只写 `回收窗口` 时，它**同时**当最早章和最迟章 → `评估窗口` 在"当前章 < 该章"时返回 `未到` → 提前兑现被挡住。
提示词说的"只是最迟提示"是错的。

**修法**：补一句"只写回收窗口时，它同时被当作最早章与最迟章"。

### #6 节拍结束 false 让"拖太久"失效 —— **部分成立**

`账本数据.ts:870-879`：`节拍结束 === false` 时 `最近节拍` **不追加**；`提醒.ts:803` `尾部同节拍` 数的就是这份历史。
所以导演诚实写 `false`，`节拍拖太久`（阈值 5）永远不触发。

**但"与提示词对撞"这个说法偏强**：`prompts.ts:175` 说的是"别为了每轮都换节拍硬塞剧情"，与"同一节拍拖 5 场该推进"不是同一件事，可以同时成立。

**真实缺陷只有一半**：`节拍拖太久` 的计数源不可靠。修法：改用 `当前节拍.已持续轮`（但要先确认那个计数器可信 —— 真机 `已持续轮 = 4` 说明它在工作）。

### #7 用「日常」当幕型反义词 —— **P1，成立**

`提醒.ts:243`：`**若这一幕是事件幕**(不是「日常」)`
幕型枚举只有 `事件/生活/收束`（`prompts.ts:149`），「日常」是**节拍**不是幕型。
"事件幕 + 日常节拍"这个组合下，这句话给出错误指令。

**修法**：改成"若这一幕**的节拍不是「日常」**"。

### #8 两个静默截断提示词从不说 —— **P1，成立**

- `引擎规则.ts:353` `if (out.length >= 8) break;` —— 知情核对静默截到 8 条
- `账本数据.ts:82` `读者领先上限 = 12`；`:694-698` 超出按"最久没动"淘汰

`prompts.ts` 全文没有这两个数。导演写第 9 条知情核对，那条**静默消失**。

**修法**：两段各补一句上限与淘汰规则。

### #9 "只增不减"与"少了的就没了"互斥，且命运册三字段不服从后者 —— **P1，成立**

`prompts.ts:105-106` 同一段里两句相反语义。
且这 5 个字段走两条路：
- 伏笔的 `知情角色`/`关联角色`：纯替换（`账本数据.ts:550-558` 的 `...规范`）
- 命运册的 `独立目标`/`承诺与债务`/`未竟计划`：走 `对账字符串列表`（`账本数据.ts:1051-1066`），**从有变空会被拒绝并保留旧值**

**修法**：删掉"只增不减"，改成"整份替换：少写的元素会消失；命运册那三个字段写成空数组会被判无证据复原、整体保留旧值"。

### #12 `下一幕.揭示` 代码在读，提示词从不要求写 —— **P2，成立**

`引擎规则.ts:990`：`for (const 项 of Array.isArray(下一幕?.揭示) ? 下一幕.揭示 : [])`
`prompts.ts:204` 模板的 `下一幕` 只有 `节拍/硬性要求/伏笔现场/禁止事项/必演/知情核对`，**没有 `揭示`**。

一条完整的通道永远填不上。导演想"这一幕必须让读者看到某条已确认的后果"时，只能塞 `硬性要求`，而那个通道在正文侧被标成"演法建议"。

**修法**：模板加 `"揭示":[]`，并补一句说明。

### #13 阈值措辞与判据差一 —— **P2，成立**

- `prompts.ts:96` "超过 6 条" vs `提醒.ts:577` `.filter(项 => 项.条数 >= 回响条数告警)`（= 到 6 就告警）
- `提醒.ts:459` "6 场以上" vs `:455` `>= 6`

**修法**：统一措辞（"到 6 条即告警"/"满 6 场没动即提醒"）。

## 二、部分成立（2 条）

### #3 冲突 ≤4 / 弧线 ≤5 是硬上限，代码从不裁剪 —— **部分成立**

`字段表.ts` 的 `容量` 注释确实说"这是单次发给模型的候选数，不是账本容量"，`归档终态` 也确实不裁剪。
但**这不是缺陷**：`prompts.ts:59` 的 `≤${冲突上限}` 是**创作指导**（"别堆太多线"），不是"代码会拦"的承诺。而且 `提醒.ts:252` 有"未收档 ≥3 就提醒先收掉一组"的软反馈。

**判：不改。** 唯一可改的是把 `≤4` 措辞从硬上限改成"工作集建议"，但这是产品口味，不是 bug。

### #10 生活幕"至少一幕"与"建议 2 幕"混写 —— **部分成立**

`prompts.ts:155` 一句里给了硬要求（至少一幕）和软建议（5 幕建议 2 幕）。
`提醒.ts:292` 只查"有没有"。

**这不算矛盾**，是"硬要求 + 加强建议"的常见写法。但拆成两句确实更清楚。**判：可改可不改，优先级最低。**

## 三、不成立的（5 条）—— 记在这里防止后续被当 bug 改掉

1. **#11 平静期"必演一律写 null"是空指令** —— `prompts.ts:347` 那句话的上下文是"平静期这一段只记账"，模型写 null 与不写等价，**没有害处**。说它"让模型误以为还在走流水线"是过度解读。
2. **#14 原著时间不可解析** —— 这是**输入质量**问题，不是提示词缺陷。提示词已经写了"先后以索引排列与时间为准"，给了降级路径。
3. **#15 三处"必须"无校验** —— `时间推进天数` 缺失确实只走 `沿用`，但那是**有意设计**（`账本数据.ts:972-973` 注释写明：导演只看得到最近三层，缺一轮不该拦整轮）。`强度` 不 clamp 是真实的小缺陷，但不在本批。
4. **#16 破限段 (a)/(d) 自相矛盾** —— 破限段是**用户显式开启**的越狱文本，它的"矛盾"是刻意的（既要它辨别注入、又要它不受场外规则约束）。改它等于改产品意图。
5. **后台自己排除的 4 条**（回响刷掉 / 必演 3 轮 / 核验对象被改写 / 代价落点过窄）—— 我复核同意，**全部不成立**。
