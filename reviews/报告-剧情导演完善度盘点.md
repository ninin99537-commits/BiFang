# 剧情导演 · 完善度盘点报告

> 日期：2026-11-13
> 提问：用户「剧情导演这个插件完善了吗？拿剧本结构理论对着看，缺什么。」
> 硬约束（用户原话意译）：**这是 RP 不是影视，节奏因人而异** ——
> 用户 A 一层楼演十几分钟、剧情一天跑几十层；用户 B 几层楼就过一天。
> 任何节奏设计必须同时容纳这两种人。
>
> 四方参与：opencode（需求/仲裁）、dsh（实现视角）、zcode（验收/否决视角）、kimicode（复查视角）。
> 底稿：`tmp/盘点-议题清单.md`

## 结论先行（四句话）

1. **节拍与结构不是这个插件的短板。** BS2 15 拍里有 12 个零实现，但其中大部分**不该实现** ——
   它们是「2 小时电影」的时长产物，RP 用的是连载剧骨架（章→幕→场），这套骨架**已经在跑**。
2. **真正的缺口是「阈值对用户不可见」。** 7 个节奏问题里有 4 个是零 schema 成本、用户立刻能感知的
   （世界时间上面板、场数上面板、更新频率文案、`prompts.ts` 措辞），**性价比远高于补任何节拍**。
3. **但你上次修的那一半，只修好了一半** —— 见 §三·补。
   杂兵那一半修好了（对抗堆积门槛）；「紧凑」那一半**没修好**，而且现有用例给出了**假绿**
   （M1 删断言仍 66/0、M2 删整组仍 65/0、M3 补断言立刻 67/2）。
   这是本轮唯一「用户已撞上、有实跑证据」的活缺陷，优先级高于全部盘点项。
4. **值得动 schema 的只有两条**：全书级主题、催化剂（开局推力）。
   其余「缺」的项，要么已被同义字段覆盖，要么做了会更糟（见 §4）。

> **口径必须分层写（kimicode 纠正，已采纳）**：
> 不分层扫全仓 2849 个文件，12 个英文术语**全部有命中** —— 但命中文件全是
> `reviews/报告…`、`tmp/盘点-议题清单.md`、`tmp/scan-*.py|txt`、`tmp/send-pandian.py`
> 这些**盘点产物自己**（我自己的报告在引用这些词，当然命中）。
> 所以只有**限定 `src/`** 才有意义：`src/` 下 223 个文件 → 11 个术语 0 命中，
> `All Is Lost` 1 处（`README.md:1326` 自述没做）。
> **准确口径是「代码 0 命中 / 1 处 README 自述 / 2 处注释提及 / 1 个语义替身」**，
> 不是「全项目 0 命中」。

> ⚠️ **「代码 0 命中」不等于「功能缺失」。** 上面这张表只说明**没用 Blake Snyder 的术语**，
> 不说明**没有对应的机制**。最典型的三条（kimicode 补）：
> - `进入第二幕 / 进入第三幕` → 替身是**幕纲 3~5 幕 + 当前幕号**（`schema.ts:518-524`）；
> - `Fun and Games` → 替身是**生活幕**（`prompts.ts:150-154`）+ **日常节拍**（`schema.ts:275`）；
> - `All Is Lost` → 替身是**全线崩塌**（7 处）。
>
> 所以「按英文术语名数」和「按语义落地数」是两个口径，**必须分开写**：
> 前者 12 个里 11 个 0 命中；后者 15 拍里至少 3 个有真替身（中点 / B 故事 / 五步终局），
> 加 3 个语义替身（三幕切换 / 生活幕 / 全线崩塌）。
> 本报告后续凡说「缺」，都以**有没有能承载该戏剧功能的机制**为准，不以**有没有那个词**为准。

> 口径：`All Is Lost` 在 `README.md:1326` 出现过 1 次，内容是**承认没做**：
> 「All Is Lost 只有提醒、道德弱点（主角正在伤害谁）没有字段、符号网没做」。
> 准确说法是「代码 0 命中，README 有 1 处自述缺口」。

### 1.4 时间尺度 —— RP 的核心问题

**世界时间是唯一时间刻度**，但建模极薄：

- 字段只有 `世界时间: { 天数: number; 文本: string }` —— `schema.ts:908`
- 导演每轮声明「时间推进天数」（可小数），代码累加，只增 —— `账本数据.ts:980-994`
- 代码引用（`世界时间` 字面）：`schema.ts`(1)、`update.ts`(1)、`提醒.ts`(6)、`账本数据.ts`(6)、`账本迁移.ts`(6)
  —— **代码 5 个文件 / 20 处**；再加 `README.md` 4 次 = **6 个文件 / 24 次**。
  `悬浮球界面.vue` **0 处**

> **口径更正（两轮才定下来，记下来因为过程本身是个教训）**：
> 我最初写「5 个文件 / 20 处」—— **这个是对的**（只算代码）。
> 复查第一轮 kimicode 说「是 6 个文件」，我**没自己重数就采纳了**，改成「6 个文件 / 20 处」。
> 复查第二轮他自己更正：「逐项加起来只有 5 个文件 20 处，是我口误，别让报告沿用」。
> 我用 `tmp/count-worldtime.py` 重数确认：**代码 5/20，含 README 6/24**。
>
> **教训：协作者给的数也要自己跑一遍。** 「对方更正了我的数」不等于「对方的数是对的」。

**关键事实（dsh 补充，我已独立核实）：天数是模型自报的，代码只卡下限、不卡上限。**

```ts
// 账本数据.ts:980
const 推进天数 = Math.max(0, Number(载货?.时间推进天数) || 0);   // ← 只有下限
// 账本数据.ts:991-994
账本.世界时间 = { 天数: (Number(旧?.天数) || 0) + 推进天数, ... };
```

唯一的校验在 `提醒.ts:284-289`：只拦「时间文本里的第 N 天 < 累计天数」，即**只防往回写，不防往前跳**。
模型报「过了 10000 天」，代码照单全收。

> **这条决定了所有「按故事时间裁决」的方案都不能用** —— 它是在用一个不受约束的模型自报值当裁决输入。

**但有一处例外，必须分清（kimicode 补）**：`冲突.最后行动天`（`schema.ts:555` 注释 / `:556` 声明）、
`update.ts:477` 的写入、`提醒.ts:255-256` 的「已 N 天没动手」、`提醒.ts:280-288` 的文本倒退检查，
都是**故事天数刻度**。但它们**只用于文案和自洽检查，不参与节奏裁决** ——
`字段表.ts:379` 的逾期是 `当前幕 - 最后行动幕`，**用幕算**。

> 准确说法：**主阈值按场，对手节流与时间自洽另有天刻度。**
> （而那个天刻度的文案正是 §三·补 第三层要改的那句假话。）

**所有节奏阈值都是按「场」算的**（场 ≈ 一次引擎推进 ≈ 一条 AI 回复）：

## 二、八个 story-design 技法 · 逐项判定

> 判定口径：**已实现 / 部分 / 缺 / 不适用 RP**。
> 「不适用 RP」是本轮最重要的判定档 —— 影视技法不能因为书上写了就必须搬进 RP。

| 技法 | 判定 | 说明 |
|---|---|---|
| `beat-sheet`（15 拍） | **大部分不适用 RP** | 见 §2.1 的重构：RP 用的是连载剧骨架，不是 2 小时电影骨架。12 个零命中里，只有 2 个是真缺口 |
| `genres`（类型承诺） | **接线已实现 / 效果未验** | 十类型 + `build类型块` + 一句话副标题。但 `引擎规则.ts:86` 只是**按设置生成提示词文本**，**不检查必备元素齐/兑现**（kimicode 反向校准）。**不要加「缺一不可」硬校验** —— 会逼模型硬塞元素 |
| `logline` | **部分 / 不必补** | **要素散在四个字段 + 主角在账本外 + 无 irony**（kimicode 纠正）。`核心问题`+`欲望`+`冲突.对立面`+`弧线.缺口` 各占一块，从没拼成一句；主角靠 `persona.name()` 运行时补（`update.ts:345-352`），**不进账本**。~~已覆盖其四要素~~ 是过强的说法 |
| `save-the-cat`（主角认同） | **不适用 RP** | 见 §2.2 —— 这是影视理论搬进 RP 会**主动做错**的第一名 |
| `theme-b-story` | **部分 → 真缺口** | B 线已实现（`书纲.谁·争什么` 注释里已写「主题在这条线上被讨论」）；缺的是**全书级命题字段**与「早期埋一句无关话」的**时机机制**，不是「主题完全没被讨论」 |
| `shard-of-glass`（碎片） | **未实现（有相邻字段，非同义）** | 技法原义是「把主题砸进主角私人的伤 **+ All Is Lost 必须由主角自己的缺陷造成**」。`弧线.缺口` 是**成长轨迹起点**，不含「正在伤害谁」、不含主题命题、不含与崩塌的因果。`全线崩塌` 7 处全是提示词，**没有一条把崩塌原因连到 `弧线.缺口`**；唯一写「失败原因必须和主角自己的缺口有关」的是 `引擎规则.ts:539`，但那是**五步终局第 2 步、只走收官分支** |
| `midpoint` | **字段已实现 / 语义靠提示词** | 字段 + 到期提醒真有（`schema.ts:535`、`提醒.ts:407-428`）；A/B 交汇与赌注升级只在 `schema.ts:529-530` 注释与提示词里，README:1364 自承「代码只负责顶到导演面前」 |
| `five-step-finale` | **已实现** | 五步 + 每步节拍 + 每步要求；固定 5 步**是优点**（RP 需要可预期的收束）。补事实：`Math.min(5, …)` 夹住后**不会停**（`update.ts:416-419`），第 6 轮起仍是「第 5 步」，停摆只由用户点确认剧终 |

> **这张表有两个口径要分清（kimicode 指出，已采纳）**：
> - 「**接线已实现 / 效果未验**」= 有字段、有提示词、有代码把它塞进输入，但**没有语义判据**能验「模型真的照做了」；
> - 「**已实现**」= 有字段 **且**有代码判据。
>
> 我原来对「缺口」要求「有机制才算有」，对「已实现」却放宽到「有提示词就算有」——
> **这是双重标准**。已按统一口径重标：`genres` / `midpoint` / `类型承诺` / 角色不全知
> 全部降为「接线已实现 / 效果未验」。

### 2.1 重构：不是「缺 15 拍」，是「用了另一种骨架」

15 拍是 **Blake Snyder 为 110 分钟商业片**设计的时长产物。其中「游戏时间 / 坏人逼近」
在 RP 里**没有对应物** —— RP 没有片长，玩家可能在这个场景里待 300 层。
（`进入第二幕 / 进入第三幕` 不算缺：幕号推进已经是它的落地物，见 §5.1 #7。）

插件实际用的是**连载剧骨架**：

```
章（跨几十场）→ 幕纲 3~5 幕（事件/生活/收束）→ 场（一次引擎推进）→ 节拍（8 个戏剧功能）
```

这比 15 拍**更适合 RP**：15 拍假定「故事有确定的长度和终点」，连载剧骨架允许「一直演下去」。

**但连载剧骨架缺一样 15 拍有、它没有的东西：开局推力。**
15 拍里由 `Catalyst → Debate → Break into Two` 三拍承担「故事从哪一刻开始变」。
插件里对应的是「冷启动 3 轮 + 接管轮数 4」—— 那是**引擎什么时候开始下令**，不是**故事什么时候开始变**。

→ **真缺口 1：催化剂（开局推力）。** 第一章没有「打破平衡的那件事」的机制。

### 2.2 为什么 `save-the-cat` 搬进 RP 会主动做错

影视里观众是**第三人**，所以需要「救猫咪」让观众站主角这边。
RP 里**玩家就是主角** —— 玩家已经在自己这边了，代码替玩家表态等于**夺权**。

这是本轮最干净的一个「不适用 RP」案例：**书上写了、代码没做、而且不做是对的。**

> **但这条论证有一个前提，必须单列（kimicode 指出）**：
> 「玩家就是主角」在**视角**上成立（`update.ts:345-352` 当前视角缺省 `persona.name()`），
> 但**代码没有禁止导演替玩家写行动/决定/心理**，而且 `prompts.ts:143-145` 明确授权导演
> 安排主角失败/死亡/离开。**这是「不适用」论证的事实缺口**，不是技法缺口 —— 见 §5.3 末「RP 盲区 ③」。

### 2.3 本报告只量了 BS2，Truby 那套没量

**这是口径边界，不是遗漏**（kimicode 指出，已采纳）。

插件是**混血**，不是纯 BS2：
- `书纲.ts:45-50` 明写「取自 **Truby** 的 Desire」→ `欲望` 三件套；
- `schema.ts:603-609` 的**缺口驱动 6 阶段弧线**、`:616` 起的角色命运/镜头外推进/对手独立目标，
  是 **character web**，不是 BS2 的 15 拍；
- `schema.ts:960` 的五步终局，也不是 BS2 的 Final Image。

**用一本书的术语表去量一个混血实现，本身就会量出一堆假缺口。**
本报告的选择是：**只把 BS2 量到底，Truby 那套标注「未量」** ——
补全 Truby（7 步 / 22 步有机情节 / 角色网 / 道德论证）会让报告膨胀一倍，
而且其中至少 4 项（弱点与需要、欲望、对手、道德论证）在源码里**已有对应物**
（`弧线.缺口` / `书纲.欲望` / `冲突.对立面` / 五步终局第 3–4 步），
补了反而要重新处理一遍「算不算实现」的双口径问题 —— 那正是本轮被 kimicode 抓住的那个毛病。

> 口径边界（kimicode 的措辞，已采用）：
> **用户问的是「拿剧本结构理论对着看」，但本轮可核的标尺只有 BS2 这一本；
> Truby 部分未量，不能由「BS2 里没有」推出「理论上缺」。**

> 若后续要量 Truby，入口是 `书纲.ts:45-50` 与 `schema.ts:600-620`，
> 且已有可用的技能 `story-architect`（22 步有机情节 + 角色网 + 主题 B 故事）。

## 三、七个 RP 节奏问题 · 逐条裁决

### Q1. 一层楼 = 多久？

**不做字段。** 一个「本层时长」字段会多一次模型自报，收益只是文案更准，代价是又一个不可信输入。
写进提示词即可：「本场推进了多久由你定，写进时间推进天数，宁可小不要大」。

### Q2. 「场」对两种用户是不是同一个东西？

**不是，但场仍然是唯一可信的计量单位** —— 因为它由代码数，不靠模型报。

- 用户 A：40 场 ≈ 故事里半天 → 催收章会显得「才半天就收」
- 用户 B：40 场 ≈ 故事里 40 天 → 催收章会显得「一天收一章」

**裁决：按场为主 + 天数背离时提醒，不裁决。**

#### 但「场」这个分母本身不稳固（kimicode 指出，我原来判轻了）

这一条影响 Q2 / Q5 / Q7 三问的**共同前提**，必须写在前面：

| 事实 | 位置 |
|---|---|
| 更新频率是「**未处理回复数 % N**」，不是「每 N 条」 | `index.ts:105-131`（`:128` 是那个取模） |
| 一次推进**最多补读 8 条**，更早的**静默跳读**，只把「跳读条数」告知导演 | `取料.ts:84`、`:169-189` |
| 面板「重新推进」**绕过频率闸门**（直接 `updateDirector(true)`） | `update.ts:652-657` |

**后果**：一场可能覆盖 1~8 条回复，也可能跳过若干条。所以调「更新频率 N」
不只是「剧情推进变慢」，还会**改变一场读到的正文窗口**。
用户 A（一天几十层）的跳读概率远高于用户 B —— **这恰好撞上本报告开头那条「两种人」硬约束**。

> 所以它不是「纯设计选择」，是**分母不稳固**。我原来把它判成「中（设计选择）」，低了。
> 修正排序（kimicode 提，已采纳）：**③ 玩家行动归属 > ① 删楼回退 ≈ ② 场分母不稳固 > ④⑤⑦ > ⑥**。

> ⚠️ 但「背离提醒」必须加护栏：因为天数是**无上限自报**（§1.4），
> 一个幻觉出来的「过了 10000 天」会让背离提醒变成噪音。
> 护栏：只有当**本轮新增天数 ≤ 30** 时才做「场/天背离」比较；
> 超过 30 天时改为单独提示「本轮时间跳跃过大，确认是否符合剧情」。

### Q3. 幕长按楼层还是按故事时间？（我点名的自相矛盾）

`prompts.ts:149` 说「幕和章都不是时间」，但 `章长度阈值=40 场` 实际就是按楼层在量。

**是矛盾，但矛盾点不是「按场算」，是「用了一个用户看不见的单位做硬阈值，且没在任何地方声明」。**

- 改成按故事时间 → 用户 A 永远不收章、用户 B 被切成流水账，**两种人都更痛**（理由见 §1.4）
- 正确修法：① 把那句改成「幕和章是**结构单位**；代码用**场**（一次推进）做阈值，不是故事时间」；
  ② **面板上把场数显示出来**（现在连「本章已演 X 场」都看不到）

### Q4. 要不要「节奏档位」？

**先不做。** 理由：档位是又一个隐藏旋钮 —— 用户选了「慢」但看不见慢在哪里，等于把复杂度推给用户。

**顺序很重要**：先做 Q3②（场数可见）+ Q6（世界时间可见）+ Q7（更新频率文案），
让用户先能**看见**自己在什么节奏上；观察一轮再决定要不要「慢/标准/快」三选一。

### Q5. 硬阈值该不该按节奏档位缩放？

**只放开 2 个：章长度、节拍拖太久。**
这两个是「用户能感知到它在催」的；回响间隔 / 对手行动间隔 / 矛盾久悬是**内部节奏**，放开只会让人调坏。

### Q6. 世界时间该不该上面板？

**该，一行只读文本。**
成本极小，收益是用户第一次能看见「过了几天」。
不算破坏防剧透 —— 它是**已经发生的事实**，不是未来剧情。
**不要做成可编辑**（可编辑 = 多一条写入路径 + 和导演自报冲突）。
同仓库 `烟火_世界运转` 已有先例（`悬浮球界面.vue:581/1533`）。

### Q7. 「更新频率」和节奏是什么关系？

**它是隐藏的节奏总旋钮，但名字和文案完全没说。**
`更新频率 = 每 N 条回复推进一次引擎` —— N 调大，场就走得慢，**所有按场算的阈值跟着一起变慢**。
用户以为那是性能选项。

**裁决：文案必改，机制不动。**
改成「引擎推进间隔：调大 = 剧情推进变慢、更省 token」。零代码风险，**性价比最高的一条**。

## 三·补 用户实测反馈：「剧情太紧凑、杂兵一个接一个」

> 用户原话（第一版）：「用了导演插件之后，剧情太快了，喘不过气，而且杂兵一个接着一个出现……
> 后面我修了一下，不确定修好了没有，我还没实测，你们也顺便检测一下。」
>
> 用户原话（**纠正版**）：「噢，对了，不是剧情太快了喘不过气，我纠正一下，是**剧情太紧凑**。」
>
> **结论：杂兵那一半修好了；「紧凑」那一半没修好，而且用例是假绿。**
> 详细证据：`tmp/缺陷-喘息没修好.md`、`tmp/更正-账本无条件写.md`、`tmp/更正二-字段语义错配.md`

### 先分清两个病（用户改口不是措辞问题）

| | 太快（时间/尺度病） | **紧凑（密度病）** ← 用户实际说的 |
|---|---|---|
| 体感 | 一章还没演透就被推着收章 | 每一场都在推进正事，没有闲笔 |
| 病灶 | 阈值按**场**算，不按故事时间 | 每一场都被强制成「带代价的事件」 |
| 对应代码 | 章长度 40 场、收束预算 8 场 | 节拍强制改写、幕纲格式、账本假记录 |
| 修法 | 放开阈值、按故事时间缩放 | 给「什么都不发生」留出合法出口 |

**这个区分改变了 zcode 一条结论的优先级**：他判「场与天未解耦」是
「唯一对某类用户是错的真缺口，优先级应高于 15 拍补拍」——
但那个判断的前提是「太快」。它影响「多久收一章」，不影响「每一场有多挤」。
**降为普通真缺口**（Q3 文案矛盾仍可验收、仍进 F 批），成立性不变。

### 修好了的那一半（2026-11-12 那次，逐条核实存在）

| 改动 | 代码位置 |
|---|---|
| 新增「日常」节拍（唯一允许什么都不发生） | `schema.ts:275`、`引擎规则.ts:118-121` |
| 日常不计入连续高/低张力、张力增量 0 | `字段表.ts:579`、`:593`、`账本数据.ts:896-897` |
| 对手主动性收口：只在升级/僵持/决战催、杂兵不催、间隔 3→5 幕、一次只点名一个 | `字段表.ts:351-395` |
| 未收档对抗 ≥3 组 → 先收一组再开新的 | `提醒.ts:264-274` |
| 幕型（事件/生活/收束）+ 一章至少一幕生活幕 | `prompts.ts:150-163`（仅提示词） |
| 日常不许被契诃夫规则征用 | `引擎规则.ts:686` |

「杂兵一个接一个」这个体感，代码层面确实被收住了。

### 没修好的那一半：三层证据，一层比一层深

这一节我改了三次结论，每次都更接近根因。**三次都记下来，因为最后那次才是真的。**

#### 第一层：导演要「日常」，被 rule1 高 / rule1 低 / rule4 强制改掉

走 `构造本幕指令()`，导演明确要「日常」：

```
连续高张力 3 幕(受挫/反转/高潮) → 导演要日常  ⇒ 实际节拍 = 余波
连续低张力 3 幕 → 导演要日常                ⇒ 实际节拍 = 阴影
上一幕是高潮 → 导演要日常                    ⇒ 实际节拍 = 余波
```

**三种全被改写。** 代码里「把节拍强制改成某个字面量」共 **5 处**（另有 1 处经变量赋值）：

```
引擎规则.ts:639  '余波'      ← 连续高张力（rule 1）
引擎规则.ts:650  '阴影'      ← 连续低张力（rule 1）
引擎规则.ts:666  '余波'      ← 高潮后必有代价（rule 4）
引擎规则.ts:715  '兑现伏笔'   ← 契诃夫
引擎规则.ts:775  '高潮'      ← 收束预算用尽（:751 的 `换成` 变量也落到这条路上）
```

**五处目标里没有「日常」。**

`:686` 只给**契诃夫**加了 `节拍 !== '日常'` 豁免；**rule 1（`:635`）和 rule 4（`:660`）都没加**。

> **更正（我自己扫描时发现的）**：我原来写「共 4 处」，漏了收束出口。
> 完整的是 `:639/:650/:666/:715/:775` 五处字面量，加 `:751` 的变量赋值 `节拍 = 换成`
> （`换成 = 候选们.length > 0 ? '兑现伏笔' : '高潮'`）。实跑见 `tmp/probe-第五条规则.ts`。
**但收束出口那两处不是缺陷**（`tmp/probe-第五条规则.ts` 实跑确认）：

```
进度=推进（不进收束分支）    → 日常保住
进度=收束 + 无候选           → 日常 被改成 高潮
进度=收束 + 有候选           → 日常 被改成 兑现伏笔
进度=收束 + 预算用尽         → 日常 被改成 高潮
```

理由：收束期**本来就不该演日常** —— 代码注释写得也对：
「节拍不能是「日常」（既不推进也不现在还债）」。这是**有意的设计**，不是 bug。
而且它明确写了「**不吃 `导演有明确意图` 豁免**」（`:744`），因为真机上 30/30 硬性要求非空，
那个豁免恒真、会让收束出口失效。

> **所以真缺口精确到 3 处**：`:639`、`:650`、`:666`。
> 这三处**都吃「导演有明确意图」豁免，但只在 `结构规则优先` 关掉时才生效**（默认开着）。

**为什么这等于没修好**：`日常` 是唯一允许「什么都不发生」的节拍；
而 `余波` =「平静但**带着代价**」、`阴影` =「**静中必须埋险**」—— 两者都是事件。
于是**越需要喘气，越被规则推着来一件事**。现在有这个档，但它在最需要的时候永远轮不到。

#### 第二层（更正一）：账本污染与节拍**无关**，写入层压根不看节拍

我一开始把「账本被写脏」归因给「节拍被改写」。**这是错的。**

`tmp/probe-账本无条件写.ts` 构造一个**节拍不会被改写**的账本
（无连续高张力、上一幕不是高潮），同一个账本只改导演要的节拍：

```
导演要「日常」→ 实际节拍 = 日常 → 对手行动更新 = {"追兵":10}  <<< 账本被写了
导演要「余波」→ 实际节拍 = 余波 → 对手行动更新 = {"追兵":10}  <<< 账本被写了
导演要「受挫」→ 实际节拍 = 受挫 → 对手行动更新 = {"追兵":10}  <<< 账本被写了
```

**节拍是「日常」的时候，账本照样被写。**

`引擎规则.ts:916-917`：

```ts
const 该出手 = 取该出手的对手(账本, 当前幕);
const 对手行动更新 = 该出手 ? { [该出手.名]: 当前幕 } : {};
```

而 `字段表.ts:376-387` 的 `该催对手行动` 四条判据（阶段/会出手阶段/逾期≥5/非杂兵）
**没有一条读节拍，也没有一条读幕纲**。

所以真正的机制是：**建议层有条件，记账层无条件 —— 两层不一致。**

| 层 | 行为 |
|---|---|
| 提醒层 `提醒.ts:259` | 「**若**这一幕的节拍不是「日常」，让对手先动手」← 条件句 |
| 写入层 `引擎规则.ts:917` | `对手行动更新 = {追兵: 10}` ← **无条件** |

#### 第三层（更正二）：不是"条件写错"，是**字段名说的和代码写的不是同一件事**

同一个代码形状（构造指令时就把「我提过」写进账本），全库**两处，只有一个在撒谎**：

| 写入点 | 写进哪个字段 | 字段注释说的是什么 | 诚实吗 |
|---|---|---|---|
| `update.ts:427` | `最近催办章` | 「代码上一次把这条线**写进指令催办**的章号」（`schema.ts:360`，粗体是我加的强调） | ✅ 名字就是「我催了」 |
| `update.ts:476` | `最后行动幕` | 「上一次**对手主动出手**的幕序号」（`schema.ts:549`，粗体原文自带） | ❌ 名字是「它做了」 |
| `update.ts:477` | `最后行动天` | 「同上，但记**故事内累计天数** —— 『对手多久没动手』用天说话才有人味」（`schema.ts:555` 原文整句） | ❌ 名字是「它做了」 |

**问题不在「提前写」，在「字段语义被偷换」。**

两个用户可见后果：

**① 会说假话。** `tmp/probe-字段语义错配.ts`，世界时间 30 天：

```
「追兵」(已 25 天没动手)。    ← 对手一次都没动过，只是 5 天前被催过一次
```

催得越勤，「看起来多久没动」越短，**账本越不真实**。

**② 假记录会压制真提醒。** `字段表.ts:379` `逾期 = 当前幕 - 最后行动幕`：
催一次 → 逾期归零 → **接下来 5 幕都不再催**。而提醒是条件句，导演完全可以不照做 ——
于是这 5 幕里对手真的静止，账本却以为「刚动过」。
**这不是脏数据，是错误的沉默。**

> 扫描确认：这个形状全库**只有 `最后行动幕/天` 一组**。
> `距上次高潮楼层` 不算 —— 它由 `账本数据.ts:901` 从**实际演过的节拍史**算出，是真实事实。

### 补充证据：「情境 × 规则」矩阵（`tmp/probe-日常被征用.ts`）

上一版这个探针**有一个情境标题标错了**（zcode 指出）：我标成「对照组：普通情况」的那格，
节拍史末位是 `高潮`，实际触发的是 **rule4**，不是「什么都没触发」。
重排后是五个情境，每格只让**一条**规则可能触发：

| 情境 | 构造 | 预期触发 | 实际节拍 | 结果 |
|---|---|---|---|---|
| 0 | 无连续高/低、末位非高潮、无候选 | **无（真对照组）** | `日常` | ✅ 保住 |
| 1 | 尾部连续高 = 3（受挫/反转/兑现伏笔），末位**不是**高潮 | rule1 高 | `余波` | ❌ 被改 |
| 2 | 连续低张力 = 3，末位**不是**高潮 | rule1 低 | `阴影` | ❌ 被改 |
| 3 | 末位 = 高潮，但连续高只有 1 | rule4 | `余波` | ❌ 被改 |
| 4 | 有到期伏笔、节拍史干净 | 契诃夫（`:686` 有豁免） | `日常` | ✅ 保住 |

**这张表比原来的三段输出强，因为它有一个真正的对照组（情境 0）**：

- 情境 0 证明「日常被改」**不是无条件发生的** —— 排除「所有情况都改」这种误判；
- 情境 1/2/3 各自**只触发一条规则**，所以能分别归因（这是原探针做不到的：
  原探针里连续高张力的那格同时触发 rule1 和 rule4，无法区分是谁改的）；
- 情境 4 证明**「加豁免」在技术上可行** —— 契诃夫已经这么做了，rule1 高 / rule1 低 / rule4 没做而已。

→ 所以真缺口是「rule1 高 / rule1 低 / rule4 缺日常豁免」，**不是机制做不到**。

### 裁决

**分两步，不能一次做完。**

**第一步（本轮，成本小）**：
1. `要留白` 一个纯函数 + **五处**调用点（rule1 高 `:639` / rule1 低 `:650` / rule4 `:666` / 提醒 `:259` / 写入 `:917`）；
   - 口径：幕纲没标类型 = **不启用留白**（照旧），保证老账本行为一个字节都不变。
   - **必须是五处不是四处** —— 我最初写成「四处（rule1 / rule4 / 提醒 / 写入）」，
     把 rule1 的高、低两条腿算成了一处。它们改写的**结果不同**（`:639`→余波、`:650`→阴影），
     少接一处，那一条腿就漏了。
2. 把那句假话改掉：「已 N 天没动手」→「已 N 天**没催它出手**」。
   - 理由（dsh）：**注释骗开发者，文案骗用户，后者更贵**。
   - 这不是妥协 —— 改完之后账本说什么、界面就说什么，至少不再有两种口径。
3. **但改文案有两个边界必须一起处理**（dsh 提，已采纳；否则新文案会在两个具体场景里说假话）：

   **边界 A：从没催过 → 不能说「已 N 天没催」。**
   `最后行动天` 是 0 或缺失时（老账本 / 新建对手），`隔天 = 天数 - 0 = 天数`，
   会输出「已 30 天没催它出手」—— **而它一次都没被催过**。
   这是**假话的另一种形态**（不是「它做了」，是「它被催过」），只是比原来轻。
   处理：`最后行动天` 为 0/缺失 → 文案改成「**还没催过它出手**」，不带天数。

   > 这条必须有专门用例：它**只在新账本或老账本上出现**，测试里不特意构造就永远看不到。
   > 现成的反证在 `tmp/probe-字段语义错配.ts` 第二个情境（「从未被催过」→ 输出「已 30 天没动手」）。

   **边界 B：天数本身是模型自报 → 只能描述，不能裁决。**
   `世界时间.天数` 由导演每轮自己写，所以：
   - ✅ 可以说「已 N 天没催它出手」（相对账本，准确）
   - ❌ 不能说「它 N 天没动」（把自报天数当事实）
   - ❌ 更不能说「所以它该出手了」（拿不可信输入做裁决）

   现行代码在这一点上是安全的：`逾期` 用**幕**算（`当前幕 - 最后行动幕`），不受天数影响。
   **改文案不会污染裁决。**
4. 顺带（零成本）：在 `字段表` 规范化处给 `最后行动天` 加一句注释
   「模型自报天数之差，**只用于文案，不用于逾期裁决**」。
   理由（dsh）：今天的问题不是「没人知道」，是「知道的人写在了别处」——
   **把约束写在字段旁边，比写在文档里活得久。**

**第二步（另立，成本中）**：
把写入从「发建议时」挪到「核验到已执行时」。
- 但先花 10 分钟看 `核验.已执行` 能不能承载「哪个对手出手了」——
  能，就是中成本正解；不能，才考虑新增自报字段（且必须名字带「自报」、永不用于硬裁决）。
- 字段改名（`最后行动幕` → `最近催办幕`）**不用迁数据**（语义/值域不变），
  但**必须配一条往返用例**：老账本（只有旧名）→ 读回 → 新名字段有值 → 再存 → 快照里是新名。
  快照往返今天已经翻车两次，**没有这条用例的改名等于没改**。

**优先级**：这条**不进 P0**（P0 全是可观测性，不动 schema），**进 P1 高位**。
理由（zcode）：P0 级都是**静默丢 / 静默清**；这条是**行为被改写**（导演明确要喘息却被覆盖，用户直接感知「紧凑」）。

### 验收判据（十二条，十二条变异，缺一不算）

```
① rule1 高：生活幕 + 导演日常 + 连续高张力   → 节拍仍是「日常」（:639 不生效）
② rule1 低：生活幕 + 导演日常 + 连续低张力   → 节拍仍是「日常」（:650 不生效）
③ rule4   ：生活幕 + 导演日常 + 上一幕高潮   → 节拍仍是「日常」（:666 不生效）
④a 要留白（左腿）：幕纲生活 + 导演要【非日常】→ 要留白 === true
④b 要留白（右腿）：幕纲事件 + 导演要【日常】  → 要留白 === true
⑤ 写入层  ：生活幕 + 导演日常 + 节拍保持日常 → 对手行动更新 === {}
⑥ 提醒层  ：幕纲生活 + 节拍=余波（已改写）   → 「让对手先动手」不出现
⑦ （A 的换出口）连续 N 场留白 → 出现「该给顶点」，且不含「余波/代价」
⑧ 反向    ：幕纲=事件 + 逾期恰好 = 5 → 对手行动更新 === { 追兵: 当前幕 }
⑨ 文案边界：幕纲=事件 + 最后行动天=0 → 文案是「还没催过它出手」，**不含天数**
⑩ 联合    ：幕纲生活 + 最后行动天=0 + 导演要日常
   → 节拍=日常 ∧ 对手行动更新={} ∧ 「让对手先动手」不出现
⑪ 设置贯通：阈值.高 = 6 + 连续 3 场高张力 → 「停在高点」提醒**不出现**
⑫ [R] 收束守卫（独立组）：进度=收束 + 导演要日常 → 节拍 ∈ { 高潮, 兑现伏笔 }
```

> 另配一组**属性式穷举**（允许集合 + 白名单），负责「新增强制路径自动被发现」——
> 它不替代上面 12 条，是**第三层**（见本节末）。

> **① ② ③ 必须分开，不能合并成「rule1/rule4」**（我自己扫描时发现的）：
> 三处强制赋值是 `:639`（→余波）、`:650`（→**阴影**）、`:666`（→余波），
> **结果不一样**。合并成一条断言 `=== '日常'` 虽然能同时抓三条，
> 但**变异时无法区分是哪条规则漏了**（删 `:650` 的豁免，合并后的断言照样红，
> 可你分不清是它还是 `:639`）。分开才能各自一条变异、各自归因。

> **④a / ④b 为什么必须拆开（dsh 提，已采纳 —— 这是原来判据集最大的覆盖洞）**：
> `要留白 = 幕纲标生活 || 导演本幕要日常`，这是一个 **OR**。
> 我原来的 ④ 入参是「幕纲生活 **且** 导演要日常」—— **两条腿同时为真**。
> 于是最常见的实现错「**只实现了一条腿**」照样能绿：
> ```ts
> 要留白 = 幕纲是生活            // 漏了「导演要日常」→ ④ 绿
> 要留白 = 导演要的节拍 === '日常' // 漏了幕纲       → ④ 绿
> ```
> 因为它的场景里哪条腿为真都够。**只有单腿输入能区分「实现了两条腿」和「实现了一条腿」。**
>
> 变异：把 `要留白` 的 OR 改成只判左边 → ④a 绿、④b 红；改成只判右边 → ④b 绿、④a 红。
>
> 房间纪律（已记）：
> **OR / 并联条件，测试必须每个分支各来一次「只有它为真」。全真组合只能证明「至少一条腿通」。**

### 收束出口的反向断言：单开一组 `[R]`，不进 `[4]`

收束期把「日常」改掉是**有意设计**（`:748-754`，且 `:744` 明写不吃豁免），
所以它不该写「不许改」的断言 —— 反过来，要写**「必须改」**的断言，防止以后有人「好心」给它加豁免。

```
[R] 收束出口语义守卫（独立组，不与 [4] 混）
  入参：进度=收束 + 导演要日常
  断言：节拍 ∈ { 高潮, 兑现伏笔 }
  变异 M1：给 :749 的 躲债节拍 去掉 '日常'（主路径）  → 必须红
  变异 M2：给 :775 加 `!== '日常'` 豁免（兜底路径）  → 必须红
```

> **为什么要两条变异（我核完源码后定的，已向 zcode 确认）**：
> 收束期把日常改掉有**两条路**，`:775` 只是兜底：
> - `:749` `躲债节拍 = ['日常','小胜']` → `:751` 换成 `兑现伏笔` 或 `高潮` —— **主路径**，日常在这里就被换掉了；
> - `:775` `if (节拍 !== '兑现伏笔' && 节拍 !== '高潮') 节拍 = '高潮'` —— **兜底**，只管收束预算用尽那一刻。
>
> 只测 `:775` 的话，「给 `:749` 加豁免」这种回退**会漏**。两条各一次变异，才算钉住这个语义。

> **为什么必须单开一组（zcode 判，已采纳）**：
> `[4]` 组的语义是「**导演意图优先于机械规则**」；收束出口的语义**正好相反**（机械裁定优先、明写不吃豁免）。
> 塞进同一组会让**组标题说谎** —— 将来读用例的人会以为收束也该吃豁免。

### 属性式穷举：让「新增强制路径」自动被发现（dsh 提，已采纳）

我原来担心「穷举用例不知道有新场景」。dsh 给了第四个方案，比我提的三个都好：

**不要枚举「代码里有几处强制赋值」，而是枚举「输入空间」，断言一条不变量。**

```ts
// 不变量：白名单外，节拍必须 === '日常'；白名单内，节拍必须落在「允许集合」里
// 注意：白名单不是布尔，是**允许的取值集合** —— 「允许被改」不等于「随便改成什么都行」
const 允许集合 = (组合: 组合): 节拍[] =>
  (组合.进度 === '收束'
    ? ['高潮', '兑现伏笔']   // 收束期：日常/小胜不许演，但也不是「随便改」
    : ['日常']);             // 其余：只有日常一个合法答案

for (const 组合 of 全部组合(
  张力: ['无', '连续高', '连续低', '高潮后'],
  幕纲: ['事件', '生活', '未标'],
  进度: ['推进', '收束'],
)) {
  const 结果 = 构造本幕指令(组合, /*导演要*/ '日常');
  const 允许 = 允许集合(组合);
  check(`组合 ${组合} → 节拍属于 {${允许.join(',')}}`, 允许.includes(结果.节拍), true);
}
```

> **形态要改成「允许集合」而不是布尔（dsh 提，已采纳）**：
> 如果白名单那一项只写「允许被改」，它就又是**无人看守区** —— 改坏了也不知道。
> 写成集合之后，收束期必须 ∈ `{高潮, 兑现伏笔}`，**不是随便改**。
>
> 这一个改动同时解决 `[R]` 的覆盖问题：`:749`（主路径）或 `:775`（兜底）不管哪条被加豁免改回日常，
> 属性穷举都会红 —— 因为「日常」不在收束期的允许集合里。**它不依赖「我记得有几处」。**
>
> 但 **两条显式变异仍然要写**（`:749`、`:775` 各一条），让人一眼看出是哪一处漏了。
> 属性穷举负责「抓得到」，显式变异负责「定位」。

> **白名单里为什么没有「契诃夫已到期」（dsh 与 zcode 都判不放，理由比我的更本质）**：
> - dsh：**白名单里的场景 = 没有守卫的场景**。`应保住 = false` 意思是「允许被改成任意值」。
>   把契诃夫放进去，等于**主动放弃**「它的豁免还在不在」这条检测 ——
>   有人删掉 `:686` 的 `!== '日常'`，它会被改成兑现伏笔，而白名单说「允许被改」，**照样绿**。
> - zcode：白名单登记的是**实现行为**，不是**设计例外**。
>   契诃夫的情况不是「允许改写」而是「**根本不会改写**」（`:686` 有豁免，导演要日常时直接跳过）。
>   放进白名单会断言一个**永远不会发生的场景**，那条断言对错都无法验证 ——
>   和计数元断言同病（测不到目标代码）。
>
> 准入标准（zcode 给，已采纳）：**只有「当前实现真的会改写」的组合才进白名单。**
> 收束出口是真的会改（无豁免），契诃夫是真的不会改（有豁免）。
> 所以白名单只有「进度=收束」一项；24 组里「契诃夫×导演日常」那组断言「**必须保住**」——
> 这顺便也把 `:686` 的豁免本身钉住了（豁免被删，那条变异会红）。

它比「逐场景穷举」强的地方：
- **输入是组合，不是「我记得的那几个场景」** —— 以后有人加一条新强制路径，
  只要它落在白名单外的某个组合里，**这条自动变红**（那个组合本来测过、现在变了）；
- 白名单是**唯一的「人记得」**，但它收窄、可审计、每项都要写理由 ——
  想加白名单必须在 diff 里写清「为什么这一版故意不改写日常」；
- 组合数不大（4×3×2 = 24），跑得起。

> **dsh 的一句总结，值得单列（因为它解释了我们今天抓到的一半东西）**：
> > 你今天连着抓到的东西，有一半是「**无人看守区**」：
> > 白名单里的一格、兜底分支、只在老账本出现的边界、只在新账本出现的字段=0。
> > 它们的共同点是**测试不主动构造就永远看不到，而且看不到的时候一切正常**。
> > 这类地方最好的守卫不是「记得去测」，而是**用输入空间穷举把它们逼出来**。
>
> 对照本轮实证：`⑦` 的文案边界（只在 `最后行动天=0` 时出现）、`[R]` 的兜底（`:775` 平时不跑）、
> 假绿的三条变异（M1/M2 删了断言仍然全绿）—— **全是同一类**。

**所以最终方案是三层**：
1. **逐赋值点用例**（①②③ 正向 + `[R]` 反向），负责「每处都对」；
2. **属性式穷举**（允许集合 + 白名单），负责「新路径自动被发现」；
3. **不写计数元断言**（见下）。

### 为什么「计数元断言」被否掉（dsh 自己撤批，我判成立）

dsh 原来建议：`断言条数 === 源码里 '节拍 = \'' 的出现次数`。
我实跑：**出现 5 次，但该配的断言只有 3 条**（契诃夫已有豁免、收束是有意为之）。

dsh 自己撤批的原话：
> 我提这条时脑子里想的是「4 处强制点、其中 1 处有豁免」，**那个模型本身就是错的**：
> 强制点里混着**有意为之**的（收束出口、契诃夫），它们**不该**有「不许改成 X」的断言。
> 所以「数出来的数」和「该写的断言数」**本来就不是同一个数**。
> **能数 ≠ 该数** —— 只有当「数出来的」和「该有的」一一对应时，计数才成立。

zcode 补的后果更重：
> 这类元断言必然「一开始就红且红得没道理」，然后有人为了绿它去数数凑断言 ——
> 比假绿更糟，它制造的是**看起来有守卫的假安心**。

**我的三个替代方案也被 dsh 否了两个**：
- 方案 1（行号锚定）= 手工列表，行号一改就废，正是「靠人记得」；
- 方案 2（每处必须有豁免或注释）= **验的是注释存在**，我们在 P1-8 上刚被「注释骗过正则」坑过；
- 方案 3（穷举用例）= 对，但不完整 —— 由方案 4 补上。

> `引擎规则.ts` 顶部那句提醒式注释可以留，但它**只是顺便，不承担验证职责**。

变异：① 删 `:639` 的 `!== '日常'` 豁免 / ② 删 `:650` 的 / ③ 删 `:666` 的 /
④a+④b 把 `要留白` 的 OR 改成单腿 / ⑤ 删 `要留白` 里的幕型判断 / ⑥ 改回「节拍不是日常」 /
⑦ 文案改成「请给余波」 / ⑧ 删 `:917` 的写入 /
⑨ **两个方向**：删 `隔天 > 0` 的兜底 **＋** 兜底文案改成含天数 /
⑩ 只删提醒层的 `要留白` 调用（引擎层不动）/
⑪ 把 `提醒.ts:798` 改回 `连续高阈值默认` → 必须红 /
⑫ 给 `:749` 的 `躲债节拍` 去掉 `'日常'` → 必须红 **＋** 给 `:775` 加 `!== '日常'` 豁免 → 必须红（`[R]` 组，**两条变异，主路径 + 兜底各一**）。

**⑧ 的两个细节（dsh 提，已采纳）**：
- **逾期取恰好 5，不取 6** —— 取 6 的话把 `>=` 写成 `>` 照样通过。
- **断言具体值 `{追兵: 当前幕}`，不是「非空」** —— 只断言非空的话，「写错成上一幕」也能绿。

**⑨ 为什么必须单列、且必须两个变异方向（zcode 提，已采纳）**：
它只在「老账本 / 新建对手」时出现，是**改了文案之后才暴露的新假话**。
- 只删兜底：钉住的是**实现细节**（那个三元写没写）；
- 兜底改成含天数：钉住的才是**语义边界**（0 天时到底能不能出现数字）。
两个都红，才算真的钉住了语义而不是写法。

> ⑨ 定性：**「改文案的前置条件」，不是独立缺陷**（zcode 判，已采纳）。
> 不改文案它不存在；改了文案它立即变成**比原来更假**的假话。必须与文案改动同批验收。

**⑩ 为什么必须有、且为什么不能带文案断言（dsh 提 + 我自己实跑修正）**：
①–⑨ **互不相交** —— 前一半只看账本空不空，后一半只看 0 的兜底，**两边都不看对方**。
于是「留白生效 + 文案仍按 0 算天数」这个组合**可以全绿**。

**但我第一版把 ⑩ 写成「… ∧ 文案是「还没催过它出手」」，这是错的**，实跑反证：
修好之后「幕纲生活 → 要留白 = true → 提醒层不出这条提醒」→ **根本没有文案**，
第三个分句**不可满足**（`tmp/probe-8自相矛盾.ts`；文件名里的「8」是改版前的编号，别被它带偏）：

```
A) 幕纲=事件 + 最后行动天=0  → 提醒响，说「已 30 天没动手」   ← ⑨ 的战场
B) 幕纲=生活 + 最后行动天=0  → 现在也响（因为没修）；修好后不响 → 没有文案
```

所以 ⑩ **只能断言「节拍=日常 ∧ 账本={} ∧ 提醒不出现」**，文案交给 ⑨。
⑩ 的变异也因此要改成「只删提醒层的 `要留白` 调用」——
这样 ⑨（事件幕场景）不受影响，只有 ⑩ 会红。

> ⑩ 的真实价值（dsh 纠正我原来的理由）：**不是「压入最后行动天=0」，是「跨层同源」**。
> 它是唯一一条同时要求**引擎层和提醒层**都改的判据 —— 只看账本它绿，看账本+节拍+提醒它才红。
> 我原来举的反例（`要留白 = 幕纲生活 && 最后行动天 > 0`）其实没人会那么写，
> 用它当卖点是错的；改成「跨层同源」才站得住。

### 派活切法与顺序（dsh 提，已采纳）

- **分两条派**（P1 高位 / P1 常规位）：判据集不同、变异不同、可独立验收。
- **同一提交里做完**：两者共用 `要留白`，分开提交会出现「引擎改了但提醒没改」的中间态 ——
  **那正是今天这个 bug 的形状**。
- **提交内有明确先后**：先 `要留白` + **五处**调用点，再文案 + 边界 A。
  理由：⑥（留白后账本为空）依赖前者，反过来不成立。写实现时顺序错了会绕一圈。

> 房间纪律（zcode 提，已采纳）：
> **凡行为产生账本副作用，判据优先断言副作用（对比断言差集），文案 grep 只用于无副作用层。**
>
> 房间纪律（dsh 提，已采纳）：
> **能数 ≠ 该数** —— 只有当「数出来的」和「该有的」一一对应时，计数才成立。
> 这是今天唯一一条**否定式**纪律：其他纪律说「该怎么做」，这条说「有些看起来该做的，不该做」。

### 字段语义错配：不进 P0，进 P1

zcode 判定（已采纳）：

> 它不是**数据丢失**（P0 级都是静默丢/静默清），是**数据说谎** ——
> 说谎的数据仍在、可见、甚至可被面板显示，但会污染下游判断（逾期归零 → 错误沉默）。
> 这恰是 P1 的定义域。

判据形态（他纠正了我的倾向）：**断言账本字段本身，不断言渲染出的天数**。

理由：渲染天数是账本字段的**确定性函数**（天数差 = 字段差），断言字段即断言渲染；
反过来只断言渲染，会漏掉「字段没变但模板插值错了」这一类。

所以两层分开、各一条变异：
- **主判据（写入层）**：行为差分 —— 被催过 vs 未催过，`最后行动天` 必须不动；
- **辅助（呈现层）**：渲染差分 —— 同一字段值，文案天数必须一致。

> 这不违反「文案 grep 只用于无副作用层」那条纪律：
> 这里验证的是**渲染函数的正确性**（输入→输出映射），不是拿文案猜行为。

这正好违反 README 自己立的一条纪律：「两处共用 `高张力节拍` 与 `连续高阈值默认`

> 判据形态：`阈值.高 = 6` + 连续 3 场高张力 → 「停在高点」提醒**不出现**。
> 变异：把 `提醒.ts:798` 改回 `连续高阈值默认` → 必须红。

#### ⚠️ 更正（2026-11-13 批 C 派活前实测）：`连续低阈值` 是同一个病，本报告漏了

上面只点了高阈值。低阈值**完全对称**，而且更隐蔽：

| 位置 | 行为 |
|---|---|
| `引擎规则.ts:467` | `低阈 = 阈值?.低 ?? 连续低阈值默认` —— 接 settings |
| `update.ts:385` | 传 `settings.导演.连续低阈值` |
| `提醒.ts:812` | `if (连低 >= 3)` —— **写字面量 3**，连常量都没用 |

实跑（`tmp/probe-连续低阈值-对照.ts`，连续低张力 = 4，幕纲「冲突」以免撞上留白豁免）：

```
用户设置 连续低阈值 = 3：  引擎调整 1 行（改成阴影）   提醒「低张力」1 条   ← 一致
用户设置 连续低阈值 = 6：  引擎调整 0 行（尊重设置）   提醒「低张力」1 条   ← 只有引擎生效
```

**为什么盘点时没抓到**：`:812` 的字面量 `3` 恰好等于 `连续低阈值默认`（`schema.ts:58`）。
默认值把缺口盖住了 —— 用例都用默认值，所以「用默认值时行为正确」恒真。
只有改过设置的用户才看得到，和「无人看守区」是同一族。

**修正结论**：P1-3 不是一处，是**两处**。批 C 必须两个阈值一起接，判据 ⑪ 拆成 ⑪a/⑪b。

#### 方法论：「字面量恰好等于默认值」是阈值类缺口的通用形态

这次漏检的机制值得单独记下来，因为它**不依赖任何人的粗心**：

```
提醒.ts:812   if (连低 >= 3)              ← 字面量
schema.ts:58  export const 连续低阈值默认 = 3
```

两者数值相同，于是：

1. 所有用例都用默认值 → 「默认值下行为正确」**恒真**
2. 用户不改设置 → 永远看不到差异
3. 改了设置 → 只有提醒侧不跟随，而**没有任何用例覆盖「非默认值」**

**判据全绿、代码确实有缺口，两者同时成立。** 这不是测试写得不好，是测试的**输入域**天然只覆盖默认值。

→ **下次盘点凡遇阈值类缺口，先查「字面量是否恰好等于默认值」。**
相等就是高危信号：它让缺口在全部现有用例里隐身。
反过来说，`引擎规则.ts:467` 那句 `阈值?.低 ?? 连续低阈值默认` 之所以能被发现，
恰恰因为它**写的是常量而不是字面量** —— 常量名让人一眼看出「这里本该跟着设置走」。

> 同族：`提醒.ts:808` 的 `连续高阈值默认` 至少是常量（可被 grep 到「哪里用了默认值」），
> 而 `:812` 的裸 `3` 连这条线索都没有。**字面量比常量更隐蔽，因为常量自带出处。**

## 五、验收视角与复查视角

### 5.1 验收视角（zcode）：三档分类

判据能不能写出来，分三档：
**✅ 可验收**（能写出测得到目标代码的断言 + 能构造变异让它变红）
**⚠️ 只能验「接线」不能验「效果」**（代码能验机制存在，验不了创作意图达成）
**❌ 不可验收**（写不出判据 / 只能靠提示词自觉 / 测不到目标代码）

| # | 技法缺口 | 档 | 理由 |
|---|---|---|---|
| 1 | 开场画面（Opening Image） | ⚠️ | 字段+接线可测；「这句真的当开场画面用了」验不了 |
| 2 | 主题陈述（Theme Stated） | ⚠️ | 同上；建议并进 #3 |
| 3 | 全书级主题 | ❌（正确性）/ ⚠️（存在性） | 「主题正确」不可验收 —— 任何字段校验都测不到「它真是这个故事的主题」。存在性可验，但那只是「有个格子填了」，**容易造成为了过验收而瞎填的字段，比没有更糟** |
| 4 | 催化剂 | ⚠️ | 部分已有（`书纲.欲望` 的「为什么是现在」≈ 激励事件）。字段非空可测，效果不可测 |
| 5 | 游戏时间 / 坏人逼近 | ❌ | 这两拍是**过程性段落**不是事件。节拍枚举+张力曲线已经在做语义替身 |
| 6 | 一切尽失 / 灵魂黑夜 | ⚠️ | `全线崩塌` 提醒已存在；缺的是「崩塌与主角缺口的相关性」，那是语义判断。**建议不新增机制，提示词补一句** |
| 7 | 进入第二幕 / 第三幕 | ✅ | **看着缺其实不该有** —— 幕号推进就是它的落地物，已实现，只是没用 BS2 的名字 |
| 8 | 终场画面（Final Image） | ❌ | 五步终局第 5 步已覆盖语义；RP 没有固定最后一帧，**故事可以随时停**，硬加字段会逼导演编假结尾 |
| 9 | 主角认同（Save the Cat） | ❌（代码）/ ⚠️（提示词） | 认同是**读者感受**，代码零可测。唯一可测的是「提示词里含建议句」——那是验提示词不是验效果 |
| 10 | 碎片 / 道德弱点（shard of glass） | ⚠️ | `弧线.缺口` 是**相邻概念不是同义**（`schema.ts:606` 是成长轨迹起点，不含「正在伤害谁」、不含主题命题、不含与崩塌的因果）。`全线崩塌` 7 处全是提示词，**没有一条把崩塌原因连到缺口**。**建议不新增字段，提示词连一句**（见 P2-1/P2-2） |

> 他的小结口径：**8 个技法缺口里，✅ 1、⚠️ 6、❌ 3**（✅+⚠️+❌ 有交叉，因为 #3/#9 是双档）。
> 其中 ✅ 那条（#7 三幕切换）是「看着缺其实已实现」——
> **这条纠正了我 §2 的判法**：我原来把它列成缺口。

**zcode 的关键提醒（已采纳进 §2）**：
> 被当已实现其实验不了的两处：**类型承诺**（接线已验、效果未验）、**中点 A/B 交汇**。

**留提示词还是做字段的判断标准**（他给的，已采纳）：
> **「每次现场判断的创作」且「忘了的后果可观察」** → 留提示词；否则才考虑字段。

#### 统一尺子（这一句是 §5.1 和 §5.3 的接缝）

本节的三档（✅ / ⚠️ / ❌）和 §5.3 末尾的「反向校准」其实是**同一把尺子**，
只是我从两头各用了一次，中间没写出来。kimicode 指出这是**双重标准**，成立：

> **有账本字段 + 代码比较 + 可观察输出 = 已实现；
> 只有文本（设置项 / 提示词块 / 注释契约）= 接线已验、效果未验；
> 两者皆无 = 缺。**

用这一句去量，两个方向的争议同时消解：

| 我原来的错 | 用这把尺子 |
|---|---|
| 把 `genres` 判成「已实现」（有设置项+提示词块就算） | → **只有文本 → 接线已验、效果未验** |
| 把 §1.5 那 8 层压成一条（有字段+判据+输出却只记一句） | → **三层齐 → 已实现**，该单列 |

> 所以 §1.5 和「反向校准」不是两个独立结论，**是同一把尺子的两端**。
> 以后再判「实现没实现」，先问三件事：字段在账本里吗？代码比较它吗？输出能观察到吗？
