# 缺陷：构建标记指纹依赖 CRLF 字节，一次 git 提交后必红（2026-11-13 发现）

> 发现方：opencode（需求位）｜ 状态：**待 zcode 裁定是否进本轮**
> 与 A/B/C 三批的**实现正确性无关**，但它会让验收时的红绿信号失真。

---

## 一、现象

`daoyan-构建标记` 现在是 **9/0 全绿**，指纹 `1f60a84c` 与源码一致。

但这个「一致」**建立在工作区的 CRLF 字节上**。仓库的 `.gitattributes` 是：

```
* text=auto eol=lf
```

→ 入库时统一存 LF，检出也是 LF。

## 二、证据

`src/剧情导演` 下有 3 个文件不是纯 LF：

| 文件 | git 跟踪 | CRLF | 裸 LF | 状态 |
|---|---|---|---|---|
| `引擎规则.ts` | 是 | 1077 | 0 | 全 CRLF |
| `提醒.ts` | **否** | 899 | 0 | 全 CRLF |
| `取料.ts` | 是 | 1 | 290 | **混合**（唯一那个 CRLF 在 `:247`，批 C 新增行） |

而 `git show HEAD:` 里，`引擎规则.ts` 和 `取料.ts` 都是**纯 LF**：

```
引擎规则.ts  HEAD: CRLF=0 裸LF=622
取料.ts      HEAD: CRLF=0 裸LF=709
```

→ 说明这两个文件是**在工作区被改成了 CRLF**，还没提交。

## 三、指纹预测

构建标记的算法是 `sha1(文件名 + 原始字节 + \0)`，**对行尾敏感**。

| 场景 | 指纹 | 构建标记 |
|---|---|---|
| 现在（工作区原样） | `1f60a84c` | ✅ 绿（与标记一致） |
| 只规范化已跟踪文件 | `962cf3cb` | ❌ 红 |
| 全部规范化成 LF | `105a75f1` | ❌ 红 |

**只要发生一次 git 提交 + 重新检出，指纹就不再是 `1f60a84c`。**

## 四、为什么这值得单独立一条

红的是 `daoyan-构建标记`，它的断言文案是「**改了一行没更新标记就红在这里**」。

但这次的红**不是**「谁忘了更新标记」，而是**行尾被 git 规范化**。
下一个看到这个红的人（很可能是验收方）会照着断言文案去追「谁漏了更新」——
追不到，因为根本没人漏。

这与今天那一族完全同型：**红的信号没说清是谁的责任。**

dsh 今天总结的四条：
1. 变异没打中 → 推断判据没问题 → 但没写进表
2. 需求方：提示词没这个词 → 推断模型不会写 → 但没跑载荷
3. 需求方：文本模式还原 → 指纹变了 → 看起来像实现方忘了更新标记 → 实际是工具改坏了文件
4. 实现方：夹具以高潮结尾 → 变红 → 看起来像 rule1 有问题 → 实际是 rule4 在兜

**本条是第 5 条**，而且是唯一一条**必然发生**的（前四条都是人为失误）。

## 五、修法选项（请 zcode 裁定，我不指定）

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 统一转 LF** | 把 3 个文件转 LF，重算指纹，更新标记 | 一次性；之后与 `.gitattributes` 一致，不会再红 |
| **B. 指纹忽略行尾** | 算指纹前 `replace(/\r\n/g, '\n')` | 标记不再对行尾敏感；但失去「精确字节」的语义 |
| **C. 不管** | 提交后看到红再更新标记 | 每次提交后红一次，且红的原因容易误判 |

我倾向 **A**（与仓库已有约定一致，不是新立规矩），但**不指定**——这是验收位的判断。

⚠️ 若选 A，注意 `提醒.ts` **未被 git 跟踪**（`git ls-files` 查不到，也没被任何 ignore 规则挡住）。
这本身是另一个问题：它在 `src/` 里、被 `取料.ts` import、被 30+ 用例引用，却不在版本控制里。

## 五·补：zcode 裁定（验收位，2026-11-13）

> **CRLF 裁定：走 A（统一转 LF）** —— 与 `.gitattributes` 一致、一次性解决、
> 防「提交后必红」的必然误判；B 失去精确字节语义、C 每次提交红一次且红因难判。
>
> **附带裁定：`提醒.ts` 未入库必须进本轮** —— 它在 `src/` 里被 30+ 用例引用却不在版本控制，
> 任何 git 操作（切分支/stash/提交）都会丢它，这不是行尾问题分级能覆盖的风险，走 A 时一并 `git add`。

执行：dsh（#225）。预期指纹 `105a75f1`（需求方实算，已要求实现方自算复核）。

## 六、与三批验收的关系

- **不影响** A/B/C 的实现正确性（代码逻辑与行尾无关）
- **影响** 验收时的红绿判读：若 zcode 在自己的检出/重打包流程里看到构建标记红，先查行尾
- 检查命令：

```bash
python -X utf8 -c "import io; b=io.open('src/剧情导演/提醒.ts','rb').read(); print('CRLF=%d 裸LF=%d' % (b.count(b'\r\n'), b.count(b'\n')-b.count(b'\r\n')))"
```

## 七、附：我今天踩的同类（已修复）

跑批 C 变异时，我的 Python 脚本用文本模式读写 `提醒.ts`：
读时 universal newline 把 CRLF → LF，写回时 `newline=''` 不还原 → **CRLF 全丢** → 指纹变 `482f9dea` → 构建标记假红。

已还原（`CRLF=899 裸LF=0`），指纹回到 `1f60a84c`。

**根因是 Python 文本模式默认做行尾转换。** 实测：

```
① Python 文本读 + newline="" 写:   CRLF=0 裸LF=3   ← 我今天踩的
② Python 文本读 + 默认 newline 写: CRLF=3 裸LF=0   ← 反而保留
③ Python 二进制往返:               CRLF=3 裸LF=0   ← 100% 安全
```

⚠️ dsh 纠正得对：**Node 的 `readFileSync(p,'utf8')` 会原样保留 `\r\n`**（已实测，`CRLF=2 裸LF=0`）。
所以规矩要分语言写：

- **Python**：碰 `src/` 必须 `open(p,'rb')` / `open(p,'wb')`
- **Node**：utf8 读写安全，但涉及行尾判断时也该用 Buffer
