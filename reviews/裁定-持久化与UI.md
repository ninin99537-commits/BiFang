## 二、成立的 P1（我核过的，共 9 条）

### P1-1 `saveMeta` 失败被吞，`writeStateSnapshot` 仍返回 true

`运行状态.ts:80-89`：`saveMeta` 返回 `void`，catch 里只 `console.error` + `toastError`。
`快照.ts:168` 无条件 `saveMeta(meta)`，`:170` 无条件 `return true`。

**后果**：快照写进楼层了，但 `meta.快照楼层` 没登记 → 下次 `loadData` 找不到它，回退到更早的快照。面板显示"已保存"，引擎用的却是旧账本。

**修法**：`saveMeta` 返回 `boolean`，`writeStateSnapshot` 在 `:168` 判它 —— 失败就 `return false`（宁可报失败，也不要"写进去了但读不回来"）。

### P1-2 `保存推进结果` 先改内存再落盘

`快照.ts:208-209`：

```ts
data.处理到楼层 = 锚点楼层;
data.清空层 = 0;
const 落盘 = writeStateSnapshot(data, 锚点楼层, 锚点楼层, true);   // ← 在改内存之后
```

失败分支 `:214` 仍返回 `数据: data`（已被污染），`update.ts:513-515` 把它赋给 `stateStore.data`。

**后果**：落盘失败时，`处理到楼层` 已前进、`清空层` 已清 0 —— 内存与磁盘分叉。下一轮会以为这一层已经推过了。

**修法**：改成先算 payload、落盘成功后再改 `data`（或失败时回滚这两个字段）。

### P1-3 `saveData` 在"原锚点有效但写失败"时静默改写到最新楼

`快照.ts:190-191`：

```ts
if (原锚点有效 && 写(原锚点)) return true;
return 最新 !== 原锚点 ? 写(最新) : false;
```

第一分支失败会**直接落到第二分支**，没有区分"锚点无效"与"写入失败"。

**后果**：正是 `:178-186` 注释里说要修掉的"锚点漂移" —— 删楼回退粒度错位、`取撤销楼层` 误判为已推。

**修法**：`原锚点有效` 时若写失败，**不要再写最新楼**，直接 `return false` 让用户看到失败。

### P1-4 `sync编剧备忘` 在"落点 null + 不用写"时跳过清理

`注入.ts:44-54`：

```ts
if (!解析.落点) {
  if (要写) { ...toast... }
  return;            // ← 这里跳过了 清理别处的副本('')
}
```

`:58-61` 才是「不写 → 清理所有副本」的分支，但走不到。

**后果**：`解析事实层落点({ 允许新建: false })` 只探 primary/additional/聊天书（`世界书落点.ts:104-158`），**不含 globalNames**。聊天书被删后必然 null → 关掉总开关，全局世界书里的旧备忘继续注入。

**修法**：`!解析.落点 && !要写` 时也要调 `清理别处的副本('')`。

### P1-5 `清理别处的副本` 不扫 `globalNames()`

`世界书落点.ts:167-181` 只 `候选.add(primary/additional/chatName)`；
而 `候选世界书名()`（`:200-222`）额外扫 `globalNames()`（`:216-220`）。

**后果**：旧版本留在全局书里的副本永远不会被注入路径清掉，主 AI 同时读到两份（一份永远陈旧）。

**修法**：`清理别处的副本` 改用 `候选世界书名()`，别自己再拼一份。

### P1-6 `提交账本变更` 里 `void sync编剧备忘(...)` 即发即忘

`账本变更.ts:34`：`void`，不 await、不排队。
`注入.ts:64-99` 走 `worldbook.entries(名)` → 改 → `worldbook.update(名, ...)` 的整本读改写。

**后果**：连续修笔（面板上快速点两下）产生并发 read-modify-write，后完成者覆盖前一次内容。

**修法**：加一个串行队列（模块级 `Promise` 链），或把 `sync编剧备忘` 的调用改成 `await`（但它是被非 async 函数调的，需要改签名）。

### P1-7 `onUnmounted` 用 `parentWin.value` 摘 resize 监听，此刻可能已为 null

`面板机制.ts:622`（挂）与 `:626`（摘）：

```ts
const parentWin = computed<Window | null>(() => frameWin.value?.parent ?? null);   // :88
```

`frameWin` 依赖 `rootEl`（模板 ref）。Vue 卸载元素 vnode 时先 `setRef(ref, null)` 再 flush `um` 钩子，所以 `parentWin.value` 为 null，`:626` 的 `?.removeEventListener` 静默不执行。

**后果**：监听器永久留在父窗口，闭包拖住整个组件（热重载时每次叠一份）。

**状态**：**待真机确认 ref 置空时序**。若顺序相反则本条不成立。修法无论如何都便宜：挂的时候把 `parentWin.value` 存进一个局部变量，摘的时候用那个变量。

### P1-8 壳 iframe 不做 script_id 去重

`悬浮球界面.ts:28-45`：直接 `$('<iframe>').attr({script_id: ...}).appendTo('body')`，此前没有 `document.querySelector('iframe[script_id="…"]')` 判存。

**后果**：脚本重复加载（重导入/热重载）就出现两个球、两套事件监听，`pagehide`（`:56-59`）只清自己那一个。

**修法**：append 前先查同 `script_id` 的旧 iframe，有就先 `.remove()`（或直接复用）。

### P1-9 `loadData` 在 `lastMessageId()` 抛错时静默返回空账本

`快照.ts:49-56`：

```ts
try { lastId = useHost().chat.lastMessageId(); } catch { lastId = -1; }
if (floors.length > 0 && lastId < 0) {
  return { ...emptyData(), 清空层: meta.清空层, 已剧终: !!meta.已剧终 };
}
```

正常分支**连 `console.warn` 都没有**（只有最外层 catch 有）。

**后果**：面板显示"还没有伏笔/章回/人物"，用户以为账本被清空。`index.ts:203-215` 的 3 秒补读只在 `!章回 && 伏笔空` 时跑一次，错过就永久空账本。

**修法**：这条路径加 `console.warn` + 一条 toast（"账本暂时读不到，正在重试"），并让 3 秒补读在这条路径上也能触发。

## 三、成立的 P2（我核过的，共 8 条）

### P2-1 `终局步` computed 把 0 显示成 1

`悬浮球界面.vue:1386`：`Math.max(1, Math.min(5, Number(账本.value.终局步) || 1))`。
`schema.ts:949` 明确 `0 = 还没开始`。

**修法**：`0` 时显示"未开始"，不要显示"第 1/5 步"。

### P2-2 `saveData` 成功后不回写 `data.锚点楼层`

`快照.ts:189-191` 只写快照、不赋 `data.锚点楼层`；对比 `保存推进结果:214` 是 `{...data, 锚点楼层}`。
`悬浮球界面.vue:1431` 与 `球状态.ts:153` 都读 `账本.锚点楼层`。

**后果**：新账本（锚点 -1）首次手改后，快照已在最新楼，面板仍显示"—"。

### P2-3 界面偏好的基线会被 localStorage 副本播种

`src/共用/界面偏好.ts:70`：`if (!基线) 基线 = klona(本地);`
`:83` 判据是 `if (基线)`，而文件头 `:6` 承诺的是"没成功读到全局就不写全局"。

**后果**：全局读失败时用本机旧缓存当基线 → 旧坐标覆盖别处/别的设备的真实值。

**修法**：加一个独立的 `全局读过` 布尔，只有它为 true 才允许写全局。

### P2-4 `兜底球心()` 在 computed 里改响应式状态

`面板机制.ts:434`（`orbStyle`）与 `:653`（`球心坐标`）都调 `兜底球心()`；
该函数 `:260-262` 直接赋值 `anchorX.value` / `anchorY.value`，而 `anchorX` 上挂着 `watch(..., applyFrame)`（`:414`）。

**后果**：渲染期改响应式状态，有递归更新风险（Vue 会警告 "Maximum recursive updates exceeded"）。

**修法**：`兜底球心` 拆成"算"与"写"两半 —— computed 里只算夹取后的值，写 `anchorX/Y` 留给 `applyFrame`。

### P2-5 老账本迁移有损：`待读队列` 丢无引用项、`节拍` 回落成「阴影」

`账本迁移.ts:442-443`：`if (!引用) continue;` —— 静默丢条目（理由/目标一起没）。
`:480`：`节拍: 节拍列表.includes(raw.节拍) ? raw.节拍 : '阴影'` —— 无"保留原文/标待核"分支。

**后果**：与 `规范化证据:258` 的"保留原文标待核"纪律相反。下次落盘即冻结成「阴影」。

**修法**：`节拍` 不在枚举内时保留原文 + 记一条 `拒绝`；`待读队列` 无引用项也记一条 `拒绝` 而不是 `continue`。

### P2-6 `clearAllData` / `discardSnapshotAt` 的 `vars.del` 失败全吞

`快照.ts:236-242`：`for (...) { try { del } catch { /* 忽略 */ } }`，`:243-249` 无条件 `saveMeta(fresh)`。

**后果**：楼层里留下孤儿快照（chat 文件变大、且永远读不回来）。

**修法**：返回"删了几份/几份失败"，失败的楼层**不要**从 `meta.快照楼层` 里删（保留登记才能重试）。

### P2-7 注入更新分支不重置 `enabled` / `probability`

`注入.ts:66-77`：`{...entry, name, content, recursion}` —— `...entry` 保留旧的 `enabled`/`probability`。
新建分支 `:83-84` 才写 `enabled: true, probability: 100`。

**后果**：用户在世界书里手动关掉（或调到 50%）那条备忘后，插件每轮"同步成功"却永远不生效，且无任何提示。

**修法**：更新分支也写 `enabled: true, probability: 100`，或检测到被关时给一条 toast。

### P2-8 `pagehide` 卸载后没有 `pageshow` 重建

`悬浮球界面.ts:56-59`：只有 `$(window).on('pagehide', ...)`，无 `pageshow` / `persisted` 分支，无 `.off`。

**后果**：bfcache 返回后球与面板彻底消失，而 `window` 上的 handler 还在。

**状态**：**待确认 bfcache 是否在酒馆页面生效**。修法便宜：加 `pageshow` 且 `event.persisted` 时重新挂。
