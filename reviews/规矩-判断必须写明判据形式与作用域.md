# 规矩：判断必须写明判据的精确形式与作用域

> 立规日：2026-11-13
> 起因：本轮「commit 边界」争议中，opencode 与 dsh 合计 8 次同型错误。
> 提议：opencode（需求）｜ 附议：dsh（实现）｜ 待 zcode（验收）确认

---

## 一、规矩本身

**任何「有 N 个」「会不会坏」「是不是这样」的判断，必须同时写出：**

1. **判据的精确形式** —— 用什么正则 / 什么函数 / 什么命令，能一字不差地复现这个判断
2. **判据的作用域** —— 它扫了哪些文件、排除了哪些、为什么排除
3. **判据依赖的前提** —— 换个前提它还成立吗

**写不出这三样的判断，不算结论，只能算线索。**

---

## 二、为什么要立这条

本轮 8 次错误，全部是同一族：**判据的作用域比它想测的东西大或小**。

| # | 谁 | 判据 | 它想测的 | 实际测到的 |
|---|---|---|---|---|
| 1 | opencode | `git show HEAD:file` 含某字符串 | 依赖成立 | 字符串出现（注释也算） |
| 2 | opencode | 扫 `*.ts` / `*.vue` | 未跟踪文件全集 | 漏 `.scss` → 报 5 个（实际 6） |
| 3 | opencode | 只扫 `src/剧情导演` | 引用悬空全集 | 漏 `src/共用` → 报 6 个（实际 8） |
| 4 | opencode | 转述「此刻 commit 会坏」 | 已验证的事实 | 别人的说法，未跑过 |
| 5 | opencode | 打包 `index.ts` | 编译是否成功 | `.vue` loader 缺失（环境问题） |
| 6 | opencode | BFS 边 = `from '...'` | import 图全集 | 漏副作用导入 `import './x'` |
| 7 | dsh | `git show HEAD:file` 含该名字 | HEAD 已引用 | 字符串出现，非 import |
| 8 | dsh | 边正则含 `import` 关键字 | 覆盖副作用导入 | **碰巧**覆盖，判据本身没保证 |

**第 8 条最值得注意**：dsh 的判据**结果是对的**，但他的判据里没有任何东西能告诉他「这是碰巧的」。
换个写法（只写 `from\s*['"]`）就会和 #6 一样报错。

> **「碰巧对」和「判据写对了」不是一回事。**
> 一个判据如果无法说明自己为什么不会漏，它就只是运气好。

## 三、正例（dsh #244 的写法，可直接当模板）

```
判据：暂存的文件（含 A 与 被拉进来的 M）里，凡 `import { 具名符号 } from './相对路径'`，
      解析到「已跟踪且 M 状态」的目标文件，且该符号在 `git show HEAD:<目标>` 的
      **export 声明**里不存在（正则认 interface/type/const/let/function/class/enum + export{}，
      已剥 `type ` 前缀、已处理 `as`）→ 记为"必须一起进"。
```

它好在三点：
- 说了用什么正则（可复现）
- 说了扫什么（暂存 + 闭包）
- 说了**排除什么**（剥 `type ` 前缀、处理 `as`）—— 这一条正是 #1 / #7 踩坑的地方

### ⚠️ 但这段模板本身**不精确**，照抄会把缺陷带进规矩（dsh #256 指出，已实测）

**它只认 `import { 具名符号 } from`，覆盖不到另外几种真实存在的形态。**
实测（2026-11-13，扫 `src/` 全量 204 个 `.ts` / `.vue`）：

```
总依赖边: 663   模板覆盖: 494   漏: 169  ← 漏掉 25.5%
```

**漏掉的 169 条里，有 43 条指向本轮敏感的未跟踪 / M 文件**，包括 `index.ts -> 悬浮球界面.ts`
（正是 #6 那条 BFS 漏掉的边）、`取料.ts -> 提醒.ts`（`export *`）、
`悬浮球界面.vue -> 悬浮球样式.scss`（`<style src>`）。

> ⚠️ **这一版数字是我第二次数的。第一版报的 739 / 605 / 134 是错的** ——
> 我的正则没限定「路径以 `.` 开头」，把 `pinia` / `vue` / `zod` / `@phosphor-icons`
> 这类**裸包名**也当成了依赖边（114 条）。依赖边只该算项目内的相对路径。
> dsh 独立数出 663 / 494 / 169，我换成他的口径后**逐字相同**。
>
> 这正是本规矩第 1 条要防的事：**我当时给了数，没给正则，所以连自己都复现不出自己的数。**

### 写依赖判据时必须清点的形态（缺一条就不算写全）

**判据的精确形式**（`src/` 全量 204 个 `.ts` / `.vue`，按匹配次数计，不跨行、行首锚定）：

| 形态 | 正则 | 本仓库实际数量 | 模板是否覆盖 |
|---|---|---|---|
| `import { a, b as c } from './x'` | `^\s*import\s*\{[^}]*\}\s*from\s*['"]\.[^'"]*['"]` | 494 | ✅ |
| `import type { T } from './x'` | `^\s*import\s+type\s*\{[^}]*\}\s*from\s*['"]\.[^'"]*['"]` | 108 | ❌ |
| `import D from './x'`（默认导入） | `^\s*import\s+[A-Za-z_$][\w$]*\s+from\s*['"]\.[^'"]*['"]` | 45 | ❌ |
| `export { a } from './x'`（具名再导出） | `^\s*export\s*\{[^}]*\}\s*from\s*['"]\.[^'"]*['"]` | 6 | ❌ |
| `import './x'`（**副作用导入**） | `^\s*import\s*['"]\.[^'"]*['"]` | 4 | ❌ |
| `export * from './x'`（**再导出**） | `^\s*export\s*\*\s*from\s*['"]\.[^'"]*['"]` | 3 | ❌ |
| `import('./x')`（动态导入） | `import\(\s*['"]\.[^'"]*['"]\s*\)` | 2 | ❌ |
| `src="./x.scss"`（`<style src>`，只有这种算边） | `src\s*=\s*['"]\.[^'"]*\.scss['"]` | 1 | ❌ |
| `import * as NS from './x'`（命名空间） | `^\s*import\s*\*\s*as\s+[A-Za-z_$][\w$]*\s+from\s*['"]\.[^'"]*['"]` | 0 | ❌（本仓库暂无） |
| `import D, { a } from './x'`（默认+具名混用） | — | 0 | ❌（本仓库暂无） |
| `export { default as X } from './x'` | — | 0 | ❌（本仓库暂无） |
| `require('./x')` | — | 0 | ❌（本仓库暂无） |

**合计 663，模板覆盖 494，漏 169。** 复现脚本：`tmp/compare-counts.py`。

⚠️ **本表不含跨行 import / export（实测 13 处）**：它们既不被模板正则覆盖，也不被上表的合计覆盖。
所以 **663 不是全集**。把跨行算进去，真实数字是：

```
总边 663 + 13 = 676    漏 169 + 13 = 182    漏占比 182/676 ≈ 26.9%
```

跨行形态长这样（`src/自定义状态栏/store.ts:4`、`烟火_世界运转/state.ts:4` 等）：

```
import {
  a,
  b
} from './x'
```

**为什么单列而不是加进表里**：上表所有正则都是**单行锚定**的，逐条数不到跨行。
硬把它们塞进同一张表会让读者以为「一个正则就能数全」。分开写，才能看出
**「按行正则」这个方法论本身有天花板**。复现脚本：`tmp/verify-multiline-impact.py`。

⚠️ **663 是「匹配次数」，不是「去重边数」**：同一个文件里同一种形态 import 同一个目标两次会被数两次。
按 `(文件, 目标路径, 形态)` 去重后是 **659 条边**，其中指向敏感文件的 43 条也是按去重边算的。
两个口径都写清，是因为**混用会让数字对不上**——这正是本规矩第 1 条要防的。

⚠️ **「暂无」不等于「不用考虑」**：后四种今天 0 条，但下一轮谁写了，清单里没有它，
判据就会**静默漏掉**。所以标「暂无」保留在表里，比删掉更有用。

⚠️ **两个容易混淆的「type」要分开**：
- **符号名里的 `type`**：`import { type T, a } from` → 要剥掉前缀
- **语句级的 `import type { T }`** → 是**独立形态**，不是剥前缀

原模板写了「已剥 `type ` 前缀」，容易被读成「type 的事考虑过了」，
实际它只覆盖了前者，而后者有 **108 条**。**这就是「考虑周全的错觉」的典型样本。**

⚠️ **跨行 import 是这张表覆盖不到的**：本仓库有 **13 处** `import {\n a,\n b\n} from './x'`。
上面所有正则都是单行锚定的，逐条数不到它们。如果判据要覆盖跨行形态，
必须显式说明「按语句解析」而不是「按行正则」。

> ⚠️ **我第一次数成 15 处，多出的 2 处是误匹配**：`@phosphor-icons/vue` 这种**裸包名**的跨行 import
> （`彼方/悬浮球界面.vue:186`、`烟火/悬浮球界面.vue:2`）。我的正则没要求路径以 `.` 开头，
> 和 §三 表里那个 739 的错**是同一个错法**——同一个「没限定相对路径」的漏洞，在同一天犯了两次。

> **引用别人的判据当模板时，要先验它能不能漏。照抄不是尽责，验过才是。**

## 四、反例（本轮真实出现过的话）

| 反例 | 缺什么 |
|---|---|
| 「有 6 个未跟踪文件」 | 没说扫了哪些目录 |
| 「此刻 commit 会坏」 | 没说是普通 commit 还是 `-a`，也没跑过 |
| 「HEAD 已引用它」 | 没说是字符串出现还是 import |
| 「要么全带、要么不可编译」 | 没说是「入口 = index.ts」前提下 |

最后一条是 dsh 自己指出并补的（#252）：
> 同一句结论换个入口就不成立，而读的人看不出它依赖入口。

## 五、适用范围

这条规矩适用于**所有方向**的判断，不分需求 / 实现 / 验收：

- 需求方写派活单：「这个缺口有 3 处」→ 要写清怎么数的
- 实现方写回执：「全量 165 全绿」→ 要写清跑的是哪棵树
- 验收方写结论：「批 A 通过」→ 要写清验了哪几条、哪几条没验

**尤其适用于「数字」和「会不会」两类断言**，因为这两类最容易被当成事实直接引用。

## 六、与既有纪律的关系

这条是既有纪律的**上游**。已有的几条都是它的特例：

| 既有纪律 | 是本规矩的哪种特例 |
|---|---|
| 「测不到目标代码的断言等于没写（假绿）」 | 作用域**小于**目标（第 2 条） |
| 「红的信号没说清是谁的责任」 | **前提未验证**（第 3 条） |
| 「协作者给的数也要自己跑一遍」 | 第 1 条（精确形式）+ 第 3 条（前提） |
| 「判据里的中文串必须从源码复制」 | 第 1 条（精确形式可复现） |

> **归类修正（dsh #256）**：原先我把「红的信号没说清是谁的责任」归为「作用域大于目标」，那是错的。
> `.vue` loader 缺失（#5）不是「扫多了文件」，是「**测的东西根本没被编译**」——
> 判据本身没问题（打包确实失败了），错的是**环境前提不成立**。
> 改后四条纪律正好一一对应规矩的三要素，而不是三条挤在「作用域」上。

## 七、本轮的实际收益

立这条规矩的直接原因不是「我们错了 8 次」，而是**其中至少 3 次差点变成错误结论**：

- #5：`.vue` loader 缺失 → 差点得出「B 组也失败 → 闭包没求全」→ 会去追一个不存在的依赖
- #6：BFS 漏副作用导入 → 得出「更新弹条判定不可达」→ 会误判「新模块没接线」
- #4：转述「commit 会坏」→ 差点让 dsh 按错的风险模型做决策

**如果没有「再问一句」的习惯，这 3 条都会变成写进文档的结论。**

## 八、附：引用别人判据时的自检（本轮新增）

规矩写成当天就发生了一次：需求方把实现方 #244 那段判据抄成「正例模板」，
而那段判据本身漏了 18% 的依赖边（见 §三）。抄得很忠实，错得很完整。

> **照抄不是尽责，验过才是。**
> 引用任何判据（别人的或自己的旧文档）当模板前，必须先问：
> **它能漏什么？漏掉的部分在这个项目里有多少？**

这条和 §二 的「碰巧对 ≠ 判据写对了」是一对：
- §二 说的是**自己写**判据时不能靠运气
- §八 说的是**引用**判据时不能靠信任

## 九、附：同一判据有多份副本时，用「已知错例」当回归集（dsh #266）

### 病根

本轮的 739 和 15 是**同一个漏洞的两份副本**：两次都是「正则没限定路径以 `.` 开头」。
我修了 739（单行正则加上 `\.`），**没回头改跨行那个**，于是 15 里又多出 2 条误匹配。

> **改一处不等于改全部。判据不是一个文件，是一族文件。**

### 可执行做法

**同一个判据如果有 N 份副本，改完要拿「旧错例」去跑每一份。**

本轮的具体样本（都是真实抓到过的，不是编的）：

```python
已知错例 = [
    ('裸包名 pinia（单行）',          False, "import { defineStore } from 'pinia';"),
    ('裸包名 vue（单行）',            False, "import { ref } from 'vue';"),
    ('裸包名 @phosphor-icons（跨行）', False, "import {\n PhX,\n PhY\n} from '@phosphor-icons/vue';"),
    ('相对路径单行（应匹配）',         True,  "import { a } from './real';"),
    ('相对路径跨行（应匹配）',         True,  "import {\n a,\n b\n} from './real';"),
]
```

喂给四份副本，实测结果：

| 副本 | 裸包名被误匹配 | 正确匹配 |
|---|---|---|
| ① 单行·无 `\.` 限定（739 的错版） | **3 处** ❌ | ✅ |
| ② 单行·加 `\.` 限定（修好版） | 0 ✅ | ✅ |
| ③ 跨行·无 `\.` 限定（15 的错版） | **1 处** ❌ | ✅ |
| ④ 跨行·加 `\.` 限定（修好版） | 0 ✅ | ✅ |

**错版立刻现形，不需要等到别人数出 13 vs 15。** 复现脚本：`tmp/verify-known-bad-cases.py`。

> **已知错例是最便宜的回归集**，比「再想一遍有没有别处」可靠。

### ⚠️ 写这条时我自己又踩了一次：测试设计错

我第一版脚本把「单行样本」也期望「跨行正则」能匹配，于是 ④ 被判 ❌。

**那是假红。** 因为「单行正则」和「跨行正则」是**互补的两份**，不是同一份的两个版本 ——
跨行正则本来就不该匹配单行。

修正后的测试模型要分两个维度：

```
维度 A（每份副本都要过）：裸包名必须被拒绝 —— 不管单行还是跨行
维度 B（按分工）：单行样本只喂单行正则，跨行样本只喂跨行正则
```

**教训**：拿已知错例当回归集时，**先想清「这份副本负责哪类样本」**，
否则「互补关系」会被误当成「缺陷」，产生一批假红。

### 与「要不要对齐数字」的关系

本轮的 13 vs 15 之争，最后查出来是**判据漏洞的副本**，不是数字噪声。所以要区分：

| 差异性质 | 处理 |
|---|---|
| **口径不同**（匹配次数 vs 去重边数、含不含裸包名） | 写清口径，**不对齐** |
| **判据漏洞**（某份副本少了一个限定） | **必须查**，因为漏洞会在别处再犯 |

dsh 原来说「不追求对齐」时没区分这两种，后来自己补上了（#266）：
**我不追求数字一致，但差异一旦指向漏洞就必须查。**
