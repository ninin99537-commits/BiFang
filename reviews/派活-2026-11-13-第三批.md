## ① P2 2.5 `必演` 改三态

### 病根

`必演` 现在是 `事件 | null`，`null` 同时表示两件事：

1. 「本幕确实没有确定要发生的事件」（导演想清楚了）
2. 「导演根本没填这个字段」（漏写）

`提醒.ts:202` 判的是 `if (!上一道 || 上一道.已跳过 || 上一道.必演) return [];`
—— 两种情况都会返回 `[]`，于是 `上一道缺必演` 这条提醒**在情况 2 下不响**。

真机上模型多数时候不填，这条提醒等于哑的。

### 改法

```ts
/** 必演三态（2026-11-13 P2 2.5） */
export type 必演态 = 必演事件 | '无' | null;
//                    有事件      明确声明没有   没说
```

- `'无'` → 提醒不响（导演想清楚了）
- `null` → 提醒照响（真的漏写）

### 硬边界

1. **`'无'` 不是空事件**。`规范化必演('无')` 必须返回 `null`（沿用现有语义），
   但 `上一道.必演 === '无'` 这个**字符串本身要保住**，不能被 `规范化必演` 吃掉。
   这是最容易搞错的地方：`规范化必演` 是给"有事件"用的，不是给三态用的。
2. **不许改 `必演事件` 接口**。`命运` / `角色ID` / `镜头外` / `既成事实` / `未执行轮` 五个字段一个不动。
3. **账本迁移必须兼容**：老账本里 `必演` 可能是 `null` 或对象，不许出现第三种形状导致崩溃。
4. **提示词要写清三态**：`prompts.ts` 里必须告诉导演「明确没有就写 `"无"`，别留空」。

### 判据（怎么算通过）

**行为**：构造 `上一道指令.必演 = null` 和 `= '无'` 两份账本，跑 `结构提醒`。

| 输入 | 期望 |
|---|---|
| `必演 = null`（没说） | 提醒里**有**「上一道指令没有「必演」」 |
| `必演 = '无'`（明确声明没有） | 提醒里**没有**这句 |
| `必演 = {内容:'x',...}`（有事件） | 提醒里**没有**这句 |
| 老账本 `必演` 字段整个缺失 | 按 `null` 处理（提醒照响） |

**反例（任一出现即退回）**：
- `'无'` 被当成有事件（提醒不响但 `规范化必演` 返回了非 null）
- 老账本读进来直接抛错
- 提示词里没提 `"无"` 这个写法（导演不知道可以这么写，等于没改）

**变异测试要求**：把 `上一道.必演 === '无'` 这个判断删掉，用例必须变红。

## ② P2 2.2 提醒表加 `组` / `优先级`

### 病根

`提醒.ts:180-484` 是 22 条平铺规则，同一条事实可能被两条同时说。
现在已经用「三处共用一个判据」（`判收章` + `选收章发言者`）部分解决了，
但那是**硬编码的三条**。将来加规则还得再想一遍互斥。

### 改法

```ts
export interface 提醒规则 {
  名: string;
  /** 互斥组名；同组只出一条。不填 = 不参与互斥 */
  组?: string;
  /** 同组内比大小，大的出。不填 = 0 */
  优先级?: number;
  生成: (账本, 上下文) => string[];
}
```

`结构提醒` 执行器改成：

```ts
export function 结构提醒(账本, 当前幕) {
  const 上下文 = { 当前幕 };
  // 先全部跑一遍，按组收集
  const 命中: { 规则: 提醒规则; 行: string[] }[] = [];
  for (const 规则 of 提醒规则表) {
    const 行 = 规则.生成(账本, 上下文);
    if (行.length > 0) 命中.push({ 规则, 行 });
  }
  // 同组只留优先级最高的那条（同优先级保留表里靠前的）
  const 组内胜者 = new Map<string, 提醒规则>();
  for (const { 规则 } of 命中) {
    if (!规则.组) continue;
    const 现有 = 组内胜者.get(规则.组);
    if (!现有 || (规则.优先级 ?? 0) > (现有.优先级 ?? 0)) 组内胜者.set(规则.组, 规则);
  }
  // 输出：无组的全出 + 有组的只出胜者
  return 命中
    .filter(({ 规则 }) => !规则.组 || 组内胜者.get(规则.组) === 规则)
    .flatMap(({ 行 }) => 行);
}
```

### 硬边界

1. **不许改变现有 22 条规则的输出**（除了互斥让位）。改完跑全量，`159` 个文件必须还是全绿。
2. **必须把现有那三条收章语义的规则归到同一组**：
   - `幕纲落后或该收章` → `组: '收章语义'`、`优先级: 3`
   - `章长度` → `组: '收章语义'`、`优先级: 2`
   - `生活幕` → **不进组**（它解释的是"为什么幕型不生效"，不是催收章）
3. **`选收章发言者` 不许删**。它现在是对的，且 `生活幕` 依赖它做让位判断。
   新机制是**在它之上再加一层保险**，不是替代它。
4. **同优先级时保留表里靠前的**（顺序稳定，不许因为 `Map` 迭代顺序漂移）。

### 判据（怎么算通过）

| 场景 | 期望 |
|---|---|
| 三条收章语义规则同时命中 | **只出 1 条**（`幕纲落后`，优先级 3） |
| 只有 `章长度` 命中 | 出 1 条（`章长度`） |
| 只有 `生活幕` 命中 | 出 1 条（`生活幕`，不参与互斥） |
| 无组规则（如 `中点`） | 照常全出 |
| 两条同组同优先级 | 出表里靠前那条 |

**反例（任一出现即退回）**：
- 改完 159 个用例有任何一条变红（说明动了不该动的输出）
- 同组同优先级时结果不稳定（跑两次顺序不同）
- `生活幕` 被拉进收章语义组（它会和 `幕纲落后` 打架，真机第 68 场就是这么坏的）

**变异测试要求**：把 `组内胜者` 那段逻辑注释掉，用例必须变红。

## ③ 构建标记自动化

### 病根

`index.ts:24` 的 `构建标记` 靠人记得手改。本轮它就停在 `v22` 没跟上（代码已到 11-13），
真机日志第一行分不清跑的是哪一版。

### 改法（选一个，你判断）

**方案 A（推荐）**：`package.json` 加 script，构建时自动写入 git 短 hash + 日期。

```json
"build:daoyan": "node tools/写构建标记.mjs && webpack --config ..."
```

`tools/写构建标记.mjs` 读 `git rev-parse --short HEAD` + 当天日期，重写 `index.ts` 里那一行。
**风险**：构建会改源文件，可能触发 watch 循环。需要确认 webpack watch 不会因此无限重编。

**方案 B（更稳）**：标记不在源码里写死，改由 webpack `DefinePlugin` 注入。

```ts
export const 构建标记 = __BUILD_MARKER__;
```

`webpack.config.js` 里用 `DefinePlugin({ __BUILD_MARKER__: JSON.stringify(...) })`。

**方案 C（最小改动）**：加一条用例，检查 `构建标记` 里的日期是否 ≥ 最近一次 `src/` 改动日期。
不合格就红，逼人改。**不改构建流程，只加守卫。**

### 我的建议

**先做 C，再评估 A/B。** 理由：C 是纯用例，零风险，能立刻防住"忘了改"；
A/B 会动构建流程，而构建流程现在跑得好（watch + 热重载），改坏了代价大。

### 判据（方案 C）

| 场景 | 期望 |
|---|---|
| `构建标记` 日期 < `src/剧情导演/` 最新 mtime 的日期 | 用例**红** |
| `构建标记` 日期 ≥ 最新 mtime 的日期 | 用例**绿** |

**反例**：
- 用例靠 `mtime` 但 `copyFileSync` 保 mtime（这台机器实测会保）→ 改成比**内容指纹**
- 日期格式解析失败直接跳过（必须红，不许静默放过）
