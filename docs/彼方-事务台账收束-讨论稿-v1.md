# 彼方 · 事务台账的收束问题 讨论稿 v1

> **交付对象**：其他 AI（用来对轰）＋ 开发 AI（后续落地）。
> **要解决的问题**：「未完成事项」这本事务台账，现在**开得比关得快**；而"进行中永不淘汰"让 8 条上限形同虚设。要讨论的是——**谁、依据什么、在什么时候，把一条「进行中」的事务关掉。**
> **读法**：§1 是自包含背景（不了解彼方也能读）；§2 是真实现场数据；§3 是已有的两份主张与分歧；§4 是要你回答的问题；§6 诚实标了哪些是事实、哪些是判断。
> 写于 2026-10-11。文中的"剧情时间"指被追踪的那场虚构剧内的时间。

---

## 0. 一句话

台账的**关门**目前完全依赖"正文恰好写到那件事完成了"，而**开门**只是模型随手一记——两边不对等；同时 `进行中` 永不淘汰，于是条目数单调增长，8 条上限永不生效。真正要设计的是"**收束机制**"，而不是"再多一个状态"。

## 1. 背景（自包含）

### 1.1 彼方是什么

一个跑在 AI 角色扮演前端（酒馆 / Tavern Helper）里的状态机插件。主 AI 写完一段正文后，彼方用**另一个独立的 AI 请求**做一次"幕后更新"：为每个 NPC 维护一张状态卡（当前在做 / 位置 / 心里惦记 / 未完成事项 / …）。状态卡写进**聊天楼层变量**（持久、可随删楼/重 roll 回退），并被注入给主 AI，作为"镜头之外真实发生过的事"。

### 1.2 「未完成事项」= 事务台账（现状规则）

每个 NPC 一个数组，每条形如：

```json
{"编号":"T9","时间":"2025-10-17","内容":"给女儿买一个玩偶当生日礼物","状态":"进行中","结果":""}
```

| 规则 | 内容 |
| --- | --- |
| 编号 | `T1/T2…` 由**代码**分配，永不复用；新事务不要写编号 |
| 内容 | **写下即冻结**（防"玩偶"被后续轮次写成"蛋糕"）；要改内容就作废旧条、另开新条 |
| 状态 | 只有 `进行中` / `已完成` / `已作废` |
| 增量协议 | 已有事务**只回「编号 + 状态(+结果)」**，内容不用重抄（重抄会被丢弃） |
| 上限 | 每个 NPC 最多 **8 条**；超额**先淘汰最旧的 `已完成/已作废`**，**`进行中` 永不淘汰** |
| 空回合 | 本轮什么都没返回（或只返回认不出的东西）→ 台账**原样不动**，连封顶都不做 |

### 1.3 两条硬限制

1. **更新 AI 只读最近 N 层正文**（设置项 `读取最近 N 条 AI 回复`，默认 3；可以调大，但不可能开到几十层）。它对一件 20 层前定下的事，**在正文里永远没有材料**。
2. **长期记忆只存在于"卡"上。** 卡的持久层是楼层变量快照；**插件模块级状态不持久**（刷新页面 / 切换聊天即丢失），历史快照也只精确保留最近约 10 层（更早是稀疏检查点）。→ 任何"计数器 / 旁路映射"必须能存活于卡内，不能活在内存里。

### 1.4 注入侧的代价（为什么僵尸条目会伤人）

台账会被渲染成**一行文本**塞进给主 AI 的表格单元格（换行压成 `; `），格式是"进行中逐条 + 最近 3 条已办摘要"，且**整块末尾共用一句固定提醒**：

> 以上是幕后已发生/已定的事实，正文收束时必须照此兑现；其中的具体物品、人名、地点不得替换或泛化。

也就是说：**一条早该作废的僵尸事务，会以"主 AI 必须兑现的事实"的身份进入正文生成**。这不是 token 问题，是剧情问题。

### 1.5 代码事实清单（判断方案可行性的前提，别绕过）

| # | 事实 | 位置 | 对方案的约束 |
| --- | --- | --- | --- |
| F1 | 台账**每一轮都会被代码重建对象**：规范化函数只产出 `{编号,时间,内容,状态,结果}` | `事务台账.ts:115-147`、`185-216` | 想给事务加任何字段（如计数），必须在**这一处**显式保留，否则每轮被丢掉 |
| F2 | `结果` **只在**状态为 `已完成/已作废` 时才落库；`进行中 + 结果` 一律丢弃 | `事务台账.ts:226-266`、`台账操作.ts:65-69` | 不存在"结果随轮次越堆越长"的累积增长；只有单次生成写太长 |
| F3 | 注入侧的"已办"**已经是压成一行、只取最近 3 条** | `事务台账.ts:339-349` | "已办整段进提示词、成本高"这个担忧不成立 |
| F4 | 封顶只认"是不是 `进行中`"；注入渲染、面板样式同理 | `事务台账.ts:162-174`、`334-349`、`台账操作.ts:74-81` | **加第四态不产生任何行为差异**，只会多一个 UI 按钮（按钮是 `v-for` 状态表渲染的） |

| F7 | 面板只能改**已有条目**的状态/结果，**不能手动新增**条目 | `悬浮球界面.vue:306-326`、`1114-1119` | "要改内容就作废旧条、另开新条"里的"另开新条"**只有 AI 能做**，玩家干等 |
| F8 | 卡上**本来就有**「当前目标」「心里惦记」两个字段 | `卡字段.ts:70-72` | 想给"持续性的事"找个家，不需要新字段、不需要新表 |

## 2. 现场数据（真实，一张卡）

剧情时间：**2025-10-18 07:25**（这张聊天用公历；提示词也支持虚构纪年，如 `0137-06-12`）

| 编号 | 写下 | 状态 | 内容 |
| --- | --- | --- | --- |
| T4 | 10-17 | 进行中 | 提醒哥哥 Lim 找出家里备用的两包彩纸装进幼儿园书包 |
| T6 | 10-17 | 进行中 | **洗完澡后**让哥哥 Lim 讲完绘本中未完的森林探险故事 |
| T7 | 10-17 | 进行中 | **明天**和哥哥 Lim 买彩纸时顺手买一盒草莓味软糖带去幼儿园分给小葵 |
| T8 | 10-17 | 进行中 | **明天**和哥哥 Lim 去文具超市时挑选一包带亮晶晶金粉的贴纸用来贴大象涂色卡 |
| T11 | 10-18 | 进行中 | 在客厅茶几上用天蓝色画笔将大象洗澡涂色卡的水池和底色涂好 |
| T10 | 10-17 | 已完成 | 早餐吃哥哥 Lim 煮的牛肉汤面 → 结果：已将整碗西红柿牛肉汤面吃完，并吃了一颗脆边荷包蛋，另一颗分给了 Lim |

### 2.1 账龄（写下日期 → 当前剧情时间）

T4 / T6 / T7 / T8 = **1 天**，T11 = **0 天**。**全部"新鲜"。**

### 2.2 T6 的结局（本稿的关键反例）

据用户确认：**澡已经洗完了**（"洗完澡后"那个时刻已经到达并过去了），而**昨晚讲的是小熊的故事**，不是那本未读完的森林探险。

→ **T6 事实上已经死了**（那个时刻的窗口关闭，且当晚发生的是另一件事），它应当被记为 `已作废（过期未兑现）`，但它现在还挂在 `进行中`。

**一个尚未确认、但会改变诊断权重的点**：这段"澡洗完了 / 讲的是小熊"是否落在更新 AI 读到的**最近 3 层**里？
- 若**在**：模型手里有反证却仍然没关它 → 病根是"规则 2 / 规则 10 压制 + 没人要求它考虑过期"，提示词必须显式授权。
- 若**不在**：模型没有材料 → 病根是"收束判断缺依据"。
两种情况的处方有重叠（都要"点名要求表态"），但**优先级不同**。

### 2.3 从这张卡读出的四件事

1. **账龄不含"死活"信息。** T6 与 T7/T8 同一天写下、同样 1 天账龄、同样没被正文碰过——但 T6 已死（而且它的时刻已经关闭），T7/T8 的"明天"**正好就是今天**，完全有效。**任何以天数或轮数为阈值的自动出清，都无法把 T6 与 T7/T8 分开。**
2. **开门率 > 关门率。** T4/T7/T8 其实是"10-18 出门采购 + 收拾去幼儿园的东西"这**一次出行**被拆成的三条；T8 与 T11 又是同一张涂色卡的**两步**（先涂底色、再贴金粉贴纸）。这张卡存在的两天里攒了 6 条、只关掉 1 条（T10）。
3. **8 条上限从未生效。** 现在 6 条，而封顶只在 **>8** 时动手；再加上"进行中永不淘汰"，条目数会穿过 8 继续长。
4. **`结果` 偏长是单次生成问题。** T10 的结果 35 字上下；按 F2/F3，它不会累积、注入时也只取最近 3 条——所以要治的只是"写太长"，不是"越堆越长"。

## 3. 已有的两份主张

### 3.1 主张甲（另一个 AI）

一句话：**"两件事被塞进了一个账本"**——把持续型事务（照顾生病的母亲、攒钱买房）从交易型台账里挪出去，放进"当前牵挂/长期目标"字段；台账只留离散、可兑账的承诺。在此前提下：

- **不单列第四态**（"已过期"），并入 `已作废`，原因写进 `结果` 自由文本。理由：枚举的唯一职责是"活着 / 已死"，对注入逻辑而言两者是同一个布尔值；状态越多、模型越容易选错。
- **裁决权**：选"**代码算客观量（轮次、筛候选）＋ 点名要求模型逐条表态**"。理由是现状（纯靠模型自觉）已被证明无效，纯代码阈值会误杀，每轮全量强制表态太贵。
- **兜底**：一次性条目"连续 ≥5 轮无实质变化"进候选池；"连续 ≥10 轮无变化且模型连续两轮都回继续"→ 代码自动作废为"过期"。
- **注入降级（它最好的点子）**：把"必须兑现"只留给"最近 N 轮有实质变化"的条目；久未推进的条目降级为"可选 / 背景说明"。这样即便漏网僵尸也不伤人。
- **`结果` 限长**：一条 ≤ 40 汉字、一句话收束。
- **提示词补丁**：规则 10（防全知：严禁以"本轮正文找不到证据"为由清洗旧记忆）需要一个例外说明——**"关闭一笔已死的承诺"是记账，不是清洗记忆**；"作废"要去污名化。

### 3.2 主张乙（工作区这一侧，也就是我）

一句话：**先降"开门率"，再逼"逐条表态"**；账龄类机制只能当安全网。

- **粒度规则（零代码）**：一次出行 / 一个场景里的多个子项合并成一条；同一步骤的后续不另开条；持续性的牵挂写进已有的「当前目标 / 心里惦记」，不开台账条目。
- **逐条表态（零代码 + 提示词）**：**不是只对"陈旧"候选表态，而是对全部 `进行中` 表态**——因为 §2.3-1 证明了"陈旧"不是可判定的候选条件（同龄、一死两活）。规模只有 5~8 条，且按 F5，状态没变的载荷本来就会被判"什么都没变"，所以**表态是零副作用的**。
- **注入降级**：同意主张甲，但有个形状限制——台账在注入侧是**压成单行的一个单元格**，末尾提醒是**整块共用一句**，所以降级只能做成**条目前缀标注**（如 `T6 进行中（久未推进，待确认）：…`），不能做成"分块 + 分句"，否则要动注入表结构。
- **兜底自动作废**：最后再上，阈值要高（它分不开 T6 与 T7）。
- **计数要不要进卡**：可以，但别先做（见 §3.4-3）。

### 3.3 双方一致的三点

1. **不单列第四态**（"已过期 / 已搁置"）。
2. **裁决权 = 代码算客观量 + 模型做语义裁决**（纯模型自觉 / 纯代码阈值 / 每轮全量逼问，三者都被否决）。
3. **注入降级是对的**：把僵尸的危害在注入端切断，能让"出清"这件事变得更保守、更安全。

### 3.4 分歧与纠正（逐题）

| 题 | 主张甲 | 主张乙 | 依据 |
| --- | --- | --- | --- |
| **A/B 分账** | 把持续型事务挪到"当前牵挂/长期目标"字段 | 方向同意，但**不需要新字段**（F8：卡上已有「当前目标」「心里惦记」）；而且**对这张卡不成立**——这 5 条没有一条是持续型，这张卡的病是粒度 | 现场数据 §2 |

## 4. 待你回答的问题

1. **同龄反例怎么破？** T6（绑定"洗完澡后"这个已关闭的时刻，已死）与 T7/T8（"明天"＝今天，有效）账龄完全相同。"连续 ≥5 轮无变化"这类候选条件筛不出 T6。那么：**为什么还要先按账龄筛一遍，而不是让模型对全部 `进行中` 逐条表态？**
2. **计数到底要不要存在卡里？** 若存，它必须穿过"每轮重建对象"（F1）；若不愿改数据结构，那就只能退回"写下日期 + 当前剧情时间"算天数——而 §2.3-1 说明天数不含死活信息。你要哪个？有没有第三条路？
3. **"什么都没返回"的那一轮算不算一轮账龄？** 算就动摇了"空回合原样不动"的既有契约（F5）；不算就漏掉模型整轮沉默的轮次。怎么选，为什么？
4. **粒度与冻结会不会打架？** 若要按主张乙把"一次出行的三条"合并成一条，那三个具体物品名（彩纸 / 草莓软糖 / 金粉贴纸）要怎么在一个条目里都保住、又不被后续轮次泛化？这与"内容写下即冻结"是同一件事的两面。
5. **自动作废的兜底还该不该存在？** 它分不开 T6 与 T7（同龄）。如果它只能当"极端情况安全网"，阈值定多少？谁来承担误杀"照顾生病的母亲"这类条目的代价（如果 A/B 分账没做干净）？
6. **"逐条表态"会不会反过来制造翻烙饼？**（这轮"继续"、下轮"作废"、再下轮又"继续"）如果会，用什么约束它？
7. **关门的责任能不能分一点给主 AI？** 注入降级之后，僵尸条目在正文层会呈现为"久未推进、待确认"；主 AI 若在正文里顺手把它做掉或明确丢掉，下一轮更新 AI 就拿到了证据。这条回路值不值得专门设计？

## 5. 主张乙的推荐顺序（按杠杆，含验收口径）

| 序 | 动作 | 改哪里 | 成本 | 验收口径（怎么算成功） |
| --- | --- | --- | --- | --- |
| 1 | **粒度规则**：一次出行/一个场景的子项合并成一条；持续性的牵挂进「当前目标/心里惦记」 | 只改提示词 | 零代码 | 新账条目数增速显著下降；对照这张卡，T4/T7/T8 应当是 1 条 |
| 2 | **逐条表态 + 规则 2/10 补丁**：对全部 `进行中` 回 `{编号, 状态}`（状态没变就回原状态）；明确"关闭一笔已死承诺 ≠ 清洗记忆" | 只改提示词 | 零代码 | T6 这类条目在一两轮内被关掉；台账不再单调增长 |
| 3 | **注入降级**：给久未推进的条目加前缀标注，把"必须兑现"留给新鲜的 | `渲染台账` + 提示词 | 小改（注意单行/整句共用的形状） | 主 AI 注入格里不再出现"已过期却写着必须兑现" |
| 4 | **兜底自动作废**：只对"被点名 N 轮仍无变化"的条目生效，阈值取高 | `事务台账.ts` + 计数 | 中（要动 F1） | 它是安全网，不是主力；上线后误杀数为 0 |
| 5 | **计数进卡**（可选项） | `事务台账.ts` 的保留逻辑 | 中 | 若 1~4 已把问题压住，则**不做** |
