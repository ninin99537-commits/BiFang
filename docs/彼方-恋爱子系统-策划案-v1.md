# 彼方 · 恋爱子系统 策划案 v10

> **交付对象**：开发 AI。
> **目标**：在「彼方_NPC幕后生命状态系统」里新增一个恋爱子系统；随后在数据库模板侧删除「恋爱对象表」。
> v9 = v8 + 独立验证收尾（见 §12 变更记录）。**代码侧已冻结**，剩余为模板侧与真机两项收尾。

---

## 0. 一句话

玩家在彼方的 NPC 状态卡上把某个 NPC 标记为**恋爱对象**（**标记即开关，没有全局设置开关**）。此后彼方每轮幕后更新时，用**同一份提示词、同一次请求**让模型报告本轮发生的**恋爱事件**，由**代码**折算成两条轴上的数值（**好感** / **情欲**），写回状态卡并注入给主 AI。

---

## 1. 领域词汇

| 词 | 定义 | 不要用 |
| --- | --- | --- |
| **恋爱对象** | 被玩家在彼方 NPC 状态卡上标记的 NPC。只有被标记的 NPC 进入恋爱子系统。 | 攻略对象、女主、恋爱目标 |
| **好感** | NPC **对主角**的情感倾向，单向。只受事件影响的**存量**（地基），不自然衰减。 | 好感度（旧数据库模板字段名） |
| **情欲** | NPC **对主角**的身体欲望，单向。会被满足而**回落的状态量**（潮汐）。 | 性欲（那是无对象的人格参数） |
| **名分** | 两个角色之间被"说定"的关系身份（恋人/未婚妻/炮友）。**事件驱动、必附原文依据**，不由数值派生。 | 关系阶段（那是数值派生的） |
| **恋爱事件** | 彼方每轮幕后更新时报告的、本轮实际发生的互动事实（轴/类型/强度/依据）。它回答"发生了什么"，不回答"涨了多少"——数值由代码折算。 | 好感变化、加分 |
| **情感倾向** | 角色的情感反应特质，一个枚举值，在代码里对应（敏感度, 粘性）两个系数。 | 性格、人设（那是世界书的） |

**核心原则**：**AI 只报事实，代码做判定。** 数值、阶段、地板、上限一律由代码产生；AI 不产生任何数字。

## 2. 数据模型

### 2.1 字段清单

**全部字段都存在 NPC 状态卡内部**（`彼方数据.NPC[名字]`），因此**持久化零改动**——NPC 对象整体 klona 进楼层快照（`快照.ts:306`）。不需要动 `快照.ts` 的 `buildSnapshotPayload` / `loadData` 白名单（那是给**顶层**字段用的）。

| 字段 | 存储形态 | 谁写 | 注册位置 | 说明 |
| --- | --- | --- | --- | --- |
| `恋爱对象` | 字符串 `"是"` / 空 | 玩家 | `字段表` + `扩展编辑字段` | 标记即开关。空值即删除（现有语义） |
| `情感倾向` | 枚举字符串 | 玩家 | `字段表` + `扩展编辑字段` | 默认 `常规`；**惰性补齐**（卡上没有就按常规算） |
| `好感值` | 数字字符串 `"56.3"` | **代码**（玩家可覆盖） | `字段表` + `扩展编辑字段` | 0–100，1 位小数 |
| `情欲值` | 数字字符串 `"42.0"` | **代码**（玩家可覆盖） | `字段表` + `扩展编辑字段` | 0–100，1 位小数 |
| `好感阶段` | 枚举字符串 | **代码**（玩家可覆盖） | `字段表` + `扩展编辑字段` | 见 §3.2 |
| `情欲阶段` | 枚举字符串 | **代码**（玩家可覆盖） | `字段表` + `扩展编辑字段` | 见 §3.2 |
| `名分` | 枚举字符串 | **代码**（AI 事件驱动） | `字段表` + `扩展编辑字段` | `无`/`恋人`/`未婚妻`/`炮友` |
| `恋爱动向` | 字符串 | **代码** | `字段表` + `扩展编辑字段` | 一行因果，见 §3.5 |
| `恋爱开局` | 字符串 `"是"` / 空 | **代码** | `字段表` + `扩展编辑字段` | **开局标记（v10）**：空时下一轮允许 AI 重报恋爱起点；清空即重新开局。见 §3.9 |
| `恋爱态度` | 字符串（一句话） | AI（增量） | **`CARD_FIELDS`** + `字段表` | 覆盖式的一句话，像 `当前状态` |
| `恋爱标签` | 逗号分隔字符串 | AI（增量）+ 玩家 | **`CARD_FIELDS`** + `字段表` | 见 §3.7；代码在合并后做词表归一化 |
| `恋爱基准日期` | 日期字符串 | **代码** | **隐藏**（不进字段表/扩展编辑字段/不注入） | 时间回落的锚点，见 §3.6 |
| `恋爱事件` | 数组（**临时**） | AI → 代码消费后删除 | **隐藏**（同 `受孕事件`） | **永不持久化** |

**关键取舍：所有可编辑字段都是字符串**（`恋爱标签` 用逗号分隔而不是数组）。这样 `合并草稿`（`数据变更.ts:65`，它只认字符串 + `未完成事项` 一个特例）、`mergeCard`、快照、UI 全部**零改动适配**。唯一的非字符串是临时的 `恋爱事件`。

### 2.2 字段注册位置（**v2 修正**）

**分三类**：

1. **AI 要写的字段必须进 `CARD_FIELDS`** —— 因为 `mergeCard`（`应用更新.ts:186`）只按 `CARD_FIELDS` 顺序做字符串合并。这类只有**两个**：`恋爱态度`、`恋爱标签`。
   - 推论：**没有 `CARD_FIELDS` 里的字段，AI 报什么都不会落库。** v1 把 `恋爱标签` 放在 `扩展编辑字段` 里是错的——`扩展编辑字段` 只服务**玩家手改**路径（`合并草稿`），AI 路径根本不看它。
   - `恋爱标签` 的词表归一化（过滤/去重/截断到 5）在**合并之后**由恋爱规则做，照 `怀孕知晓` 单向闸的位置（`应用更新.ts:352-368`）。

2. **代码写、玩家可覆盖的字段** → `字段表` + `扩展编辑字段`（`卡字段.ts:86`）：`恋爱对象`、`情感倾向`、`好感值`、`情欲值`、`好感阶段`、`情欲阶段`、`名分`、`恋爱动向`。
   - `扩展编辑字段` 的定义就是"由代码维护、玩家可手动覆盖"（`卡字段.ts:84-86`），正好。

3. **纯代码内部字段**（不进 `字段表`、不进 `扩展编辑字段`、不注入）：`恋爱基准日期`、`恋爱事件`。先例：`周期长度`、`受孕事件`、`哺乳期开始日期`。

**必须新增 `恋爱字段` 常量**并在 `模型请求.ts:21` 的 REQUIRED 过滤里排除它——否则 `CARD_FIELDS` 里的 `恋爱态度`/`恋爱标签` 会变成"新建 NPC 必填"，而没被标记的 NPC 不该有恋爱字段。写法照现成的 `PHYSIO_FIELDS`：

```ts
// 模型请求.ts:21 现状
const REQUIRED_CARD_FIELDS = CARD_FIELDS.filter(field =>
    !PHYSIO_FIELDS.includes(field) && !NON_STRING_CARD_FIELDS.includes(field));
// 改为
const REQUIRED_CARD_FIELDS = CARD_FIELDS.filter(field =>
    !PHYSIO_FIELDS.includes(field)
    && !恋爱字段.includes(field)
    && !NON_STRING_CARD_FIELDS.includes(field));
```

⚠️ **`字段分组表` 的初始化器写死了三个键**（`卡字段.ts:88`）：`{ 生活: [], 内心: [], 生理: [] }`。只改联合类型不加 `恋爱: []`，模块加载时 `字段分组表[字段.组].push(...)` 会直接 **TypeError**。

⚠️ **`字段分组` 联合类型**（`卡字段.ts:41`）是**封闭的** `'核心' | '生活' | '内心' | '生理'`，要加 `'恋爱'`。

## 3. 规则（新建 `恋爱规则.ts`）

**纯函数、不依赖酒馆平台**，照 `生理规则.ts` 的模式（常量 + if/else 阈值，不做数据驱动 DSL）。常量与提示词中文说明**并排维护、双份对照**（照 `生理规则.ts:2-3` 的自陈）。

### 3.1 两条轴

| 轴 | 性质 | 是否自然衰减 | 量程 |
| --- | --- | --- | --- |
| 好感 | 存量（地基） | **否**（只受事件影响） | 0–100，1 位小数 |
| 情欲 | 状态量（潮汐） | **是**（时间 + 满足两条回落通道） | 0–100，1 位小数 |

### 3.2 阶段表与滞回

**好感阶段**（0–100）

| 阶段 | 区间 |
| --- | --- |
| 陌生 | 0 – 15 |
| 认识 | 16 – 30 |
| 熟悉 | 31 – 50 |
| 朋友 | 51 – 70 |
| 暧昧 | 71 – 85 |
| 恋人 | 86 – 95 |
| 挚爱 | 96 – 100 |

**情欲阶段**（0–100，直白命名）

| 阶段 | 区间 |
| --- | --- |
| 无感 | 0 – 20 |
| 有性趣 | 21 – 45 |
| 想要 | 46 – 75 |
| 饥渴 | 76 – 100 |

**滞回规则**：保持当前阶段，除非数值**越过当前档边界 2 点以上**。
- 升档：`值 ≥ 当前档上界 + 2`
- 降档：`值 ≤ 当前档下界 − 2`

例：当前 `暧昧`(71–85)，值升到 87 才变 `恋人`；当前 `恋人`(86–95)，值降到 84 才退回 `暧昧`。

**两条补充规则（v2）**：
- **每轮重算**，不是只在有事件时才算。这样玩家手改 `好感值` 后阶段会自动跟上（手改的 `好感阶段` 只要还在滞回区间内就被尊重）。
- **跨档直接落到数值所属的档，可以跳档**，不逐级爬升。滞回的作用是防抖，不是限速。

### 3.3 情感倾向（一个枚举，两个系数）

| 情感倾向 | 敏感度 | 粘性 | 读作 |
| --- | --- | --- | --- |
| 内敛 | 0.7 | 0.9 | 心里翻江倒海，表面没事 |
| 常规 | 1.0 | 1.0 | 默认 |
| 外放 | 1.4 | 1.0 | 一点小事就高兴/炸毛 |
| 慢热 | 0.6 | 0.6 | 很难捂热，热了就很难凉 |
| **病娇** | **1.6** | **0.2** | 一碰就烧，而且几乎不回落 |

**两条轴各有自己的放大器（v4 定稿——此前 §3.3 与 §3.5 的公式互相矛盾，以本表为准）**：

| 事件 | 乘什么 |
| --- | --- |
| 好感涨 / 好感落 | × 敏感度 |
| 情欲涨 | × 敏感度 |
| **情欲落（满足回落 + 时间回落）** | **× 粘性，不乘敏感度** |

- ⚠️ 粘性**不作用于好感**——病娇被背叛时好感要暴跌（× 1.6），不是只掉一点。
- ⚠️ 敏感度**不作用于情欲的回落**——否则"外放"（1.4）会变成"性爱之后冷却得更快"，语义正好反了。
- 例：病娇的「性行为(大)」= −35 × 0.2 = **−7**（不是 −11.2）。

### 3.4 事件表

**AI 报的事件形态**（`恋爱事件` 数组的每一项）：

```json
{ "轴": "好感", "类型": "交心", "强度": "中", "依据": "她第一次说起母亲的事" }
{ "轴": "名分", "类型": "确认关系", "依据": "她点头说'那我们试试吧'" }
```

- `轴` ∈ `好感 | 情欲 | 名分`
- `强度` ∈ `微 | 小 | 中 | 大`（名分事件不需要强度）
- `依据` 必填，必须是正文里真实发生的（原文里的一句话）。**强制程度分两档（v7）**：
  - **名分事件：硬性。** `依据` 缺失或全空白 → **整条事件被拒绝**（名分不变、不写动向）+ `console.warn`。理由：名分是"说定的事实"，凭空变更会破坏叙事一致性，且玩家一眼能看出。
  - **数值事件：软性。** `依据` 缺失 → 仍计算，但 `console.warn`。理由：数值是渐变量，依据缺失的风险低；而全丢弃会导致恋爱数值完全不涨，代价过高。
  - ⚠️ 实现上**不许用类型名兜底依据**（例：`依据 || 类型`）——那等于没有校验。
  - `依据` **非字符串**时（`123` / `true` / `{}`）经 `String()` 强转后非空即通过，`[]` 被拒。**判为接受（v9）**：契约规定 `依据` 是字符串，非字符串输入本身即契约违反；最坏结果只是名分变更附了一条无意义的依据文本，而名分**类型**合法性仍单独校验。为这一极低概率输入再加一轮改动 + 复验不划算。若真实日志里观察到，再收紧。

**事件类型的规范名（v2）**：代码持有**规范名**，提示词只教规范名，下表里的另一种写法只作**兼容别名**。

| 规范名 | 兼容别名 |
| --- | --- |
| 自慰 | 独自解决 |
| 分手 | 决裂 |

**强度 → 基础值**

| 强度 | 好感 | 情欲 |
| --- | --- | --- |
| 微 | 0.5 | 1 |
| 小 | 1.5 | 3 |
| 中 | 3 | 6 |
| 大 | 6 | 12 |

**好感事件**

| 方向 | 类型 |
| --- | --- |
| 涨 | 陪伴同行 · 交心 · 礼物帮助 · 肢体亲近 · 共患难 |
| 落 | 冷落爽约 · 言语伤人 · 失信欺骗 · 越界（强迫/背叛/当众羞辱） |

**情欲事件**

| 方向 | 类型 | 微 | 小 | 中 | 大 |
| --- | --- | --- | --- | --- | --- |
| 涨 | 调情挑逗 / 肢体亲密 / 情欲未遂 | 1 | 3 | 6 | 12 |
| 落 | 性行为 | −15 | −22 | −28 | −35 |
| 落 | 自慰 | −5 | −8 | −12 | −18 |
| 落 | 冷静收场（被打断/争吵/尴尬收尾） | −5 | −10 | −15 | −20 |

**名分事件**

| 类型 | 变更 |
| --- | --- |
| 确认关系 | `名分 = 恋人` |
| 婚约 | `名分 = 未婚妻` |
| 无恋爱的性关系 | `名分 = 炮友` |
| 分手 | `名分 = 无` |

（`青梅竹马` / `主仆` / `单恋` 属于关系底色，**不由事件驱动**，走 `恋爱标签` 或玩家手动设置。）

### 3.5 数值流水线（**v2 修正**）

**挂载点（v3 定稿）**：一整块自包含代码，放在 `mergeCard` **末尾**、`merged['最后更新'] = Date.now()` 之前（即 `:439` 生理周期日期块之后）。**不**拆成三个插入点。整块必须**原子**（要么全跑，要么完全不跑），且在 `mergeCard` 的 return 之前。

**闸的位置（v3 定稿）**：整块以 `merged['恋爱对象'] === '是'` 为闸，闸必须在**"复制 `恋爱事件` 入卡"之前**——未标记时连复制都不做，只 `console.warn` 一句。
⚠️ 若先复制入卡再靠闸跳过，未标记 NPC 的 `恋爱事件` 会永久留在卡上（它不在 `CARD_FIELDS` 里，`mergeCard` 的字符串循环不管它，没有任何路径会删它），随每份快照一路膨胀。

对**每个被标记的恋爱对象**，每轮更新时：

```
1. 把本轮 AI 报的 `恋爱事件` cloneDeep 进卡，照 `受孕事件` 的做法（应用更新.ts:241-248）
   —— **仅当已标记**；未标记时连复制都不做（见上方闸的说明）
2. 惰性补齐：卡上没有 `情感倾向` → 按 `常规`；没有 `恋爱基准日期` → 按本轮剧情日期（首次不回落）
3. 逐条事件：
     轴 = 名分 → 走独立的 `应用名分事件`
     否则     → `折算事件(事件, 情感倾向枚举名) → { 轴, 方向, 变化量 }`
                  基础 = 强度表[轴][强度]
                  好感涨 / 好感落 / 情欲涨 → 基础 × 敏感度
                  情欲落（满足回落）        → 基础 × 粘性
                  // 见 §3.3 的放大器表
4. 时间回落（仅情欲）：跨天数 = max(0, dateOnlyTs(本轮剧情日期) − dateOnlyTs(恋爱基准日期))
                      情欲 −= 跨天数 × 2 × 粘性
5. **按方向分桶，不先净额相抵（v5 修正；v6 澄清：两条轴都要分桶）**：
     涨桶 = Σ(该轴涨事件变化量)
     落桶 = Σ(该轴落事件变化量) + 时间回落量（仅情欲有时间回落）
     ⚠️ **好感轴同样必须分桶**——只给情欲分桶是同一个漏洞的另一半：好感一轮报 +6+6 与 −3，
        净额 +9 会被夹成 +8（结果 58）；分桶则是 +12 先夹到 +8 再相抵 −3（结果 55）。
6. **只夹涨桶**：`涨桶' = min(涨桶, 单轮上限)`（好感 +8 / 情欲 +20）；落桶不设上限
7. `涨后 = clamp(当前值 + 涨桶', 0, 100)`
8. 情欲：`实际落 = min(|落桶|, max(0, 涨后 − 地板))` → `新值 = 涨后 − 实际落`
   好感：无地板截断 → `新值 = 涨后 + 落桶`
9. 夹到 0–100
10. 重算阶段（±2 滞回，可跳档）
11. 写 `恋爱动向`（**本轮有实际变化才写**，否则保留原值）；更新 `恋爱基准日期` 为本轮剧情日期
12. **`delete 恋爱事件`**（消费掉，永不落盘）
```

**单轮上限只作用于涨方向（v2 修正）**：v1 写的是"累加之后夹 ±8/±20"，这会让 §3.4 的满足回落表**形同虚设**——`性行为 大 = −35`、`中 = −28`、`小 = −22` 三档全被夹成 −20，"贤者时间"根本表达不出来。而且上限的动机本来就是**防 AI 讨好玩家刷高数值**，落方向没有这个动机。所以：**净变化为正时夹上限，为负时不夹**（仍夹 0–100 与地板）。

**`恋爱动向` 的格式**：

```
好感+3(交心) / 情欲−7(性行为) / 情欲−4(时间回落3天) · 2026-08-18
名分→恋人(她说"那我们试试吧") · 2026-08-18
```

- 用**剧情日期**，不用楼层号（v2 拍板，见 §12）。理由：楼层号会因删楼/重 roll 失效，剧情日期不会；且 `storyTimeText` 已在 `mergeCard` 作用域内，**零签名改动**。
- **记实际值，不记名义值（v5 定稿）**：若一次 `冷静收场` 名义上是 −20，但被地板截断成实际只掉 5，动向记 `情欲−5(冷静收场)` 而不是 `−20`。理由：动向回答的是"这个数字为什么是这个值"，记名义值会让玩家对不上账。
- **时间回落也要记成因**（`时间回落N天`），否则玩家会看到情欲莫名下降。
- **名分变更记 `名分→X` 并附依据原文**，这是 Q19 可审计性的落地。
- **没有实际变化的轴不写**；本轮所有轴实际变化都为 0 时，`恋爱动向` **保持原值不动**（日期即"上次变化是什么时候"，别清空）。
- 变化量内部保留 **2 位小数**（v4），避免浮点尾数（如 `0.30000000000000004`）。

### 3.6 情欲的回落与地板

**基准日期（v2 新增）**：卡内隐藏字段 `恋爱基准日期`，存**上一轮结算时的剧情日期**（取 `剧情时间` 的**结束**时刻的日历日）。
- 先例：`生理周期日期`、`哺乳期开始日期`——纯代码字段，不进 `字段表`、不进 `扩展编辑字段`、不注入。
- 每轮结算后更新为本轮剧情日期；本轮 `剧情时间` 缺失或非法时，**跳过时间回落且不更新基准日期**（"没有依据就不动手"，照 `生理规则.ts:313-323`）。

**跨天数**：`max(0, dateOnlyTs(本轮剧情日期) − dateOnlyTs(恋爱基准日期))`，用现成的天级原语 `dateOnlyTs`（`剧情时间.ts:9`），照 `correctPhysioByStoryTime`（`生理规则.ts:212`）的算法——**同一日历日不变、跨午夜 +1 天、跳 N 天 +N**，基准倒退时压成 0。

**时间回落量**：`跨天数 × 2 × 粘性`。

**情欲地板**（按**结算后**的好感阶段决定）：

| 好感阶段 | 情欲地板 |
| --- | --- |
| 陌生 / 认识 | 0 |
| 熟悉 | 10 |
| 朋友 | 15 |
| 暧昧 | 30 |
| 恋人 | 45 |
| 挚爱 | 60 |

**地板只截断回落，不抬升（v4 定稿）**：

```
实际回落量 = min(原回落量, max(0, 当前情欲值 − 地板))
```

- 地板是"**冷却后的稳态**"，不是磁铁。情欲低于地板时回落不生效（没有余温可保），但**也不会被拉到地板上**。
- **为什么必须这样**：若地板抬升，好感一到"恋人"情欲就会被凭空抬到 45，而且**每轮无事件也会自己涨**——这会无声覆盖玩家手改的情欲值，与 §10 验收标准"手改后不覆盖"直接冲突；而且"深爱但清心寡欲"的角色将无法存在。
- 地板表达"**越爱越想要**"：冷静下来也留有余温。病娇因粘性 0.2，实际几乎不会触到地板。
- 用**结算后**的好感阶段：刚确定关系的那一夜之后，冷却的余温就已经按新关系算了。

**好感没有回落通道**（不衰减）。

### 3.7 名分与标签

**`名分`**（单选）：`无` / `恋人` / `未婚妻` / `炮友`。事件驱动、必附依据（§3.4）。

**`恋爱标签`**（多选，逗号分隔字符串，上限 5）——闭合词表：

| 分类 | 词 |
| --- | --- |
| 关系底色 | 青梅竹马 · 主仆 · 单恋 |
| 情感 | 冷战 · 心结 · 猜忌 · 占有欲 · 依赖 · 口是心非 |
| 负面 | 敌意 · 恐惧 · 厌恶 |

- **AI 只能从词表里选**，词表外的词**丢弃**（防止 AI 每轮发明新词把注入文本撑爆）。
- `恋爱标签` 进 `CARD_FIELDS`（这样 AI 报的值才会被 `mergeCard` 合并），归一化在**合并之后**做：按词表过滤 → 去重 → 截断到 5 个。
- **玩家手改路径同样要归一化（v7）**：`合并草稿`（`数据变更.ts:65`）写入 `恋爱标签` 时也要调 `校验标签`。否则玩家能从详情页塞进词表外的词甚至数字并注入主 AI，"闭合词表"这个前提就废了。
- **归一化后为空时的语义，按路径区分（v8 修正）**：
  - **AI 路径**：`mergeCard` 的字符串循环对空串**一律跳过**（全仓所有字段都这样，"没返回 / 空 = 沿用旧值"），所以 AI 报 `恋爱标签: ""` **不会**清空标签。AI 想删标签就报**剩下的那些**——但因此 AI 无法把所有标签清空。这与全仓行为一致，**不为这个字段开先例**。
  - **玩家路径**：清空输入框 → `空值即删除` → 删字段。真正能"明确清空"的是这条路。
  - **原始非空但归一化后为空（全是非法词）→ 保留旧值**，不删。否则 AI 报错一个词就会连带清掉旧标签，那是数据丢失而不是"清空"。
- 要加词就改代码常量——这是**刻意的摩擦**，防止词表长成第二个自由文本字段。

### 3.8 常量与导出契约（**v2 修正**）

```
好感阶段表 / 情欲阶段表 / 阶段滞回 = 2
情感倾向表（敏感度, 粘性）
强度表[好感][强度]、强度表[情欲][强度]
情欲落事件表[类型][强度]
单轮上限：好感 8 / 情欲 20（只作用于涨方向）

```

**建议导出签名**：

| 导出 | 签名 | 职责 |
| --- | --- | --- |
| `推算阶段` | `(轴, 值, 当前阶段?) → 阶段` | 带 ±2 滞回，可跳档 |
| `折算事件` | `(事件, 情感倾向枚举名) → { 轴, 变化量 } \| null` | **只处理数值事件**（好感/情欲）；名分事件返回 null |
| `应用名分事件` | `(卡, 事件) → 名分` | 独立函数，只管名分 |
| `校验标签` | `(字符串) → 字符串` | 词表过滤 + 去重 + 截断到 5 |
| `应用恋爱回合` | `(卡, 事件[], storyTimeText) → 新卡字段` | 整个 §3.5 流水线；**自己读写 `恋爱基准日期`** |

- `折算事件` 收**枚举名字符串**（如 `'病娇'`），不收系数对——系数表由规则模块持有。
- `应用恋爱回合` **不收跨天数参数**（v1 的签名不自洽：调用方没有数据来源）。它自己从卡上的 `恋爱基准日期` 和 `storyTimeText` 算——这正是 `correctPhysioByStoryTime(merged, oldCard, storyTimeText)` 的既有形态。
- `应用恋爱回合` **不收楼层号**；`恋爱动向` 用剧情日期。

**与提示词的对照**：以上每个常量在 `prompts.ts` 的中文说明里都要有对应表述，两份**并排维护**（照 `生理规则.ts:2-3` 的既有约定）。

### 3.9 冷启动：开局（**v10 新增**）

**问题**（v9 遗漏）：`应用恋爱回合` 对 `情感倾向`（`:194-196`）、`名分`（`:197-198`）、`恋爱基准日期`（`:288-290`）都做了惰性补齐，**唯独 `好感值` / `情欲值` 没有**——它们被 `取数值`（`:82-85`）默认成 0。于是：

- 人设里写着「青梅竹马」「未婚妻」「已在一起多年」的 NPC，标记后第一轮结算出来是 **`好感 0 / 陌生`**。
- **模型没有任何表达通道**：`prompts.ts:34` 明令「绝对不要输出任何数字」；`:30` 又要求恋爱事件只报**【最新回复正文】**里真实发生的互动——既成关系不是本轮正文，报不出来。
- **自己也涨不上去**：`单轮上限 好感 +8`（`:75`）——从 0 爬到恋人档 86 **至少 11 轮**。
- **两处连带**：情欲地板按**结算后好感阶段**取（`:298`），好感是陌生 → 地板 0 → 情欲一起冷启动；而 `青梅竹马` 就在标签词表里（`:71`），模型可以写这个标签、写「已经在一起两年」的态度，数值却是 0——**卡自己打自己**。
- **名分同样补不了**：名分事件缺依据整条拒绝（`:232-235`），而人设里的既成关系没有"正文依据"。

**规则**：把「起点」当作**第五样惰性补齐**。补齐来源只能是模型——只有它读得到人设（`prompts.ts:238`：每张卡附一个「人设参考」字段）。

#### 1. 触发窗口

开局只在下面**两条同时成立**时被接受：

| 条件 | 含义 |
| --- | --- |
| `卡['恋爱开局']` ≠ `是` | 这个 NPC 还没开过局 |
| `卡['恋爱动向']` 为空 | 还没有任何一轮结算出过变化 |

第二条是**防迟到乱开**：已经跑了几十轮、动向有记录的 NPC，不会被一个错报的开局直接跳到恋人档。反过来，一个刚被标记、但正文里早已相处很久的 NPC，窗口仍然开着——这正是要修的 case。

#### 2. 模型报什么（复用 `恋爱事件` 数组，新增一个 `轴` 取值）

`轴` 从 `好感 | 情欲 | 名分` 扩到 **`好感 | 情欲 | 名分 | 开局`**。开局元素自带三个数据键：

```json
{ "轴": "开局", "好感": "恋人", "情欲": "有性趣", "名分": "未婚妻", "依据": "人设：两人是青梅竹马，已订婚" }
```

| 键 | 取值 | 可省 |
| --- | --- | --- |
| `好感` | 好感阶段名（陌生/认识/熟悉/朋友/暧昧/恋人/挚爱） | 是 |
| `情欲` | 情欲阶段名（无感/有性趣/想要/饥渴） | 是 |
| `名分` | 名分词表（无/恋人/未婚妻/炮友） | 是 |
| `依据` | 字符串，**必填** | 否 |

**仍然是「只报事实，不报数字」**：模型给的是**阶段名**（领域词汇，§4.2 注入给主 AI 的本来就是它），数值由代码产生。§8 的「不让 AI 产生任何数字」不变。

**为什么不做成独立的临时字段**：独立字段要在 `数据变更.ts` / `应用更新.ts` / `快照.ts` / `模型请求.ts` 各开一个口（照 `恋爱事件` 那四处），而开局只需要数组里一个元素的位置。代价是 `轴` 多一个取值——小得多。

**为什么依据可以来自人设而不是正文**：名分事件的依据硬性要求正文（§3.4 v7），是因为名分是「两人说定了什么」，只有正文能证明。开局是**回溯已有状态**，人设本身就是权威来源——它不需要正文「发生」过。

#### 3. 阶段 → 数值：取档下界

| 好感 | 陌生 | 认识 | 熟悉 | 朋友 | 暧昧 | 恋人 | 挚爱 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 值 | 0 | 16 | 31 | 51 | 71 | 86 | 96 |

| 情欲 | 无感 | 有性趣 | 想要 | 饥渴 |
| --- | --- | --- | --- | --- |
| 值 | 0 | 21 | 46 | 76 |

**取档下界，不取档中点**。理由：① 保守——「刚进这一档」，之后靠事件自然往上走；② 不与 §3.2 的 ±2 滞回打架（档中点 90.5 离恋人档上界 95 只差 4.5，一次 `+6` 就顶到滞回线）。

#### 4. 在流水线里的位置（§3.5 第 2 步）

开局**先于事件折算**，只填「卡上没有」的字段，**绝不覆盖已有值**（玩家手改优先）：

```
旧好感 = 卡['好感值'] 非空 ? 取数值(卡['好感值']) : 开局映射(好感) ?? 0
旧情欲 = 卡['情欲值'] 非空 ? 取数值(卡['情欲值']) : 开局映射(情欲) ?? 0
名分   = 卡['名分']   非空 ? 卡['名分']          : 开局的名分 ?? '无'
```

之后照 §3.5 原样跑：事件折算 → 分桶 → 只夹涨桶 → 时间回落 → 地板 → 重算阶段。

- **开局不吃 `单轮上限`**：它是基线不是增量。同轮既有开局又有事件时，先落基线再应用事件。
- **名分事件压过开局**：同轮既报了开局名分又报了名分事件时，以名分事件为准（它来自正文，更权威）。
- 开局**不影响** `恋爱基准日期` 的落法：首轮照旧落基准、本轮不回落。

#### 4.5 空轮不落库（**v10 裁决 · 必须实现**）

⚠️ 没有这一条，第 5 条的「漏报不锁死」**是假的**。这是 v10 初稿的自相矛盾，开发侧实测确认（`恋爱规则.ts:359-362` 四条补丁无条件写）。

**问题**：`应用恋爱回合` 每轮都把两条轴的值与阶段无条件写进补丁。于是模型漏报开局的那一轮，卡上照样出现 `好感值 = '0'`。下一轮开局虽然被接受（触发窗口还开着），但第 4 条的缺省判据是「卡上该字段为空」——已经不空了，86 填不进去；而 `恋爱开局 = '是'` 照写，窗口就此关死。**冷启动永久丢失，且比不修更糟**（多了一个骗人的标记）。

**规则**：给「数值状态类字段」的补丁加一道**有值才写**的闸。

```
该轴有值 = 卡上该字段非空(trim)  ||  本轮开局填了该轴  ||  本轮该轴有事件
```

| 字段 | 写补丁的条件 |
| --- | --- |
| `好感值` / `好感阶段` | `好感` 有值（阶段跟随值，两者同进同出） |
| `情欲值` / `情欲阶段` | `情欲` 有值 |
| `名分` | 本轮开局填了名分 **或** 本轮有名分事件（**不含**「卡上已有名分」，见下） |
| `情感倾向` / `恋爱基准日期` | **不受影响**，照旧无条件惰性补齐（它们是配置与锚点，不是数值状态） |

**为什么按轴分别判，而不是「本轮无事就全不写」**：后者会让「手改 `好感值` 后阶段自动跟上」（§10）失效——那一轮若正好没有事件，阶段就不会重算。按轴判里的 `卡上该字段非空` 那一项正好兜住它。

**为什么 `名分` 的闸不含「卡上已有名分」（v10 收紧）**：`好感` 那条「卡上非空 → 写」是**承重**的（阶段必须跟值同进同出）；`名分` 没有伴生字段，卡上已有名分时把同一个值写回去是**空转**——对最终卡片零影响（`mergeCard` 遇到同值等于没变），却会把「名分事件被拒 ⇒ 补丁不带 `名分`」这条强断言削弱成「值没被改」。收紧成 `名分变化 !== null 或 开局?.名分 !== undefined` 后语义相同、断言更硬。

**顺带修好的旧毛病**：玩家清空 `名分` 后，v9 会在下一轮无条件补回 `'无'`（`名分未落` 为真）；现在闸拦住了，**清空就是清空**。

**为什么不用「把缺省判据放宽成 `取数值 === 0`」**：两行就能让漏报兜底跑通，但玩家手改 `好感值 = 0`（且从未有过动向）时会被开局覆盖，破「绝不覆盖」。这是本裁决拒绝的替代方案。

**已知边角（不修）**：玩家只清 `好感值`、留着 `好感阶段`（如 `暧昧`）→ 下一轮无事件时两个字段都不写，卡上停在「值空 + 阶段暧昧」。要"修"就得让阶段按 0 重算成 `陌生`，那反而是拿派生值覆盖玩家留下的输入，比现状更糟。**保守不动**：注入照常用玩家留下的阶段；下一轮一旦有事件，值从 0 起算、阶段随之重算。

**代价（已知并接受）**：标记后、第一次产生数据之前，详情页两条轴显示为**空**而不是 `0 / 陌生`。这比显示一个错的默认值更诚实——冷启动 bug 的本质就是「凭空断言 0」。同理，注入里那两列在该 NPC 上显示 `—`（列本身在全员皆空时会被动态列集整个丢掉）。

**顺带收益**：「已知为 0」与「还不知道」在卡上从此可区分；`应用恋爱回合` 不再凭空造出一个没有依据的完整状态。

#### 5. 落库与留痕

- 应用了开局 → 写 `恋爱开局 = 是`（§2.1 的持久标记）
- **同时写进 `恋爱动向`**，用「开局」字样与增量区分，让玩家一眼看见并核对：

```
好感开局 86(人设：青梅竹马，已订婚) / 情欲开局 21(人设：…) · 2026-08-18
```

- **没报开局 → 不写标记、不写动向**，窗口保持开着，下一轮还能开。这一条防的是「AI 首轮漏报 → 冷启动永远丢失」——但**它只在第 4.5 条同时落地时才成立**：否则那一轮卡上已被写上 `好感值 = '0'`，第 4 条的缺省闸失效，86 永远填不进去。两处必须一起改，只改一处等于加了个骗人的标记。
- 开局行**与增量行可以同时存在**（同一轮里先落基线、再应用事件）。
- 开局的名分行**即使随后被同轮的名分事件压过，也保留在 `恋爱动向` 里**（v10 裁决）：玩家能看到「开局说未婚妻 → 正文里分手了 → 最终无」整条链路，比只留结论有用。

#### 6. `恋爱开局` 字段归属

| 项 | 值 |
| --- | --- |
| 谁写 | **代码**（`应用恋爱回合`）；AI 不写这个键 |
| 类型 | 字符串 `'是'` / 空 |
| 进 `CARD_FIELDS` | **否**（AI 不写它） |
| 进 `字段表` | 是，组 `'恋爱'` |
| 进 `扩展编辑字段` | **是**——这是玩家唯一的重开入口（清空即重新开局） |
| 进 `NON_STRING_CARD_FIELDS` | 否（它是普通字符串） |
| 快照 | 随卡整体保留（普通字符串字段，无 delete） |

#### 7. 硬红线不变

## 4. 模型契约（`prompts.ts`）

### 4.1 要求 AI 报什么

**触发条件**：本轮输入里存在**已标记的恋爱对象**（`恋爱对象 === "是"`）。**没有标记 → 整段恋爱说明不出现**（这就是"标记即开关"的落地方式；不标记 = 零成本）。

说明段照 `生理监测` 的条件段写法（`prompts.ts:149-193`），**只做 userContent 尾部追加**（`${noNewNpcInstruction}${physioInstruction}${恋爱段}`），`system` 主体零改动。要点：

1. 只有标记为恋爱对象的 NPC 才报 `恋爱事件`，其他 NPC 不报。
2. `恋爱事件` 只报**本轮正文里真实发生**的互动，**必须附 `依据`**（原文里的一句话）。
3. **绝对不要输出任何数字**——不报好感值、不报情欲值、不报增减量。数值由代码算。
4. 事件类型、强度档、名分词表、标签词表**全量列出**（AI 只能从中选）。
5. 名分变更**必须**走 `名分事件` + 依据，不许直接改字段。
6. `恋爱标签`：**沿用旧标签**，只在正文明确改变时才增删；总长 ≤ 5。
7. `恋爱态度`：一句话，写**外在可观察的倾向**，不写内心独白（正例："嘴上说不在乎，但你一走开就盯着门口"）；没变化就不返回。
8. **不许重报**：上一轮已经报过的事，这轮不许再报（v2；见 §8 已知取舍）。
9. 防全知同样适用：NPC 不知道正文里她没参与的事。

### 4.2 注入给主 AI 什么

**不注入裸数值。** 注入"关系语义"，让它能演，但不能把数值当 KPI 刷。

位置：**并入现有的那条常驻世界书条目** `【彼方】NPC幕后生活`（`彼方条目.ts:15`），由 `buildInjectionPrompt`（`prompts.ts:279`）生成。

**格式（v10 改成竖线表）**：**一次表头 + 每行一个 NPC**，与烟火同款（先例：`世界字段表.ts:329-337` 的 `注入表头` / `注入行`）。列集**动态**——只保留"本次注入的 NPC 里至少有一个非空"的列，无值的格子填 `—`：

```
名字 | 锚点 | 当前在做 | 关键事件 | 位置 | 生理周期 | 好感 | 情欲 | 名分 | 标签 | 恋爱态度
爱丽丝 | 35岁急诊科护士 | 值夜班 | 和你聊过母亲的事 | 医院 | 黄体期 Day 12/28 | 暧昧 | 想要 | 恋人 | 冷战,占有欲 | 她嘴上说不在乎, 但你一走开就盯着门口
鲍勃 | 退伍老兵 | 擦枪 | — | 营地 | — | — | — | — | — | —
```

- 恋爱五列（`好感`/`情欲`/`名分`/`标签`/`恋爱态度`）**只在被标记的 NPC 那一格有值**，其余填 `—`；**一个标记都没有时这五列整个不出现**——未标记的 NPC 注入里一个"恋爱"字样都没有（`prompt-shape.test.ts` 的 [12] 块钉住）。
- **为什么不照抄烟火的固定列集**：烟火的层是**同构**的（每层固定小列集，每条档案都有全部列），所以 `—` 几乎不出现；彼方的卡是**异构**的（19 个候选字段里每个 NPC 只占一部分：生理列仅非男性且生理监测开着、恋爱列仅被标记的），固定列集会在"生理监测关掉、只标记了一个人"的聊天里产出大半张 `—` 的表，**比旧写法还费 token**。
- **为什么换掉原来的"标签: 值"写法**：`- 名字 | 锚点: … | 关键事件: … | 未完成事项: … | 周期影响: … | 防护: … | 性行为: …` 把标签按 NPC 重抄一遍，N 个 NPC 就重复 N 遍；表头只写一次。顺带修掉了旧写法的一个毛病——`当前在做`/`生活状态`/`当前状态`/`位置`/`生理周期` 五个字段当时**连标签都没有**，只能靠位置猜。
- ⚠️ **`未完成事项` 那一格必须压成单行**：`渲染台账`（`事务台账.ts:353`）用 `\n` 分行，直接塞进单元格会把这条数据行撕成两行。`prompts.ts` 里做 `.replace(/\n/g, '; ')`（半角 `; ` 与台账内部的全角 `；` 区分开）。
- 改的是 `buildInjectionPrompt`（世界书条目内容），**不是** `buildUpdateMessages`（幕后更新提示词）——所以「未标记 = 逐字节不变」那条硬红线**不受影响**，不用重跑 192 组。

**为什么不新建条目**：
- 现有条目是**蓝灯常驻、禁递归、`after_character_definition`**，直接复用。
- 条目名要避开 ACU 屏蔽词（`状态/规则/变量/叙事/文风/判断/检定…`，见 `彼方条目.ts:17`），新建条目就多一个踩雷点。
- 只有一条汇总条目，注入侧没有按 NPC 条件化的能力（`worldbook-inject.ts:31`），并进去最省事。

**"态度"从哪里来**：`恋爱态度` 字段。`彼方` 现有的 `秘密想法` / `隐藏目标` 是**刻意不注入**主 AI 的（`prompts.ts:258-300` 里没有它们），所以恋爱语义需要自己的载体。

**风险与保险（v3）**：`恋爱态度` 有被主 AI 当旁白复述的风险，等级与已在注入的 `当前状态`/`周期影响` 同类（远低于被刻意排除的 `秘密想法`——那是内心独白，复述即泄底；`恋爱态度` 本来就是给外在行为上色的）。两道保险：
1. **生成侧**：§4.1 第 7 条要求更新 AI 只写外在可观察的倾向。
2. **一行 kill switch**：真机若仍在复述，从 `buildInjectionPrompt` 摘掉态度段即可；字段仍在卡上、详情页照常可见，**零数据损失**。

### 4.3 开局（**v10 新增**）

在 `恋爱说明段` 里追加一段（仍在 `恋爱对象名单.length === 0` 就返回空串的那层**之内**）：

```
【恋爱开局】(只在「恋爱开局」还不是「是」的恋爱对象上问一次): 若人设参考或已有剧情表明她与主角的关系**早已存在**(不是本轮才发生)——如人设写着青梅竹马 / 未婚妻 / 已在一起多年——就在「恋爱事件」数组里**额外加一条** 轴="开局" 的元素:
{ "轴": "开局", "好感": "恋人", "情欲": "有性趣", "名分": "未婚妻", "依据": "人设：两人是青梅竹马，已订婚" }
关系是刚认识、或本轮才建立的就**不加**这条。
- 「好感」「情欲」「名分」三个键都可省略, 只报你从人设/剧情判断得出来的; **只填阶段名, 绝不填数字**。
- 报的是「现在到哪一步」, 不是「以后会到哪一步」; 拿不准**取低一档**, 宁可报低不要报高。
- 这条的「依据」来自**人设或已有剧情**, 不必是本轮正文——它回溯的是已经存在的关系, 不是本轮发生的事。
- 卡上「恋爱开局」已经是「是」的 NPC **不要加这条**。

**判据为什么是「恋爱开局」而不是「好感值」（v10 裁决）**：本节初稿写的是「只在卡上还没有 `好感值` 的才问」「卡上已经有 `好感值` 的不要加」。那与 §3.9 第 5 条**直接矛盾**——模型漏报的那一轮，`应用恋爱回合` 照旧会把 `好感值` 落成 `'0'`；下一轮卡上就有了 `好感值`，提示词于是自己把窗口关死，§3.9 那条「漏报不锁死、下一轮再报仍被接受」永远走不到。`恋爱开局` 是**只有接受开局才会写**的标记（§3.9 第 6 条），拿它当判据，提示词侧的开窗条件才与代码侧的两道闸一致。`恋爱动向` 非空那道「防迟到乱开」由**代码**守（模型多问一次、代码拒掉，代价可接受），提示词不重复它。
```

**为什么让模型报阶段名而不是数值**：§8 的「不让 AI 产生任何数字」是铁律；阶段名是**领域词汇**，模型本来就要用它——§4.2 注入给主 AI 的 `恋爱: 好感 恋人 · 情欲 想要` 用的就是同一套词。

**这一段的成本**：只在有标记对象时出现；未标记时整段恋爱说明都不存在，所以不影响 §10 第一条。

   - **接受**：卡上无 `好感值`/`情欲值`/`名分`，且 `恋爱开局` 空、`恋爱动向` 空 → 开局 `{好感:'恋人', 情欲:'有性趣', 名分:'未婚妻'}` → `好感值 '86'` / `情欲值 '21'` / `好感阶段 '恋人'` / `名分 '未婚妻'`，并写 `恋爱开局 '是'`，`恋爱动向` 含「开局」字样。
   - **是基线不是增量**：开局 `挚爱` → `好感值 '96'`。单轮事件最多只能 `+8`，这条同时证明开局**不吃 `单轮上限`**。
   - **绝不覆盖**：卡上已有 `好感值 = '30'` → 同一条开局消息不改它，只应用事件（玩家手改优先）。
   - **只开一次**：`恋爱开局 = '是'` → 开局被忽略。
   - **防迟到乱开**：`恋爱动向` 非空 → 开局被忽略。
   - **漏报兜底**：既无开局也无事件 → **不写** `恋爱开局`，且按 §3.9 第 4.5 条**两条轴一个字段都不落**（卡上仍然没有 `好感值`）；下一轮再报开局**仍被接受**、`好感值` 落 `'86'`。
   - **空轮不落库（§3.9 第 4.5 条）**：已标记 NPC 首轮既无开局也无事件 → 卡上不出现 `好感值`/`情欲值`/`好感阶段`/`情欲阶段`/`名分`（`情感倾向`/`恋爱基准日期` 照常惰性补齐）。**有事件的那一轮照常落值。**
   - **手改后阶段跟上不受影响**：卡上 `好感值 = '80'`、本轮无事件 → `好感阶段` 仍被重算为 `暧昧`。
   - **只认第一条开局元素**：数组里有两条 `轴: "开局"` 时只取第一条，第二条静默忽略（事件循环里所有 `开局` 都 `continue`，不会被重复折算）。
   - **非法值**：`好感: '很爱'` → 该键忽略、其余键照常；三个数据键全非法 → 整条忽略且**不写标记**（窗口不关）。
   - **依据硬性**：缺 `依据` / 空串 / 全空白 → 整条开局拒绝（与名分事件同档）。
   - **同轮共存**：开局 + 事件同轮 → 先落基线再应用事件，`恋爱动向` 两段都在。
   - **名分压过**：同轮开局名分 `未婚妻` + 名分事件 `分手` → 以 `分手` 为准。

**"不标记 → 逐字节相同"的证明方式（v3 定稿）**：采纳开发侧的两层方案，**不做常驻 golden fixture**。

- **第一层（开发期一次性 byte-diff）**：改动前先跑一遍全开关矩阵（破限 × 预填充 × 头部填充 × 防截断 × 生理监测 × 有无 context），把 `JSON.stringify(messages)` 落盘；改完再跑一遍逐字节比对，零差异才算过。结果写进交付说明，比对脚本用完即删。
- **第二层（常驻回归守卫，写进 `tests/prompt-shape.test.ts`）**：
  1. `buildUpdateMessages(不带恋爱参数)` 与 `buildUpdateMessages(恋爱名单 = [])` 深比较相等——新参数缺省时输出一个字节都不变；
  2. 无标记时，全矩阵下任何一条消息里都不出现恋爱说明段的特征串；有标记时出现，且位置是任务 user 的**尾部追加**；
  3. 角色序列与任务下标不因标记而变（沿用现有 `[1]–[9]` 的口径）。

**为什么不存常驻 golden fixture**：那会让以后任何一次无关的共享提示词改动都红在这条上，是典型的"会被删掉或被无视的测试"。字节级等价由第一层在本次交付时证明一次即可，此后由第二层的结构断言守住。

## 8. 不做的事 / 已知取舍

**不做**
- ❌ 不建"恋爱事件史"台账（历史靠 `近期关键事件` FIFO + 纪要表 + 正文）。
- ❌ 不做第三条轴。

- ❌ 不迁移旧「恋爱对象表」的任何字段（外貌/穿着/所在地点/在场状态/人际关系/当下想法/过往经历全部丢弃，从零开始）。

- ❌ 不新增世界书条目。
- ❌ 不做"恋爱笔记"自由文本字段。

**已知取舍**
- **`恋爱事件` v1 无防重报手段**（`受孕事件` 有 `时间` 字段做窗口过滤，恋爱事件没有）。AI 若把上轮事件再报一次，数值会重复计。v1 **接受此风险**，靠提示词明确禁止 + `依据` 可审计；v2 可考虑补一个可选 `时间` 字段做窗口过滤。
- 情欲的**满足回落**依赖 AI 如实报"性行为/自慰/冷静收场"。
- `恋爱态度` / `恋爱标签` 是 AI 写的字符串，存在漂移可能。缓解：**增量**返回（没变化就不返回，沿用旧值）、词表闭合、上限 5。
- 重试是"**原样重发**"（`README.md:111-120`），同一份提示词重发时模型可能报不同事件，最终以**最后一次成功的那次**为准。
- 快照只保留 10 份（`快照.ts:20`），恋爱数值随快照回滚——这是**特性**，不是 bug。
- 名分变更由 AI 登记，可能误读剧情。缓解：**必附原文依据**并记进 `恋爱动向`，玩家一眼可查、可直接改字段。
