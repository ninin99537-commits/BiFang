Problem

这个领域的每条规则都有两份实现：一份是给模型的散文，一份是模型答错之后纠正它的代码。没有任何东西让两份一致， 所以一次修复要改两种语言——这正是最近 60 次提交的样子。更糟的是它们已经公开矛盾： prompts.ts:141 说孕 4~5 周为「疑似」、5~6 周以上「已确认」，而 update.ts:777–780 写的是 week < 4 / week < 6：同一条规则，两套边界，谁权威没人能回答。

Solution

一个 module 持有规则本身（边界与阈值作为数据，有序纯转换作为实现），随机源与剧情时钟以参数进入； 提示词段落由它生成或至少被它校验，卡内校正由它执行。顺序不再是注释里的叮嘱，而是流水线本身。

Wins

  • locality：149 次提交的热点收进一个 module
  • 规则只声明一次，散文与代码不可能再漂移
  • interface 就是 test surface：纯转换脱酒馆可跑
  • leverage：同一条规则服务模型与代码两个调用方
  • 顺序约束从注释变成类型与流水线
  • 骰子可注入 → 结果可复现

Problem

决定发什么 · 去问模型 · 把答案落到状态里 · 把状态存下来，四件事互相穿插，理解任何一件都要读完整段。 最尖的耦合：重试循环靠比对 '现在, 按上述全部规则开始执行任务。' 这个字符串字面量来定位任务消息，而它定义在 prompts.ts:241——两个 module 共有一个顺序不变式，中间却没有 seam。

Solution

四个阶段各自成为 module，各自拥有 interface 与失败模式；重试策略独立成 module，向提示词 module 索取锚点而不是自己反推。 删除测试：删掉这个函数，复杂度不会消失，只会散到 index.ts 与界面里——它值得留下，只是不该是一个函数。

Wins

  • interface 是 test surface：喂假 completer、断言结果
  • 「3 次重试、先坏后好」成为一条直接测试
  • prompts.ts 收回自己字面量的所有权
  • 并发守卫只剩一处
  • 错误模式统一：能拒绝，或返回结果
  • 统计只算一次，不再重走 payload
界面口径不一致的另一半： updateNpcStates 从不 reject（1695–1717 全部吞掉、只 toast + 写 debug store），所以 index.ts:111–113 的 .catch() 永远不可达； worldbook-inject.ts:78–80 同样吞掉全部失败，而 update.ts:1681 又加了 .catch()。两处 interface 声明「不抛，另行上报」，两处调用方写着相反的信念。

Problem

「发给模型哪些消息」由三处一起决定：settings 的五个布尔、builder 里的一串条件拼接、以及重试循环对数组做的手术。 重试循环必须知道策略产生的形状——它硬编码收尾字符串才找得到任务消息，还得保住尾部的 SPECIAL NOTE 与承诺。 另外 getUpdatePromptSeed（prompts.ts:298–318）是同一份提示词的第二个渲染器，已经漂移（无生理段、无各类尾段、用户消息只有 6 行）。

Solution

把「提示词形状」做成按模型名选择的策略 module：返回消息数组 并且声明锚点；重试循环读锚点，不再反推形状； 模型专用文本成为该策略的资源；种子渲染器与 builder 共用同一条渲染路径。

Wins

  • 重试循环不再知道策略细节
  • 新增模型 = 新增一个策略
  • 41 KB 模型专用文本集中成资源
  • 布尔组合不再相乘
  • locality：策略修正只改一个 module
  • 策略输出可被测试直接断言

Problem

「一个 adapter 只是假设的 seam」在这里不成立：快照日志、解析修复、标签过滤、更新 store、toast、悬浮球宿主都各有两个具体实现， 连 writeStateSnapshot 的五参 interface 都一字不差地抄了两遍。seam 已经为真，只是没有 module 站在上面—— interface 是一条靠人重新打字的命名约定。复制品已经漂移，规则修复要手工搬两次，README 把这件事记成了流程。

Solution

共享 module 以存储键与 payload 归一化器为参数，两个项目各自成为调用方；悬浮球宿主的样式搬运改用已有的 util/script.ts（MutationObserver + 可取消 destroy），而不是各自的 300/1200ms 重试。

Wins

  • 规则修一次，两个项目同时得到
  • 复制品从负债变成第二个 adapter
  • leverage：未来每个脚本继承日志与解析管道
  • 手抄同步义务消失
  • locality：iframe 清理与几何只有一份
  • README 不再需要记录同步动作

但要清楚它的父级是谁：真正让这个仓库无法验证任何东西的是 candidate 4——逻辑层直接把环境当数据源用，所以没有任何规则能离开酒馆运行。 host interface 一出现，candidate 1 的生理 module 就是它后面的第一个租户，candidate 2 的重试策略、candidate 7 的时钟、candidate 10 的快照日志 会依次跟着变得可测。这条路径上唯一需要协调的是 candidate 5：它把今天的复制品变成两个正当的 adapter，并让 README 里手写的「（烟火同步）」不再需要存在。
