## 三、这套界面最容易踩的四个坑

### 1. 面板 UI 与脚本代码分处两个 document

脚本跑在「脚本 iframe」的 JS 上下文，面板 UI 画在「球 iframe」的文档里。
**任何 DOM / document 级操作都必须用 UI 所在的 document**：

```ts
const 界面文档 = () => 根节点.value?.ownerDocument ?? null;   // 与 悬浮球界面.vue 的 frameWin 同源
```

用 `window.document` 会挂到脚本文档上，**静默失效且不报错** —— 本项目在这一条上连挂三版才修好（见第五节）。

### 2. `.bf-panel` 上有 `@click.stop`

面板根节点 `@click.stop`（防止点击穿透到酒馆页面），所以**冒泡阶段的 document 委托收不到面板内 click**。
要做事件委托必须 `addEventListener('click', fn, true)`（捕获阶段）。
`scroll` 本身不冒泡，也只能用捕获。

### 3. 生命周期钩子不能拿来"取 ref"

`onMounted → nextTick` 里取模板 ref 可能还是 `null`（真包上实测过），随后 `if (!el) return` 把监听悄悄跳过。
挂监听请**在 setup 里同步挂**（document 一定存在），或用 `watch(根节点, …, { immediate: true })` 非空再挂，并保持**幂等**（先摘后挂）。

### 4. 调试钩子不许裸挂

`window.__bfStateStore`（状态仓）与 `window.__bfNavDiag`（导航诊断）都是**排障后门**，统一挂在脚本变量 `彼方_settings.调试.暴露状态 === true` 之下，默认 `false`、关掉即 `delete`。
**不要为了省事直接挂全局** —— 那等于给任何同源脚本一条改状态的通道。

> **三个 `__bf*` 全局要分清**（2026-11-16 收尾实测）：
> - `__bfStateStore` —— 调试用，**门控**（`调试.暴露状态`）
> - `__bfNavDiag` —— 调试用，**门控**（同一个开关）
> - `__bfOpenPanel` —— **功能入口**，`悬浮球界面.vue:941` 无条件挂（脚本按钮靠它开面板），**看到它在不是漏洞**
>
> 收尾实测终态（真实卡「最后生还者」）：`store=false / diag=false / openPanel=true`，`settings.json` 里 `调试.暴露状态=false`。

## 四、结构与不变量（改之前先看）

- **令牌只有一个真源**：`theme.ts` 的 camelCase 键 → `--bf-kebab` 注入 `.bf-root`（暗色默认）与 `.bf-root[data-theme='light']`。**不要在 CSS 里写死颜色**；「实心底 + 文字」的组合必须用 `-ink` 令牌。
- **响应的四档媒体查询**：`≤1050` / `≤800` / `≤560` / `≤380`；`320px` 只是验收宽度，不另设断点。
- **字段控件化 18 项**（R9）：8 个 `<select>` + 4 个 `number` + 1 个胶囊多选 + 2 个日期文本 + 1 个 `cycle` 组合 + 2 个拆项（`生活状态` / `近期关键事件`）。
  拆项与回写**必须用源码现有协议**：`生活状态` = `类(值); 类(值)`（`生活状态.ts` 的 `join('; ')`），`近期关键事件` = `；` 分隔（`卡合并.ts`）。**别自创 `|` / `:` 格式**。
- **日期不换 `type="date"`**：会丢时刻、破坏 `correctPhysioByStoryTime` 的天数推进。保持文本 + `YYYY-MM-DD HH:mm` 提示。
- **`生理周期` 的 `/NN`（周期长度）只读**：来自隐藏键 `周期长度`，UI 不提供编辑框。
- **设置页 6 节是 UI 分栏，不是 schema 分组**：schema 只有 `启用幕后` / `接口` / `接口预设` / `更新` / `提示词` / `标签` / `调试`。改设置页前先看 `settings.ts`，别照着面板图层级推断。

## 五、这次踩过的坑（按代价排序）

1. **「注入等价」证明不了「真包生效」** —— 目录高亮一个 P2 挂了四版：
   `v1/v2` 挂载函数里 ref 为 null 提前 return → `v3` 委托挂上了但挂到**脚本文档** → `v4` 改用 `根节点.ownerDocument` 才对。
   结论：涉及事件挂载的修复，**必须在真包上验**，注入脚本只能证明"逻辑等价"。
2. **文档先于事实** —— 我最初的两份稿子有过整表互斥（令牌表）、臆测字段（`接口类型`/`请求超时`/`段落名称`/`预填充` 写成 input）、臆测章节（`恋爱追踪`/`生理状态` 独立成节）。全部由复查抓出，最终以 **HTML + 源码**为准回改。
3. **锚点会被覆盖** —— 交付前的 dist 快照必须复制到房间目录；同一个 `dist/index.js` 会被 watch 反复重建，"我当时测的是哪份"必须靠指纹而不是时间戳。
   我自己就错过一次：按时间戳推断 dist 是旧包，实际特征串 `1609e3bc` 在里面。
4. **`共用/提示条.ts` 是三方共用**（彼方/剧情导演/烟火）。改它要跑三家回归（`提示条.test` 72 / `提示条-面板开合` 33 / `bifang-panel-contract` 39），并且**先报后改**。
5. **设备模拟会整页重载酒馆** —— 切 mobile 视口时酒馆会 reload 并回到默认聊天，面板按设计返回空态。**别把它当成"面板丢数据"的缺陷**（我误判过一次）。

## 八、协作是怎么走的（给以后的项目参考）

三段式：**需求（派活/裁定）→ 实现（只写代码）→ 验收（只判定）**，外加 **复查（只读，两轮：开工前差异清单 + 收尾整体体检）**。

有效的做法：
- 每批交件必须带 **patch + 指纹 + 可复跑命令原文**；需求侧独立复算一遍再放行。
- 一批一个结论，打回要「文件:行 + 现象 + 期望」。
- 判据写死（R1–R16 + TD 台账），冲突时**以示例 HTML + 源码为准**，文档跟着改。
- 「另立/不夹带」是纪律：收尾阶段只修指出的那一处，其余记债。

无效/危险的做法：
- 用注入脚本代替真包验证（吃过四次亏）。
- 用时间戳代替指纹判断"测的是哪份产物"。
- 跨三方共用模块"顺手改"。

## 十、协作上这轮新立的三条规矩（都吃过亏）

1. **判定性证据必须落在 `tests/` 或 `docs/`**，不许只存在于 `rooms/` 或 `tmp/`。判据是"**验收能不能不问我、自己跑出来**"——跑不出来只算自述。这条促成了 `V4` 真实缺陷被发现。
2. **数清单类的东西优先 `import` 真值再 `.length`**，不要用正则切源码文本。`衣物/随身物` 里的 `/` 会把粗糙分隔切坏（一次算成 22、一次报成 32，实际 20/31）。
3. **凡陈述状态（未改/已复原/还是原样）必须当场贴产生该结论的命令输出**，贴不出来就写"我没查，不确定"。这条挡掉了两次"凭记忆写状态"。
4. 附：**开工要两个条件同时满足** —— 需求位明确派活 **且** 用户明确同意。只有前者不许动手。

### 十一·补：为什么"这个聊天"读不到世界近况（根因链，2026-11-16 复查核出的）

判据是三条同时满足才成立：
1. 烟火已启用（默认开）✓
2. 烟火在该聊天**成功跑过至少一轮** ✗ ← **当前缺这条**
3. 角色卡绑定了主世界书 ✓（`primary = 最后生还者-世界书`）

"没跑过"不是被关掉，是**没触发**，因果链全在源码里：
- 自动推进**只在收到 assistant 消息时触发**（烟火 `index.ts:72`）
- **正文 < 500 字直接跳过**（`:80-83`「疑似被截断, 已跳过」）—— 长思考 + 短正文的聊天很容易卡在这
- 更新频率要攒够楼层（`:84-90`）
- **启动补读只在"已有快照或已有世界数据"时才做**（`:129-137`），两样都没有 → 启动也不写
- 写条目还要求"有世界数据"（`inject.ts:48-52`），没有反而会**删掉**自己的条目

→ **排查口诀**：先看那个聊天有没有正经跑过一轮（正文够长、楼层够多），再看世界书里有没有 `【烟火】世界动向`；两样都没有就是"从未同步"，不是彼方读不到。

**这也是一条通用教训**：`B 天然生效` 这类结论必须区分「代码路径成立」与「运行时数据存在」——在"数据不存在"的聊天里验"路径成立"，是无效验收。

### 十一·补二：一个静默失败面 —— 「标签过滤」的 `只读` 模式

`settings.标签.模式` 有两个值（`settings.ts:96`）：
- **`排除`（默认）** → 剥离列表里的标签内容，**保留正文** ✅ 正常用法
- **`只读`** → **只保留列表里的标签内容**，正文被丢弃 ❌

而默认列表有 20+ 个标签（`thinking` / `think` / `aftertalk` / `think_nya` …）。一旦模式被改成 `只读`：
**彼方读到的不是正文，而是标签里的思考块**（甚至几乎为空），于是"基于错误文本产出状态"，**全过程不报错**。

**这是本轮第一次真机跑时踩到的坑**（用户第一次更新就撞上，切回 `排除` 后正常）。
- 排查入口：更新回执里"发出的内容"看着不像正文 → 先查这里；
- 更好的做法：设置页那两个模式要给出**一眼能懂的反例**（"选`只读`会导致读不到正文"），或者干脆加个默认值哨兵。这条属产品改进，未做。
