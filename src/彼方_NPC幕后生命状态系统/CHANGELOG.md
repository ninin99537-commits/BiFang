### 5. ~~删「迁移旧段」里"按锚点插入位置"那套~~ ✅ 已删（2026-11-19）

**它是白算的。** `bifang-probe-ordering.mjs` 实测：

```
① 换不同的 条目顺序 初始值 → 最终模板完全相同
③ 条目顺序 故意写成 ['b','a'] → 模板仍按 条目 数组顺序
```

原因（时间线）：

```
t1  迁移旧段()：按锚点算位置 → 写进 条目顺序
t2  条目转模板()：只读 条目 数组 → 写进 模板      ← 条目顺序 在这里被丢
t3  拼装：只读 模板
```

⚠ **必须记住的事实**：迁移后，旧段是按**数组顺序追加**的，**不按锚点**。
而这件事**删之前就已经如此** —— 那批不改变任何用户可见行为，只是把"假装在按锚点排"
的代码删掉。留这句话是因为：一句假话留在文档里（"迁移保留了锚点位置"）比留在代码里更难查 ——
代码还能跑给人看，文档只能被相信。

## 2026-11-14 — 保存/清空失败不再假装成功；关掉写入世界书后条目真的会清掉

- **用户的问题（一）**：点保存没反应、点清空说"已清空"，可刷新一看数据还在；更糟的是清空之后彼方又把整条聊天重分析了一遍，人物一个个"复活"。
- **根因**：写盘失败被吞在持久层里——`saveData` 两条路径都返回 `undefined`，调用方拿不到"成没成"，只能靠"返回的数据自己变了没"去猜；`clearAllData` 读不到当前楼层时把清空层写成 `0`，等于告诉下一轮"从第 0 楼开始分析"，于是整条聊天重新过一遍，而玩家以为自己清空了。
- **改动**：
  - `saveData` 现在返回 `boolean`（就是"落盘了没有"），`clearAllData` 返回 `{ 成功, 清空层, 失败原因? }`；`变更返回` 多一个 `失败?: string`，失败时 `数据` 是**入参原引用**。不引入抛错——两套失败表达并存，后来人一定会漏掉一套。
  - **写不进去就不提交界面**：以前是"先改 store 再写盘"，写失败时界面已经按没存下来的那份渲染了，玩家下一次刷新才发现丢了。现在写成功才提交。
  - 清空改成**先定截止点、再动手**：读不到当前楼层就直接放弃，一份快照都不删（失败时清空层保持旧值，不是 0）。
  - 界面八处出口（清空 / 加 NPC / 移除 NPC / 改状态卡 / 改事务状态 / 新增事务 / 恋爱标记 / 清空生理数据）都改成"有 `失败` 就弹 warning 并 return"，不会再出现"没存上却弹已保存"。
- **用户的问题（二）**：把「写入世界书」关掉之后，世界书里那条「NPC幕后生活」还在，主 AI 继续读一份过期状态。
- **根因**：清理只在"数据变更"时发生；启动与切聊天两条路都在 `目标 === '关闭'` 时直接 return，总开关关掉时外面还套着一层 `if (启用幕后)`。另外整个同步函数被一层 `try/catch` 吞成 resolved，三处调用方的 `.catch` 全是死路径——世界书坏了用户永远不知道。
- **改动**：关掉总开关等同于「写入世界书: 关闭」，启动 / 切聊天 / 删楼 / 切分支四条路都会走一趟清理（两本世界书里的彼方条目都删）；同步失败不再吞掉，取不到目标世界书时抛出，由上游弹一条警告。**注意时机**：关掉之后要等一次启动或切聊天才清干净，不是点一下立刻消失（想马上清就切一下聊天）。
- **验证**：`pnpm test` **142 个用例文件全绿**（新增 `bifang-save-failure` 15 条、`bifang-worldbook-shutdown` 9 条断言）；三条变异逐条实做——`saveData` 改回隐式 `undefined` → 红 5 条、worldbook-inject catch 改回吞异常 → 红 2 条、清空退回"先删后定" → 红 3 条（清空层实际变成 0）。

## 2026-11-11 — 「排除条目」写一条就够（标题含这些字即排除）、三家同一份判定、名单只按换行切

- **用户的问题**：一堆 `[mvu_update]1`、`[mvu_update]2`… 的条目，难道要一条条填进去？另外三个插件的名单输入各用各的分隔符（彼方 `,，;；、`、烟火 `,，、空格`、导演只有逗号），同一份名单换个插件就得换个写法。
- **回答**：判定本来就是**标题/备注包含即命中**（不是全名相等），填一条 `[mvu_update]` 就能挡掉整族条目。之所以会以为要写全名，是因为界面上那个输入框的提示写着「每行一个条目名（或它的关键词）」，示例又是个完整条目名——**功能在，说明没写清楚**。
- **改动**：
  - **判定收进 `共用/世界书排除.ts`**（三家同一份）：`解析名单()` / `命中排除()` / `条目标签()` / `排除说明()`。彼方、剧情导演、烟火各自那份 `isExcluded` 全是同一个语义的三份副本，这次合成一处；两家原来自带的“自己写的条目自动排除”规则（`extra.yanhuo` / `extra.daoyan`）保持不动。
  - **判定不分大小写**了：`[MVU_Update]` 这类写法也挡得住。
  - **名单只按换行切**：逗号 `,` `，`、顿号 `、`、分号 `;` `；` 一律算内容的一部分——条目名里本来就可能带这些字符，以前按它们切会把一个名字切碎，于是“填了却没排除掉”还找不出原因。三个插件的列表输入（排除条目 / 常驻条目 / 标签列表）都换成这个解析，界面文案统一成「每行一条」；烟火与导演原来那两个单行 `<input>` 改成 `<textarea>`（单行输入框根本打不进换行）。
  - **导演补上了这个设置**：`世界书排除` 一直在 schema 与读世界书的调用里（`取料.ts` 传了 `excludeNames`），但界面上从来没有输入框——现在“提示词”卡片里有一格。
  - **日志里报数**：`[彼方] 世界书用上 5 条 —— 查询 2 本(…); 排除条目挡掉 3 条([mvu_update]1、[mvu_update]2…)`；烟火、导演同理。静默排除是排查黑洞，挡没挡住要能看见。
- **边界（故意不做）**：**不按条目关键词（keys）匹配**。关键词多是角色名，用名字做排除会连带挡掉一大片人设条目——要排某条，写它的标题。
- **验证**：新增 `tests/worldbook-exclude.test.ts`（共用语义 27 条断言：换行切分、大小写、只认开头、keys 不参与、日志措辞）与 `tests/bifang-worldbook-exclude.test.ts`（彼方端到端 11 条断言）；全量 `pnpm test` **128 个用例文件全绿**，`pnpm build` 全部入口编译通过。

## 2026-11-10 — 设置页重排：两列瀑布 → 单列六组（空掉的栅格、满页的灰字都收掉）

- **症状**：设置页"看着乱"。实测（面板 1094×712，正文区 1048×603）：五组塞进 `repeat(auto-fit, minmax(400px, 1fr))` 的两列栅格，列高由各组内容决定，于是**第 1 行右列比左列高 476px、第 2 行左列比右列高 404px、第 3 行右列整格空着**——约 35% 的栅格面积是空白，空的位置还在阅读流中间（读到一半左列没了，得回头看右边）。另有 19 段 12.5px 灰字说明共 885px（占页高近四成），其中「接口能不能用」和「生理字段会一起注入」是同一个语气；页高 2357px ≈ 3.9 屏，没有目录。
- **根因（布局层，不是文案层）**：① 两列靠 `auto-fit` 自动流，**列高没有人为配对**，内容一变就重新错位；② 分组按"当初写在哪个 section"而不是"用户多久改一次"，`幕后更新` 一组 1154px 里塞了更新节奏 + 世界书两件事；③ 说明文字与控件同权（同一灰、同一量级），一条控件后面能跟三段解释；④ 全是"字段行 + 开关行"的自然流，没有组边界与编号，五组读成一条长清单。
- **改法**：**单列铺满正文区**（`max-width: none`，与仪表盘/人物/日志同宽；行宽交给控件：说明 74ch、数字框 200px、输入框才拉满）。顺带修了一个只有铺满时才看得见的坑：滚动条会吃掉右边的内边距，长页面必出滚动条 → 左 28px / 右 36px，**正文块设了 `max-width` 却不加 `auto` 外边距时更糟**（多余空间全堆右边，实测左 28 / 右 140）；现在 `.bf-page-settings` 用 `scrollbar-gutter: stable both-edges`，两侧各留一格，左右恒等。六组按"改得勤→改得少"编号：`01 接口 / 02 幕后更新 / 03 世界书 / 04 提示词 / 05 标签过滤 / 06 数据备份`，组头是衬线标题 + 编号 + 右侧状态摘要（当前的模型名 / 频率 / 写入目标 / 段数 / 过滤模式）。**全页只允许三种行**：开关行、字段行（120px 标签槽 + 控件）、分段行；开关行整行可点，悬停底色用 `box-shadow` 外扩 8px 铺出去（不靠加内边距，否则标题会离开左边线）。说明文字 12px、74ch 封顶、基本一行；原理与长表格进 `<details>`（「发送顺序」现在是代码块，不再是描边的说明段）。`幕后更新` 拆出独立的 `03 世界书`（写入 / 读取注入两个小节，常驻与排除两个 textarea 并排）。`04–06` 默认收起成三行目录。动作归位：「获取模型列表 / 测试连接」起在控件列左沿，「清空生理数据」变成「生理监测」那行的行内危险动作，「从文本导入」收进折叠。

- **空列表 / 拉取失败不再只报一句"失败"**：提示里明确写「拉不到列表不代表接口不能用，可直接手填模型名，再用『测试连接』实测」。判断接口是否可用的可靠依据是「测试连接」（它发真实短请求，不经过 `/models`）。
- **前提更正**：`/models` **不是** OpenAI 兼容协议强制要求的端点，协议只要求 `/chat/completions`。所以「拉模型返回 0 个」不能等同于"地址或密钥错了"。
- **用例**：新增 `tests/bifang-model-picker.test.ts`（40 断言，两版各验一遍）。钉住两条：① 候选面板与当前值无关、不许带过滤器；② 拉取模型不许覆盖已填的模型名。**反面判据**：把控件改回 datalist / 把覆盖逻辑塞回去，用例必须变红（已实测会红）。

## 2026-10-26（续）— 切 tab 不生效 / 添加NPC 弹窗不显示（同一根因的第二、第三个受害者）

- **症状（还是那位 Firefox 用户，装完 2026-10-26c）**：面板出来了，但**点「设置」tab 界面不变**（还停在仪表盘）；关掉面板再打开，直接显示设置页 —— 再点别的 tab 又不动。等于「状态变了、画面没换」。
- **根因同上一轮**：`tab` 是响应式的、也确实变了（所以重开就对了），但页面切换包在 `<Transition name="bf-pagefade" mode="out-in">` 里。**`out-in` 要等离场过渡结束后才插入新页**，而 Vue 的过渡收尾依赖 `requestAnimationFrame` —— 那台机器上它不跑，离场永远结束不了，新页永远插不进来。
- **同一个坑的第三个受害者**：「添加 NPC」弹窗（`bf-fade` 遮罩 + `bf-pop` 本体）。进入过渡的 `-enter-from`（`opacity: 0`）要等 rAF 才被摘掉，所以在他那儿这个弹窗**永远透明**。
- **做法（构建 2026-10-26d）**：**面板里一处 Vue `<Transition>` 都不留**，全部换纯 CSS 关键帧 ——
  - 面板本体 `bfPanelIn`（上一轮已换）；
  - 页面切换：去掉 `<Transition mode="out-in">`，改由 `.bf-page` 自己的 `bfPageIn` 播；
  - 模态：`.bf-modal-backdrop` 用 `bfFadeIn`、`.bf-modal` 用 `bfModalIn`；
  - 旧的 `.bf-fade-*` / `.bf-pop-*` / `.bf-pagefade-*` 过渡类全部删掉（留着只会有人再包一次）。
  关键帧由浏览器自己播完，不需要任何 JS 参与，rAF 死不死都一样。
- **验证**：产物 + 假宿主，先 `window.requestAnimationFrame = () => 0` 再操作：打开 → 仪表盘；点设置 → `.bf-settings-layout` 出现、仪表盘消失、导航高亮跟着走；点日志 / NPC / 仪表盘各切一轮全部生效；「添加」弹窗 `opacity: 1`、遮罩也在。`pnpm test` 85 个用例文件全绿（守卫用例新增「模板里不许再有 `<Transition>`」「不许再出现 `mode="out-in"`」「`.bf-page` 的关键帧在位」「旧过渡类已清掉」）。
- **一句话教训**：这个插件跑在**别人的嵌套 iframe** 里，任何"靠 JS 帧回调收尾"的动画都会在别人的机器上变成"永久停在第一帧"。面板里的动效一律写成纯 CSS 关键帧。

`buildInjectionPrompt` 交给主 AI 的那段，从「每个 NPC 一行、每行把字段名重写一遍」改成「表头 + 数据行」：字段名只在表头出现一次，每行按列对齐。

- **恋爱拆成 5 列**，不再是 `恋爱: 好感 暧昧 · 情欲 想要 · 名分 恋人` 那样一条复合段——`好感 / 情欲 / 名分 / 标签 / 恋爱态度` 各占一格，和其余字段同一张表。

- **零字段兜底照旧**：整批 NPC 一个字段都没有时，退回 `- 名字 | 状态未知`，不输出一行空表头。
- **不改提示词语义**：注入仍然只给阶段名/名分/标签/态度，不给 0–100 的裸数值；`情感倾向`、`恋爱动向`、`好感值`、`情欲值` 一律不进注入。
- **红线不受影响**：这段在 `buildInjectionPrompt` 里，不在 `buildUpdateMessages`。「没有标记任何 NPC ⇒ 更新提示词逐字节不变」的 192 组 byte-diff 打的是后者，二者是两个函数。注入侧的断言由 `tests/prompt-shape.test.ts`（表头首格是「名字」、恋爱五列落在表头末五位、裸数值不许出现）与 `tests/bifang-backstage-ledger.test.ts`（台账渲染落在「未完成事项」这一列的数据格里）钉住。

## 2026-10-10 — 恋爱子系统（标记即开关：不标记则提示词逐字节不变）

新增 `src/彼方_NPC幕后生命状态系统/恋爱规则.ts`（纯函数）+ `tests/bifang-love-rules.test.ts`，其余改动落在 13 个既有文件里（含 `数据变更.ts`：玩家手改 `恋爱标签` 也要过闭合词表）。设计口径见 `docs/彼方-恋爱子系统-策划案-v1.md`（v10）。

- **没有全局开关**：在 NPC 详情页点「标记恋爱对象」写 `恋爱对象=是`，取消标记写空值（空值即删除）。**没有任何 NPC 被标记时，提示词与从前逐字节相同**——恋爱说明段只做「任务 user 消息」的尾部追加，未标记时输出空串。这条由一次性 byte-diff（改 `prompts.ts` 的那一轮必须机械重跑：**192 组** = 64 组开关 × 3 变体，`JSON.stringify(messages)` 与基线 `1b9db1c` 比：未标记 **128/128 组逐字节相同、0 字节差异**；标记的 64 组剥掉那一段后逐字节相同、且那一段在 64 组里完全一致 = 恋爱说明段 **1323 字节**）+ `tests/prompt-shape.test.ts` 的常驻结构断言双重守住。
- **冷启动 / 开局（v10）**：人设写着「青梅竹马 / 未婚妻 / 已在一起多年」的 NPC，光标记会从 `好感 0 / 陌生` 起步（模型被禁止报数字，"既成关系"也不是本轮正文，单轮上限 +8 要爬 11 轮）。所以起点做成**第五样惰性补齐**：AI 在 `恋爱事件` 里额外加一条 `轴="开局"`，只报**阶段名**（`好感`/`情欲`/`名分` 可省，`依据` 必填、可来自人设），代码按**档下界**落值（恋人 86 / 有性趣 21）。两道闸：`恋爱开局 ≠ 是` 且 `恋爱动向` 为空（**防迟到乱开**）；开局是**基线不是增量**（不吃单轮上限），**只填缺省、绝不覆盖**手改值，同轮里 **`名分` 事件压过开局名分**；接受后写 `恋爱开局=是` 并留一行 `好感开局 86(人设：…)`，**没报就什么都不写**（窗口留着，漏报还能补）。
- **空轮不落库（v10 裁决 · 漏报不锁死的前提）**：数值状态类字段「**有值才写**」——`该轴有值 = 卡上非空 ∥ 本轮开局填了该轴 ∥ 本轮该轴有事件`（事件看**折算命中过没有**，不看净额：`+3` 与 `−3` 同轮相抵、净额 0 也照样落）。`名分` 没有伴生字段，闸更紧：**只在真的变了或本轮开局填了它时才写**（不每轮空转写回；玩家清空后不再被补成 `'无'`）；`情感倾向` / `恋爱基准日期` 是配置与锚点，照旧无条件惰性补齐。**没有这条，「漏报不锁死」是假的**：漏报那轮若先把 `好感值` 落成 `'0'`，下一轮的缺省闸就不成立 → 86 永远填不进去，而标记照写，窗口就此关死。代价（已知并接受）：第一次产生数据前详情页两条轴显示为**空**而不是 `0 / 陌生`。
- **AI 只报事实，代码算数值**：AI 只返回 `恋爱事件`（轴/类型/强度/依据），代码折算成两条轴：好感（存量，不衰减）与情欲（状态量，会被满足与时间回落）。代码持有阶段表、±2 滞回、情感倾向的 (敏感度, 粘性) 系数、单轮上限、情欲地板。
- **单轮上限只夹涨方向**（好感 +8 / 情欲 +20）：落方向不设限，一条「性行为(大)」情欲真的掉 −35 而不是被夹成 −20（用例钉住）。
- **系数怎么乘（v4）**：好感涨/落与情欲涨 × 敏感度；**情欲落（满足回落 + 时间回落）只 × 粘性，不乘敏感度**——否则"外放(1.4)"会变成"性爱之后冷却得更快"，语义正好反了。病娇的「性行为(大)」= −35 × 0.2 = −7。
- **情欲地板只截断回落、不抬升（v4）**：`实际回落 = min(原回落, max(0, 情欲 − 地板))`，地板按**结算后**的好感阶段取（刚确定关系的那一夜之后就按新关系冷却）。情欲低于地板时回落不生效，但也不会被拉到地板上——所以"深爱但清心寡欲"能存在，手改的情欲值也不会被凭空抬高（与验收标准"手改后不覆盖"一致）。
- **一份隐藏基准日期**：`恋爱基准日期` 存上一轮结算的剧情日期（照 `生理周期日期` 的先例，只前进不倒退），时间回落按真实天数差算；剧情时间缺失/非法时跳过回落且不更新基准——**没有依据就不动手**。
- **闸在复制之前**：`mergeCard` 末尾那整块恋爱代码以 `恋爱对象=是` 为闸，未标记的 NPC 连 `恋爱事件` 都**不复制入卡**（它不在 `CARD_FIELDS` 里，一旦入卡没有任何路径会删，会随快照膨胀），只 `console.warn` 一句；用例钉住"未标记的卡上不出现 `恋爱事件` 键"。
- **注入只给阶段名/名分/标签/态度，不给 0–100 的裸数值**：主 AI 需要的是"该怎么演"，不是分数。生成侧要求只写外在可观察的倾向；真机若仍在复述态度，从 `prompts.ts` 的 `buildInjectionPrompt` 摘掉那一段即可（字段仍在卡上，零数据损失）。
- **一致性**：名分变更必须走名分事件**并附原文依据**（缺依据整条拒绝，不做 `依据 || 类型` 兜底），`恋爱动向` 记一行因果供玩家核对；`恋爱标签` 走闭合词表（词表外的词丢弃、去重、上限 5），AI 路径与**玩家手改路径**都过同一个 `校验标签`，且"归一化后为空"不等于"想清空"（AI 报错 → 保留旧值；玩家清空输入框 → 删字段）；旧「恋爱对象表」数据一律不迁移，从零开始。

## 2026-10-09 — 重试不再回喂上次输出与错误原因

「重试时把上一次的坏输出连同错误原因发回给 AI，让它自己改」这套机制整个删掉了（当初是为了治"AI 不肯守格式"）。现在模型已经稳定守格式，这个补丁只剩坏处：每次重试都要多塞进一大段上次的坏输出（白占上下文），还可能被模型顺着抄一遍。

- **重试 = 原样重发同一份提示词**。`共用/模型往返.ts` 里的 `反馈文本` / `带反馈` 与 `上次原因` / `上次输出` 两个状态一并删除，`attemptMessages` 永远是 `[...messages]`。
- **连带拆掉整条只为回喂存在的管线**：彼方的 `锚点`（`提示词锚点` / `算锚点` / `请求参数.锚点`）——它的唯一用途就是把反馈接到「任务 user 消息」上；解析器的 `片段` 字段（每次请求都白切一份 JSON 候选，成败都给，现在没有调用方）；`模型请求.ts` 的 `extractJsonSnippet`。
- **重试本身完全保留**：次数仍是 3 次，接口错仍等 `2 秒 × 第几次`、结构错仍等 0.6 秒；「不是 JSON 就抛出」的口径照旧。之所以留着结构失败的重试，是因为"输出被接口砍断"这类失败原样重推一次往往就成了（2026-10-01 真机实测：3284 字的输出被砍断，手动重推即成功）。
- 界面上那句「正在重试（n/3）：…」与日志里的阶段名一个字没改——`取重试理由` / `结构失败标签` 都还在，只是不再进提示词。

## 2026-10-03 — v5.15 「未完成事项」升级为事务台账 + 「持有物」字段退休

同一件事——"跨楼层的事实不能被模型一轮轮改写掉"——以前压在几个字段上, 现在收进一本账:

**一、「未完成事项」从"一句话"升级为事务台账**（新增 `事务台账.ts`）

它以前是**每轮重写的一句话**: 具体名词没有任何锚点, 模型一轮记错, 之后所有轮次都拿错的那份当"上一轮", 于是永久错下去(真机事故: 幕后定下"给女儿买一个玩偶当生日礼物", 推了几轮进正文就变成了"蛋糕")。现在每个 NPC 的「未完成事项」是一本**只增不改的账**:

- 每项是 `{编号, 时间, 内容, 状态, 结果}`: 编号 `T1/T2…` 由**代码分配**(新事务不用写编号), **内容写下即冻结**, 之后只能改**状态**(只有 `进行中`/`已完成`/`已作废` 三个值)与结果——要改内容就作废旧条、另开新条, 旧条内容一字不改地留在账上。整份重抄是幂等的(重抄的内容会被丢弃, 一律以账上写的为准)。
- **每个 NPC 最多 8 条**: 超额先淘汰最旧的已办, 但 `进行中` 的**永不淘汰**。
- **旧数据自动迁移**: 卡里原来的整句字符串, 读取时直接变成一条 `进行中`(内容一字不改), 不需要你手改。
- **注入改成"事实"口吻**: 发给主 AI 的现在是"进行中逐条 + 最近已办摘要 + 一句固定提醒", 提醒里写明"以上是幕后已发生/已定的事实, 正文收束时必须照此兑现; 其中的具体物品、人名、地点不得替换或泛化"; 更新 AI 那边同样照此要求——旧账写"玩偶", 就不许写成"蛋糕/礼物/东西"。
- 面板跟着改: 详情页显示台账(进行中在前、带状态徽章, 状态与结果可直接改), 「🛡️ 事实档案」页改成只读的台账行; 顺手修掉"数组直接进文本清理函数"的崩溃, 以及**编辑表单保存时把台账当字符串写回、把整本账静默丢掉**的老问题。

- 先修掉它"**越滚越长**"的真机问题: 列表切条只在**括号外**切(顿号在括号里是描述的一部分, 如"旧运动外套(2025-09-18 身上套着、袖子挽到手肘)"), 把模型照抄提示词写下的"顿号/逗号/分号"三个**词**还原成符号, 同名按括号前的物品名归并只留一条, 清掉"是另一条子串"的碎片——存量脏数据在下一次更新时自行收敛。

- **最新正文标注**：「最近正文回复」每条按顺序标注（【较早回复 1】…【最新回复】），提示词明确**在场/当前场景一律以【最新回复】为准**——较早楼层在场但最新回复已不在场的 NPC 不再被误列「在场NPC」，也不会因较早楼层的出现而误判。

## 2026-08-03 — v1.18 世界书激活改用酒馆主AI机制

- **不再自己扫描匹配世界书**：之前彼方遍历所有世界书条目、自己按关键词匹配（与主 AI 的激活结果不一致，且浪费性能）。现在直接调用酒馆模板环境里的 `getWorldInfoActivatedData(世界书名, 扫描文本)`——**和主 AI 完全相同的激活逻辑**（蓝灯常驻、绿灯关键词匹配、概率等），命中哪条就用哪条。实测 616 条世界书激活仅需约 40ms。

## 2026-08-03 — v1.17 后台互动按当前状态替换 + 移除判定收紧

- **后台互动改为"当前仍在进行"整体替换**：AI 返回的「后台互动」就是当前有效的互动清单，已结束的互动自动消失（如上一轮汤米×杰西的交接询问，本轮他们不再互动就不会再列入）；没有互动时返回空数组即清空。提示词会带上现有的后台互动记录，供 AI 判断哪些仍在进行。
- **在场建档**：识别出的新重要 NPC 即使在场也要创建状态卡，在场判定只针对已追踪的 NPC（已在上版强化，本版在输出要求中再次明确）。
- **移除NPC 只移除已建档角色**：只有现有状态卡/名单中已有的角色才列入 `移除NPC`，从未建档的角色（如被提到但没被追踪的）不再列出，避免无效移除。

## 2026-08-03 — v1.16 更新卡顿优化

- **世界书处理提速**：扫描文本小写化只算一次（原来每条触发词都对整个文本做一次小写转换）；世界书条目按名字缓存 60 秒（不再每次更新都重新拉取上千条）；EJS 模板环境按需创建（只有条目里真的含 `&lt;%` 才合并消息变量）；宏替换只在含 `{{` 时执行；清理逻辑无模板语法时直接跳过。
- **减少全量楼层读取**：「读取最近 N 条 AI 回复」只拉楼层末尾一小段，不再每次更新都读取整个聊天。
- **清空层不再长期生效**：清空层原本在清空后一直按「只分析清空之后的楼层」过滤，导致删除楼层后续聊时自动更新只发 1 条新楼层。现在清空层只在**清空后的首次更新**生效（防旧NPC复活），成功更新后自动重置为 0，恢复正常分析最近 N 楼。

## 2026-08-03 — v1.15 上下文补全 + 建卡判定放宽 + 历史记忆

- **历史记忆（`<recall>`）**：用户输入里的 `<recall>...</recall>` 块是历史轮次纪要的索引，其中的 AM 编码（如 AM0384）就是对应纪要世界书条目的触发词——彼方世界书按主 AI 的方式激活，正文/用户输入里出现 AM 编码即自动触发对应纪要。提示词新增「历史记忆」规则：不要把过去的事当成今天正在发生的；角色只知道自己亲身经历/听到/看到/被告知的事；记忆里的旧状态不代表现在。
- **建卡判定放宽到「最近剧情或最近正文回复」**：v1.13 把「正文」理解成只有 AI 回复，导致只出现在用户输入里的角色（如乔尔/泰丝）建不了卡。现在最近剧情（用户输入）和最近正文回复里实际出现的角色都算；仅被名字提到/回忆/谈论仍不算。新识别的重要 NPC 即使在场也创建状态卡，在场判定只针对已追踪的 NPC。

## 2026-08-03 — v1.14 修复思维链泄漏 + 手动更新补全用户输入

- **修复 Subtext 思维链整块泄漏**：Subtext 格式是 `<!-- begin_of_Subtext_think -->`（注释标记）＋**纯文本思维内容**＋`<!-- end_of_Subtext_think -->`，之前只删了标记、中间的思维文本（"首先分析用户输入…"等上万字）全发给了彼方接口，导致它看到的"正文"其实是模型的思考过程。现在整块（含中间内容）一并删除，只留真正的剧情正文。
- **手动更新补全用户输入**：清空后「最近剧情」上下文被清空层过滤成空，导致发到接口的只有 AI 回复没有用户输入。现在手动更新（悬浮球/脚本按钮）会连同用户输入一起完整分析，自动更新仍受清空层约束。
- **世界书条数上限改为设置项**：新增「世界书条数上限」（默认 40 条，范围 1–200），与字数上限并列，控制每次注入世界书的条目数。

- **死亡/退场角色强制移除**：正文明确死亡的 NPC 一律列入 `移除NPC`，绝不再返回其状态卡；名单中已追踪的 NPC 正常更新幕后生活不受此限制。

## 2026-08-03 — v1.12 世界书只读角色卡绑定

- **世界书只读角色卡绑定 + 聊天世界书，不再读全局世界书**：之前会把全局世界书排在前面，蓝灯常驻条目容易占满容量上限导致角色卡主世界书/附加世界书的内容进不了请求。现在只读取角色卡主世界书 + 附加世界书 + 聊天世界书，全局世界书一律忽略。
- **世界书内容上限改为设置项**：新增「世界书内容上限」输入框（默认 8000 字，范围 500–50000），控制每次注入世界书的字数上限，防止请求过大。
- **世界书条目模板语法按主 AI 规则求值**：彼方读的是原始世界书条目，条目里的 ACU 模板语法（`<if cond="cell:恋爱对象表/艾莉/年龄 >= 19 , cell:重要角色表/艾莉/年龄 >= 19">` 这类条件块）之前会原样发给接口。现在彼方会用 ACU 的表格数据（`AutoCardUpdaterAPI`）**真正求值条件**：`seed` 关键词匹配最近回复、`cell` 查表比较（支持 `,`OR/`&`AND/`!`NOT/括号，含嵌套 `<if>` 与 `<else>`），只保留命中分支——和主 AI 看到的内容一致。`{[db...]}`/`{[sql "..."]}` 表达式、`<random/>` 等标签、`$v:` 变量引用无法求值，注入前移除；`<if db/sql>` 与无法求值的条件保守保留主分支内容。条目前的「【世界书名】」来源标记已去掉。
- **世界书条目还支持酒馆宏与 EJS 模板**：条目里的 `{{user}}`/`{{char}}` 等酒馆宏会按主 AI 的方式替换（用 `substitudeMacros`）；`<% ... %>` EJS 模板会用与主 AI 相同的模板环境（`EjsTemplate`，合并全局/聊天/楼层变量，MVU 变量 `stat_data` 等可直接使用）渲染；EJS 环境不可用时兜底移除模板块，避免把代码发给更新 AI。处理顺序为 `<if>` 求值 → EJS → 宏替换 → 清理。

## 2026-08-03 — v1.10 修复清空/移除NPC 无效

## 2026-08-03 — v1.0 创建

- 依据《Elsewhere/彼方 设计初稿》实现核心工作流: 监听 AI 回复 → 检测不在场景中的 NPC → 用独立 API 更新其幕后状态卡并保存到聊天变量。

- 时间跳跃处理: 从正文回复中识别"几天后/几个月后/一年后"等, 只更新跳跃后的当前状态。
- 未来扩展方向全部实现: 秘密想法、隐藏目标、位置、可能偶遇、NPC 后台互动。
- 独立 OpenAI 兼容接口: 支持自定义接口地址/密钥, 通过 `GET /v1/models` 获取模型列表并下拉选择, `POST /v1/chat/completions` 生成更新; 内置超时、错误提示、连接测试。
